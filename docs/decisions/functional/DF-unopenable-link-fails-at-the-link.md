# DF-unopenable-link-fails-at-the-link: a directory link whose target cannot be opened fails at the link or is pruned, and exits move with it in both directions

**Date:** 2026-11-07

## status: Accepted

## 1. Context

A directory link whose target exists but cannot be opened made the walker raise an error with no path, and the failure fell back to the walk root. Each walk root that met the link therefore named a different place, none of them the one that failed: `error: docs: permission denied`, and on `grund 0.21.0` an empty location for the config root. The line told its reader to make a readable directory readable. Because the location was a walk root, nothing asked whether the walk was going to read through the link at all, and a path-scoped run judged the failure as being somewhere else. Reported as [issue #1266](https://github.com/agent-grounds/grund/issues/1266).

## 2. Decision

The failure is located at the link, once ([§FS-scan.scope.links.unresolvable.unopenable](../../functional-spec/FS-scan.md#scopelinksunresolvableunopenable-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-once)), and is reported only where the scan would have read through the link, the project-root fence and the ownership boundary included, judged on the link's canonical target ([§FS-scan.scope.links.owed.fence](../../functional-spec/FS-scan.md#scopelinksowedfence-the-project-root-fence-is-judged-on-the-target-opened-or-not)). Both halves move exits, because the fallback was what decided them.

### 2.1 Exits move in both directions

Measured on `grund 0.21.0` and on this change. Each project is otherwise clean, with `docs/FS-b.md` indexed and cited. "Barred" is mode `000`, run as a user that mode stops.

| Tree | Run | Before | Now |
|---|---|---|---|
| **Outward:** `docs/ext -> ../../outside`, `outside` barred | `grund check`, `grund check docs`, `grund check --full` | `error:` at the config root and at `docs`, exit `2` | nothing further, exit `0` |
| Outward | `grund list`, `grund refs FS-b`, `grund FS-b`, `grund cover` | the same failure, exit `2` | the answer, exit `0` |
| Outward | `grund fmt --write` | `error: nothing was rewritten: …`, exit `2` | the rewrite, exit `0` |
| Outward, with a citation `fmt` would rewrite | `grund fmt --check` | `error: nothing was rewritten: …`, exit `2` | the rewrite it would make, exit `1` |
| Outward, with an `unknown reference` in `notes.md` | `grund check` | exit `2` | that finding, exit `1` |
| Outward, one level down: `docs/sub/ext -> ../../../outside` | `grund check docs/sub` | `error: docs/sub: permission denied`, exit `2` | nothing further, exit `0` |
| **Never read:** `docs/ext -> ../real`, `real` barred, and both kept out of the walk, by `.gitignore`, by `exclude = ["ext/", "real/"]`, or by a hidden link name with `exclude = ["real/"]` | `grund check`, `grund check docs` | `error:` at the walk roots, exit `2` | nothing further, exit `0` |
| **Into a member:** `docs/ext -> ../m/secret`, a loaded workspace member's directory, barred | `grund check docs` | `error: docs: permission denied`, exit `2` | a caution at `m/secret`, exit `0` |
| **Only the link reaches it:** `docs/ext -> ../real`, `real` barred and hidden, or under `exclude = ["real/"]` or `.gitignore` `real/`, and the link itself not ignored | `grund check docs/ext` | `warning: nothing to scan …` and cautions at the walk roots, exit `0` | `error: docs/ext: unreadable symlink: permission denied; …`, exit `2` |
| **The link's name is excluded too:** `exclude = ["ext/", "real/"]`, or `.gitignore` naming `docs/ext` and `real/` | `grund check docs/ext` | the same warnings, exit `0` | the same error, exit `2` |

From `2` to `0` or `1`: a run whose only failure was a link the walk was never going to read. From `0` to `2`: a run scoped to a link it could not open, where no other walk root reports that link's target. `fmt --write` may rewrite here because the declaration set it resolves against is the one a readable target gives, so [§REQ-no-wrong-citation.3](../../requirements/REQ-no-wrong-citation.md#3-no-wrong-write)'s proof of completeness holds.

### 2.2 What moves in bytes only

- A whole-project run over an inward link exits `2` before and after. Its lines become `docs/ext` and `real`, where they were the config root, `docs` and `real`. The same holds for a run where only the link reaches its target, which now names `docs/ext` alone.
- `grund check notes.md`, which reports neither the link nor its target, exits as it did. Over an outward link its cautions go and `success` returns. Over an inward one the cautions at the walk roots become a single one at `docs/ext`.
- `grund check docs/ext` over an inward link whose target the walk does read exits `2` on both builds, and now names the link as well as `real`.

### 2.3 What does not move

- `grund check docs/ext` over an outward link is the root gate's answer, [§FS-scan.scope.links](../../functional-spec/FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed): `warning: nothing to scan …`, exit `0`. Only the caution that named `docs` goes.
- The same unreadable directory standing at `docs/ext` with no link is reported at `docs/ext` and exits `2` on both builds, for `grund check`, `grund check docs` and `grund check docs/ext`.
- A whole-project run over a loaded member's unreadable directory exits `2` on both builds, for that directory.

## 3. The correction route

These exits flip a shipped verdict, which [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered) allows only by a named route. [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids) is the route, and all five conditions hold.

1. *Prior prohibition.* The old exit `0` violated [§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips): `grund check docs/ext` could not open the directory it was asked about and passed. That section says a file the scan cannot read is reported at its path and the run exits `2`, and that an incomplete report "never passes as if it were". The directory was owed: with the target readable, the same run reads through the link and reports `docs/ext/x.md:3: error: unknown reference FS-nope`, on `grund 0.21.0` too. The old exit `2` violated [§REQ-never-crashes.2](../../requirements/REQ-never-crashes.md#2-exit-codes-are-the-api): that section freezes `0` for a clean run and `2` for a scan failure, the requirement opens by promising truthful exit codes, and its [§REQ-never-crashes.1](../../requirements/REQ-never-crashes.md#1-every-failure-is-a-diagnostic) gives `2` to a run that could not complete. These runs completed. With the target readable, `grund 0.21.0` prints the same bytes and exits the same as this change prints with the target barred: over an outward link on `check`, `check docs`, `check --full`, `list`, `refs`, `grund FS-b`, `cover` and `fmt --check`, with and without a finding, and `fmt --write` makes the same rewrite; over the links kept out of the walk on `check` and `check docs`. So the unreadable directory took nothing out of the report. The one row with a line of its own, into a loaded member, keeps the caution about that member's directory, which is a real failure of the member's walk and leaves the exit alone, as [§FS-check.1.3.6.3](../../functional-spec/FS-check.md#1363-a-file-the-wider-walk-could-not-read-is-said-out-loud) says. Each section belongs to a separately declared hard requirement in every release since `v0.10.1`, the first release whose walk follows directory links, so each prohibition already applied when the old verdict shipped.
2. *Accepted proof.* This record, which cites those sections and proves the conflict above. [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path)'s deprecation path does not fit, because there is no old form to carry beside a new one: nothing a user writes selects the wrong location. [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations)'s mechanical migration does not fit either, because nothing a user wrote is at fault, so there is no command to run on anyone's behalf.
3. *Named release.* The release note below names each of these exits, who notices and what to do.
4. *Actionable findings.* Where `0` becomes `2`, what replaces the old verdict is `error: docs/ext: unreadable symlink: permission denied; make the path readable, or keep it out of the scan`: located at the link and naming the action, as the line for an unlinked directory at that path already is. Where `2` becomes `0` nothing replaces it, because the failure goes. Where `2` becomes `1` what is left is a finding the run had already found and still printed.
5. *No new licence.* This route cannot justify ordinary policy tightening, feature removal, or a prohibition invented by this change, and it is used for none of them. No check, rule or diagnostic code is added, a run gets what the same tree with a readable target or an unlinked directory already gets, and neither prohibition is written here.

**The weak point.** The exit `2` is the narrower ground, and the objection is plain. Something did fail to open during the scan; `2` is, in the words of [§REQ-never-crashes.2](../../requirements/REQ-never-crashes.md#2-exit-codes-are-the-api), "a scan or CLI-level failure"; and that section's sharpest sentence is about a wrong `0`, not a wrong `2`. The reading this record takes is the one [§FS-check.2.4](../../functional-spec/FS-check.md#24-an-incomplete-run) writes down: a `2` "always means 'do not trust this report as complete'", and a failed open in the walker's own loop check, on an entry the walk then refuses, is not a hole in any report. An objector can still hold that any failed open is a scan failure, and this record refuses that position rather than disproving it. It would make a project's verdict turn on the mode of a directory the project never reads, which may lie outside the project and belong to someone else.

There is a narrower fix for that objector: report an outward link at the link and keep its `2`. It would repair the location and move no exit from `2`. It was not taken, for three reasons. [§FS-scan.scope.links.owed](../../functional-spec/FS-scan.md#scopelinksowed-which-unresolvable-links-are-owed-a-report) already says a link `.gitignore` covers stays silent, so that half of the move corrects the code to a point that had shipped. The fence prunes the same link in silence when its target can be read. And the line would ask its reader to make readable, or keep out of the scan, a directory the scan has already kept out.

The exit `0` has a smaller objection: the old run was not silent, and each of its warnings was true of something. But the caution called the failure outside the report scope because it was located at a walk root, and the failure was exactly the path the run was given.

## release-note: Release note

- [§FS-scan.scope.links.unresolvable.unopenable](../../functional-spec/FS-scan.md#scopelinksunresolvableunopenable-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-once), [§FS-scan.scope.links.owed.fence](../../functional-spec/FS-scan.md#scopelinksowedfence-the-project-root-fence-is-judged-on-the-target-opened-or-not), [§DF-unopenable-link-fails-at-the-link](DF-unopenable-link-fails-at-the-link.md#df-unopenable-link-fails-at-the-link-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-or-is-pruned-and-exits-move-with-it-in-both-directions), [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids): **a directory link whose target cannot be opened fails at the link or is pruned, never at a walk root, so exits move in both directions.** **Exits move from `2` to `0`:** where the only failure was such a link and the walk was never going to read through it, because its target is outside the project or inside a loaded workspace member, or both the link and its target are ignored, excluded or hidden, `grund check`, `check <path>`, `list`, `refs`, `grund <ID>`, `cover` and `fmt --write` now give the answer they give with a readable target, and `fmt --write` rewrites where it refused. `check` and `fmt --check` exit `1` where that answer holds a finding or a rewrite. Nothing to do: the run read everything it was going to read. **Exits move from `0` to `2`:** `grund check <link>`, naming such a link whose target the other walks do not read, now reports `error: <link>: unreadable symlink: permission denied; …` where it said there was nothing to scan. Make the target readable, or stop naming the link. **Who notices:** a hook or CI step narrowed to such a link, a run that relied on exit `2` to learn that a directory the project never reads had become unreadable, and a script reading the failure's location, which is now the link where it was the config root or a home. The verdict moves by the correction route of [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids), because the old exit `0` broke [§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips) and the old exit `2` broke [§REQ-never-crashes.2](../../requirements/REQ-never-crashes.md#2-exit-codes-are-the-api); every finding that replaces it names its location and the action to take. Closes [issue #1266](https://github.com/agent-grounds/grund/issues/1266).
