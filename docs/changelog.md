# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file and **older releases live one-per-file under `docs/changelog/`**, so a reader (human or agent) only loads the history they ask for. Nothing is written here between releases: a release writes its own section from the pull requests merged since the previous tag and the compatibility notices the decision records gained since then ([§FS-distribution.4.6](functional-spec/FS-distribution.md#46-the-release-lists-the-pull-requests-merged-since-the-previous-tag)). The changelog is part of the conformant tree, so every citation a section carries is checked (`grund check` validates them).

## 1. Conventions

### 1.1 Shape of a release

From 0.16.0 on, a release is the list of the pull requests merged since the previous tag, newest first, one line each — `- [<title>](<url>) (PR #N)`, the pull request's own title escaped so that it is text and never a citation ([§FS-distribution.4.6.2](functional-spec/FS-distribution.md#462-one-line-per-pull-request-its-title-linked)) — followed, when the release has any, by `### Compatibility notices`. Every merged pull request is listed, docs-only ones included. Releases up to and including 0.15.0 keep the Keep-a-Changelog sections they were published with — `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`, and in the first release narrative subsections such as `Baseline` or `Distribution and bindings` — and are not rewritten.

### 1.2 Compatibility notices and schema versions

A compatibility notice says what a verdict change breaks and for whom. It is written where the change is decided, as a `## release-note: Release note` section holding one bullet on the decision record, and the release that first carries it publishes it under `### Compatibility notices` ([§FS-distribution.4.6.4](functional-spec/FS-distribution.md#464-compatibility-notices-come-from-the-decisions)). A bump of `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) or of the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)) is a breaking change for the consumer, so it is announced the same way: a notice, with its migration, on the decision that bumps the schema. Up to 0.15.0 it was a `**Schema:**` bullet under **Changed**.

### 1.3 How a section is generated

`scripts/prepare_changelog_release.py prepare <version>`, which both release helpers run ([§FS-distribution.4.4](functional-spec/FS-distribution.md#44-two-helper-workflows-bump-the-version-on-a-validated-candidate)), reads every commit since the previous tag, asks the forge which merged pull request each belongs to ([§FS-distribution.4.6.1](functional-spec/FS-distribution.md#461-the-range-is-every-commit-since-the-previous-tag)), and writes the section; `preview` prints the same body and writes nothing. A forge call that fails, or answers with something that is not JSON, is tried again after one second and then two, so one dropped connection does not lose the release ([§FS-distribution.4.6.3](functional-spec/FS-distribution.md#463-a-refused-release-leaves-the-tree-as-it-was)). When the range still cannot be read whole it refuses and writes nothing ([§FS-distribution.4.6.3](functional-spec/FS-distribution.md#463-a-refused-release-leaves-the-tree-as-it-was)). So a pull request's title is its release line, and a pull request writes nothing here.

### 1.4 Progressive discovery

Only the **most recent release** is inline. When a new release ships, its generated section takes the inline place, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md`, and a one-line link counting what it held is added under [section 3, Older releases](#3-older-releases) ([§FS-distribution.4.5](functional-spec/FS-distribution.md#45-what-the-version-bump-includes)). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

### Compatibility notices

- [§DF-config-discovery-keeps-lexical-parents](decisions/functional/DF-config-discovery-keeps-lexical-parents.md#df-config-discovery-keeps-lexical-parents-config-discovery-climbs-the-paths-lexical-parents-before-resolving-directory-links), [§REQ-no-missed-citation.1](requirements/REQ-no-missed-citation.md#1-no-silent-skips), [§REQ-backwards-compatibility.5](requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids): In **0.22.2**, the verdict changes from exit `0` to `2` for a narrowed `check` whose governing config refuses an outward kind home or whose scope holds an unreadable manifest. Commands through directory links, including `config explain` and `config migrate`, search the path's lexical ancestors, so a config above the target or the defaults no longer replace the enclosing project's config. The same search now finds the workspace `grund init` teaches, so a linked target no longer lists a stranger workspace's members; the config of a `grund-lsp` workspace folder opened through a link, which now reports that project's config errors; and the member a narrowed run lies in, so a path under a member with no config of its own runs as that member, its paths spelled from the member, even where it links out of the workspace or into another member. Every finding names its location and the action to take: repair the unreadable manifest named by the version-1 finding, or move the outward version-2 kind home inside the project and update its config entry. No link traversal policy changes.

- [§FS-rules.3.2.1](functional-spec/FS-rules.md#321-counting-distinct-cited-declarations): **an outbound count may count distinct cited
  declarations, and refusals of a sentence with `distinct` after its count
  name the real failure.** `<subject> must cite at least 3 distinct SRC.`
  counts the different `SRC` declarations the subject cites, so citing one
  source three times, or at its sections and chapters, counts once. A failure
  is `citation-cardinality`:
  `COUNTRY-001-rs.truck-mass cites 1 distinct SRC; RULE-001-country-truck-mass requires at least 3; add or remove those citations until the count fits; counted at …`.
  `… at least 3 SRC.` still counts citation sites, with the same verdict and
  bytes. In any sentence with `distinct` after the count, a refusal now names
  what the same sentence without `distinct` is refused for, rather than
  `unknown kind "distinct X"` ([§FS-rule-refusals.sentences](functional-spec/FS-rule-refusals.md#sentences-strict-refusals)): a configured
  `RULE-001-country-truck-mass: The truck-mass chapter of each COUNTRY must cite at least 3 distinct SRC or DOCX.`
  is reported as
  `RULE-001-country-truck-mass is not a valid rule: unknown kind "DOCX"`,
  no longer as
  `RULE-001-country-truck-mass is not a valid rule: unknown kind "distinct SRC"`,
  and `check --rule` prints `error: unknown kind "DOCX"` where it printed
  `error: unknown kind "distinct SRC"`, each followed by its `known kinds:`
  line; a non-citable kind or an unknown alias moves the same way. With kinds
  `FS`, `GOAL` and `REQ`, these refusals move on both surfaces, each from what
  it printed before to what it prints now:
  `Each FS must cite at least 3 distinct GOAL.` from `unknown kind "distinct GOAL"` to accepted;
  `Each FS must cite at least 3 distinct mem/GOAL.` from `` citation target `distinct mem/GOAL`: invalid namespace qualifier segment `distinct mem` in `distinct mem` before kind `GOAL` (expected [a-z][a-z0-9-]*, one segment per workspace level) `` to what `mem/GOAL` gets in the same scope;
  `Each FS must cite at least one distinct GOAL.` from `unknown kind "distinct GOAL"` to `"distinct" is redundant after "at least one"; accepted form: Each FS must cite at least one GOAL.`;
  `Each FS must cite each distinct GOAL at least once.` from `unknown kind "distinct GOAL"` to `"distinct" has no meaning per target; accepted form: Each FS must cite each GOAL at least once.`;
  `Each FS must not cite any distinct GOAL.` from `unknown kind "distinct GOAL"` to `"distinct" has no meaning in a prohibition; accepted form: Each FS must not cite any GOAL.`;
  `Each FS must cite at least 3 distinct GOAL or distinct REQ.` from `unknown kind "distinct GOAL"` to `"distinct" must follow the count; accepted form: Each FS must cite at least 3 distinct GOAL or REQ.`;
  `Each FS must cite at least 3 GOAL or distinct REQ.` from `unknown kind "distinct REQ"` to `"distinct" must follow the count`, with no form and no `known kinds:`;

- [§DF-show-format-orthogonal](decisions/functional/DF-show-format-orthogonal.md#df-show-format-orthogonal-shows---format-answers-every-query-form-and-a-text-or-md-batch-heads-each-answer--coordinate-), [§FS-show.3.3](functional-spec/FS-show.md#33-batch-query): **`grund show --batch` (stdin, `--all` or `--glob`) now prints in every `--format`.** `text`, the default, and `md` head each answer with a `==> <coordinate> <==` line and keep a failed query's message and hint in its place on stdout, where the command used to refuse with `--batch requires --format=json` and exit `2`; `--format json` prints the same envelopes as before. **Who this affects:** a script that ran `grund show --batch` without `--format json` and relied on its refusal now gets text; add `--format json` to keep the envelopes. An unknown format under `--batch` is now ``unsupported show format `<f>` ``, the second-coordinate hint keeps the read's own `--format`, and a missing section in a member whose separator differs is hinted with that member's separator. Part of [issue #1385](https://github.com/agent-grounds/grund/issues/1385).
- [<§>FS-init.2.3.8.4](functional-spec/FS-init.md#238-substituted-content): **The managed block says the trigger converts once an ID follows it.** The `grund init` block now reads, for the default trigger and a project whose kind is `FS`, "Type `$$` followed by an ID, e.g. `$$FS-user-login`, in a grund-aware editor; the trigger becomes `§` as soon as the ID has its kind's shape." The example follows the project's own trigger, kind and ID format. A version-1 config with `[reference] strict = false` gets the sentence without the example. The block moves from v43/v44 and v45/v46 to **v47/v48** and **v49/v50**, so `grund check` reports a block an earlier release wrote as outdated. **What an upgrader does:** run `grund init` once to re-render the block; unmanaged content is kept. (agent-grounds/grund#1370)
