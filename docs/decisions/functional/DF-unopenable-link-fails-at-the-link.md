# DF-unopenable-link-fails-at-the-link: a directory link whose target cannot be opened fails at the link or is pruned, and exits move with it in both directions

**Date:** 2026-11-07

## status: Accepted

## 1. Context

A directory link whose target exists but cannot be opened made the walker raise an error with no path, and the failure fell back to the walk root. Each walk root that met the link therefore named a different place, none of them the one that failed: `error: docs: permission denied`, and on `grund 0.21.0` an empty location for the config root. The line told its reader to make a readable directory readable. Because the location was a walk root, nothing asked whether the walk was going to read through the link at all, and a path-scoped run judged the failure as being somewhere else. Reported as [issue #1266](https://github.com/agent-grounds/grund/issues/1266).

The refusal `fmt` gave over such a link was an accident of that location, and on some runs it was all that stood between the run and a wrong write. With no link at all, `grund 0.21.0` ran `fmt --write docs`, exited `0`, and wrote `<§>m/FS-001-login` for `<§>m/FS-001`, while a second holder of that number sat in a directory of the member `m` it could not read. Nothing in the proof of [§FS-fmt.7.4](../../functional-spec/FS-fmt.md#74-no-write-without-a-complete-model) asked about the project the citation resolved against.

## 2. Decision

The failure is located at the link, once ([§FS-scan.scope.links.unresolvable.unopenable](../../functional-spec/FS-scan.md#scopelinksunresolvableunopenable-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-once)). Whether it is reported turns on one question: is the failure a hole in anything the run reads ([§FS-scan.scope.links.owed.fence](../../functional-spec/FS-scan.md#scopelinksowedfence-the-project-root-fence-is-judged-on-the-target-opened-or-not))?

| Family | What it is | Behaviour |
|---|---|---|
| **Outward** | the canonical target is outside the project and in no tree the run reads | silent |
| **Kept out** | the link is ignored, excluded or hidden | silent; a target read another way keeps its own line |
| **Read another way** | the target is in another project the run loads, inside the root, or in an import's tree ([§FS-imports.mount](../../functional-spec/FS-imports.md#mount-an-import-is-a-mounted-root-read-live-and-read-only)) | reported at the link |
| **No declared blind spot** | the link stands at a home the config lists without walking, or fits no row above | reported at the link |

A run scoped to a link nothing else reports fails at that link. Separately, a rewrite resolved against another project needs that project's proof ([§FS-fmt.7.4.4](../../functional-spec/FS-fmt.md#744-a-rewrite-into-another-project-needs-that-projects-proof)): where its scan met an error, `fmt` rewrites nothing and says so.

### 2.2 What moves in bytes only

Every row here exits as it did, so none owes a route.

- A whole-project run over an inward link exits `2` before and after. Its lines become `docs/ext` and `real`, where they were the config root, `docs` and `real`. The same holds for a run where only the link reaches its target, which now names `docs/ext` alone.
- A link into a loaded member, `docs/ext -> ../m/secret`, exits `2` before and after on `grund check`, `grund check docs`, `grund list`, `grund FS-b` and `grund fmt --write`. Its lines become `docs/ext` and, on the runs that report it, `m/secret`. A link between members, `a/spec/ext -> ../../b/secret`, and a member's link into the root's tree, `m/spec/ext -> ../../shared`, do the same on `grund check`, and the first on `grund fmt --write`.
- A link into an import's tree, `docs/ext -> ../../lib/secret`, exits `2` before and after on `grund check`, `grund check docs`, `grund list` and `grund fmt --write`, and now names `docs/ext`, with `../lib/secret` where the run reports it.
- A link standing at a `scan = false` home, `docs/ext -> ../.real` with `folders = ["docs/ext"]`, exits `2` before and after on `grund check`, `grund check --full` and `grund fmt --write`, and now names `docs/ext`.
- A value home that is such a link, `values -> .store/real` with `.store/real` barred, exits `2` before and after on `grund check`, `grund check --full` and `grund list`. Its lines were the config root and `values: read value home: permission denied`, and are now the walk's one, `values: unreadable symlink: permission denied`, by [§FS-check.2.4.2](../../functional-spec/FS-check.md#242-one-failure-one-line). A cases root that is such a link is one line the same way.
- A kept-out link whose target another walk reads exits `2` before and after on `grund check`, and now names only the target: `m/secret`, or `real` under the path glob.
- `grund fmt --write docs` over a link no ignore file covers into that member already refused, and now names `docs/ext`.
- `grund check notes.md`, which reports neither the link nor its target, exits as it did. Over an outward link its cautions go and `success` returns. Over an inward one the cautions at the walk roots become a single one at `docs/ext`.
- `grund check docs/ext` over an inward link whose target the walk does read exits `2` on both builds, and now names the link as well as `real`.

### 2.3 What does not move

- `grund check docs/ext` over an outward link is the root gate's answer, [§FS-scan.scope.links](../../functional-spec/FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed): `warning: nothing to scan …`, exit `0`. Only the caution that named `docs` goes.
- The same unreadable directory standing at `docs/ext` with no link is reported at `docs/ext` and exits `2` on both builds, for `grund check`, `grund check docs` and `grund check docs/ext`.
- A whole-project run over a loaded member's unreadable directory exits `2` on both builds, for that directory, and `grund check docs` over it exits `0` with its caution.
- `fmt` with no rewrite to make against the failed project exits `0` and writes what it wrote: a link already right, a citation in inline code, a shorthand no visible declaration holds, a full ID with cross-references off, and the project's own citations. A whole run with cross-references off still wraps nothing and still rewrites its own citations under [§FS-fmt.3.1](../../functional-spec/FS-fmt.md#31-an-unreadable-path-is-named-and-a-partial-run-still-rewrites) at exit `2`.
- A narrowed rewrite into a member whose own link is outward or kept out, as in the two rows above, writes at exit `0` on both builds, and `grund fmt --check docs` over it exits `1`. Its scan meets no error here, and the old build did not ask.
- A conflict block in the aliased project does not refuse a narrowed rewrite into it, on either build ([§FS-fmt.7.4.4](../../functional-spec/FS-fmt.md#744-a-rewrite-into-another-project-needs-that-projects-proof)). A whole run still refuses on it.

## 3. The correction route

These exits flip a shipped verdict, which [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered) allows only by a named route. [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids) is the route, and all five conditions hold. Each family's condition 1 is its own, quoted from the release it applied in.

1. *Prior prohibition.* Four, one per family, set out in [§DF-unopenable-link-fails-at-the-link.3.1](DF-unopenable-link-fails-at-the-link.md#31-outward-from-2-the-bytes-turned-on-an-input-that-is-none-of-the-three), [§DF-unopenable-link-fails-at-the-link.3.2](DF-unopenable-link-fails-at-the-link.md#32-kept-out-from-2-the-region-is-outside-every-walk), [§DF-unopenable-link-fails-at-the-link.3.3](DF-unopenable-link-fails-at-the-link.md#33-scoped-to-a-link-from-0-an-unreadable-path-passed) and [§DF-unopenable-link-fails-at-the-link.3.4](DF-unopenable-link-fails-at-the-link.md#34-wrong-writes-a-rewrite-resolved-against-a-set-with-a-hole-in-it). No row is grounded on any other's. The old verdict over an outward link violated [§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation), the old verdict over a kept-out link violated [§REQ-no-missed-citation.2](../../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded), the old exit `0` over a scoped link violated [§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips), and the old write violated [§REQ-no-wrong-citation.3](../../requirements/REQ-no-wrong-citation.md#3-no-wrong-write). Each prohibition already applied when the verdict it forbids shipped, from the release each section names, so no row claims an older one.
2. *Accepted proof.* This record, which cites those sections and proves each conflict. [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path)'s deprecation path does not fit, because there is no old form to carry beside a new one: nothing a user writes selects the wrong location or the wrong write. [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations)'s mechanical migration does not fit either, because nothing a user wrote is at fault, so there is no command to run on anyone's behalf.
3. *Named release.* The release note below names each of these exits, who notices and what to do.
4. *Actionable findings.* Where `0` becomes `2`, what replaces the old verdict is located and names the action: `error: docs/ext: unreadable symlink: permission denied; make the path readable, or keep it out of the scan`, as the line for an unlinked directory at that path already is, and `error: nothing was rewritten: m/docs/secret: permission denied; make the path readable, or keep it out of the scan`, which names the directory the proof is missing. Where `2` becomes `0` nothing replaces it, because the failure goes. Where `2` becomes `1` what is left is a finding the run had already found and still printed.
5. *No new licence.* This route cannot justify ordinary policy tightening, feature removal, or a prohibition invented by this change, and it is used for none of them. The `fmt` refusal is the existing one, brought to a write [§REQ-no-wrong-citation.3](../../requirements/REQ-no-wrong-citation.md#3-no-wrong-write) already forbade. Neither a check nor a diagnostic code is added, and none of the four prohibitions is written here. The rows with no honest prior prohibition, a link into a project or an import the run reads and a link at an unwalked home, keep their exit and are in [§DF-unopenable-link-fails-at-the-link.2.2](DF-unopenable-link-fails-at-the-link.md#22-what-moves-in-bytes-only).

### 3.1 Outward, from `2`: the bytes turned on an input that is none of the three

[§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation) forbids it. At `v0.14.0`, the first release with the fence, it reads: "Three inputs decide the bytes, and all three must be held fixed before two runs are compared", the tree, the config and the invocation, and "Each is a legitimate input; none may be a *hidden* one, and a difference that cannot be traced to one of the three is a bug." The mode of a directory outside the project and in no tree the run reads is none of the three. The run reads nothing behind it and answers the same whatever the mode says, yet the mode decided its bytes. Measured on one tree, config and invocation, `grund check`, with only the mode of `outside` differing:

| Build | Mode `755` | Mode `000` |
|---|---|---|
| `v0.13.0` | exit `1`, `docs/ext/o.md:3: … unknown reference FS-nope` | exit `2` |
| `v0.14.0` | exit `0` | exit `2`, `error: docs: permission denied` |
| `grund 0.21.0` | exit `0` | exit `2` |
| This change | exit `0` | exit `0`, byte-identical |

The wrong verdict dates from `v0.14.0` and not before. Through `v0.13.1` the walk read through an outward link, so its mode did change what the run read, and the `v0.13.0` row is no defect. The fence ended that, and the verdict stayed behind it. [§FS-scan.scope.links.owed](../../functional-spec/FS-scan.md#scopelinksowed-which-unresolvable-links-are-owed-a-report) is not this ground: as shipped it names ignore files and broken and looping links, and it says nothing of a link whose target cannot be opened. A link into an import's tree is not in this family: from `v0.21.0`, the first release with imports, the section's tree "also includes each tree an import names".

A narrower remedy was available, reporting an outward link at the link and keeping its `2`, which moves no exit here. This record decides against it. The ground above says the `2` is the defect, and the issue's own second remedy agrees. It would leave the kept-out rows moving anyway, so it would not spare the route. And its line would ask a reader to make readable, or keep out of the scan, a directory the scan already keeps out. What it costs is real and named in the release note: a run that used exit `2` to learn that a directory the project never reads had become unreadable no longer learns it.

### 3.2 Kept out, from `2`: the region is outside every walk

[§REQ-no-missed-citation.2](../../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded) declares this region, in the same words at `v0.10.1` and `v0.14.0`: "Hidden paths, `[scan] exclude` names, ignore-file matches, non-scanned extensions, and E2E fixture trees are outside every walk, `--full` included". At `grund 0.21.0` it reads that they "are pruned wherever a walk descends into them, `--full` included". A failure of a walk into that region contradicts the declaration, and the run answered the same with the target readable. `[schema.sources] exclude` is the version-2 form of `[scan] exclude` ([§FS-config-v2.schema.sources.exclude](../../functional-spec/FS-config-v2.md#schemasourcesexclude-exclude-is-a-gitignore-style-glob-list)). Where only the link is kept out and the target is read another way, the target keeps its own line, so no failure the run earned goes missing.

### 3.3 Scoped to a link, from `0`: an unreadable path passed

[§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips), in every release since `v0.10.1`, the first whose walk follows directory links: a file the scan cannot read "is reported at its path and the run exits `2`", and an incomplete report "never passes as if it were". `grund check docs/ext` could not open the directory it was asked about and passed. The directory was owed: with the target readable, the same run reads through the link and reports `docs/ext/x.md:3: error: unknown reference FS-nope`, on `grund 0.21.0` too. The old run was not silent, and each of its warnings was true of something. But the caution called the failure outside the report scope because it was located at a walk root, and the failure was exactly the path the run was given.

### 3.4 Wrong writes: a rewrite resolved against a set with a hole in it

[§REQ-no-wrong-citation.3](../../requirements/REQ-no-wrong-citation.md#3-no-wrong-write) forbids it. `v0.13.0` is the first release that carries that section, which `v0.12.3` does not, and this record says nothing of a release before it. It reads: "A persisted rewrite **is** a resolution", which binds the writer to [§REQ-no-wrong-citation.1](../../requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution) "exactly as it binds the reader", and "`fmt` may not write a rewrite that changes what an ID token says unless the declaration set it resolved against is proven complete. Where the proof is missing — a path in the walked tree that could not be read — nothing is rewritten and the run says so". `v0.13.0` already wrote at exit `0` over the barred directory, measured on the rows above with cross-references on and off, and wrote at exit `2` on the whole run with cross-references off. `v0.14.0` and `grund 0.21.0` did the same. The import rows date from `v0.21.0`, the first release with imports, and the section stood there.

An expanded shorthand changes what an ID token says, so the section's second sentence covers it in terms. A link wrapped or re-pointed does not change the token, so that sentence does not name it, and its ground is the first: a persisted rewrite is a resolution. The row with a second `FS-001-login` behind the bar shows that this is more than a reading: the barred run writes a link where the readable run writes none.

The section names no kind of failure, so a broken or looping link, an unreadable file and a file that is not UTF-8 in the member move as the barred directory does: each is a path the walk could not read, and a whole run already refused on each of them on `grund 0.21.0`. A conflict block is none of these, because the file was read.

A row whose write turned out to be right moves too, because the section asks for the proof and not for a good outcome. That is the one place this refuses a run that was doing no harm, and the reader's action ends it.
