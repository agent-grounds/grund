# DF-global-excludes-anchor-at-the-repository-top: a global excludes pattern anchors at the repository top, wherever grund runs from

**Date:** 2026-10-17

## status: Accepted

## 1. Context

[§FS-scan.scope.ignore-files](../../functional-spec/FS-scan.md#scopeignore-files-respect_gitignore--the-ignore-files) has always had the scan honor git's global `core.excludesFile` beside the repository's own ignore files, and a git excludes file has one meaning: git reads each of its patterns relative to the top of the repository the path belongs to. grund handed the `ignore` crate the process working directory as the root of that matcher, at three places: the walk, the one-level probe walker that answers for an entry on disk, and the predicate that names the rule refusing a stub target. The crate strips that root from a path before it matches. Where the working directory did not prefix the path in the same spelling, an anchored pattern, one with a `/` before its end such as `notes/gen/`, had nothing to anchor to and matched nothing. That held from any subdirectory of the repository, from a directory outside it, and under a config root above the repository top. On Windows it held from everywhere, because the walk reads canonical `\\?\D:\...` paths and the working directory is spelled `D:\...`. An unanchored pattern such as `gen/` matches at any depth, which is what hid it.

So one tree was read differently depending on where `grund` was started. git ignored `notes/gen/a.md` from `docs/`, while `grund check` from `docs/` read it, counted its declarations, and passed a stub to it that the same command refused from the top. It surfaced on Windows CI, where the test of the global-ignore stub refusal printed `success` on four heads of one pull request. The test was changed to the unanchored `gen/` and the product was left as it was ([issue #785](https://github.com/agent-grounds/grund/issues/785)).

## 2. Decision

### 2.1 The global file anchors where git anchors it

[§FS-scan.scope.ignore-files.global](../../functional-spec/FS-scan.md#scopeignore-filesglobal-a-global-excludes-pattern-anchors-at-the-top-of-its-paths-repository) states it. A global pattern anchors at the top of the repository the path belongs to, at the innermost one where repositories nest, and at nothing else, whatever directory the run starts from and however the platform spells its paths. Precedence is git's and does not change, and a path in no repository is matched by none of the global patterns, as before.

### 2.2 One root, read by every place that consults the file

The walk, the probe walker and the stub predicate read one derived root. Fixing only the predicate the report named would have left the walk reading, from the same directory, a file the predicate refuses as a stub target. Fixing only the walk would have left the stub passing, because the predicate keeps a rule only where the probe walker agrees. [§FS-declarations.stubs.target.3](../../functional-spec/FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing) already says a stub target keeps the walk's semantics, so the three move together.

## 3. Alternatives considered

**Make the working directory and the walked paths share a spelling.** Stripping the `\\?\` prefix from the walked paths, or canonicalizing the working directory the same way, makes the root prefix the path when Windows runs from the repository top, and changes nothing else. From a subdirectory, from outside the repository, and under a config root above its top, the working directory still does not prefix the path, so the anchored pattern still matches nothing. Rejected: it removes one platform's symptom and keeps the wrong root.

**Root the matcher at the config root or the scan root.** This is correct only where that root is the repository top. A `grund.toml` may be found above the repository it scans ([§FS-config.1](../../functional-spec/FS-config.md#1-file-location-and-discovery)), and a scan may walk into a nested repository, so this moves the defect rather than removing it. Rejected.

**Specify the global file as read from the working directory.** That would write the defect into the specification and leave grund disagreeing with git about a file git owns, which [§FS-scan.scope.ignore-files](../../functional-spec/FS-scan.md#scopeignore-files-respect_gitignore--the-ignore-files) never promised. Rejected.

## 4. What this costs, and why it may be taken

Correcting the anchor moves which files a run reads, and only where an anchored global pattern ignores a file and the run starts somewhere the old root did not prefix the path: a subdirectory of the repository, a directory outside it, a config root above its top, and on Windows anywhere. From the repository top on Linux and macOS nothing moves, because there the old root already was the repository top. Where it moves, a file git ignores is no longer read, so verdicts move both ways. A tree moves from failing to passing where a finding sat inside such a file, such as a dangling citation or a duplicate declaration. Three verdicts move from passing to failing:

- `grund check` exits `1` for a citation that resolved only to a declaration in such a file, which now dangles.
- A declaration that only such a file cited may go uncited, and its file ungrounded, an error under `[reference] require_grounding` ([§FS-check.3.6.3](../../functional-spec/FS-check.md#363-findings)).
- A citation rule that only a citation in such a file satisfied may fail.

The stub half moves no verdict a release has shipped. The refusal of an ignored stub target is new in the unreleased 0.19.0 ([§DF-stub-target-exclusions](DF-stub-target-exclusions.md#df-stub-target-exclusions-excluded-and-ignored-stub-targets-are-broken-from-grund-0190)), and 0.18.0 only warned. From 0.19.0 that refusal reaches the targets an anchored global pattern ignores from wherever the run starts.

The route is [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids), and this record is the accepted proof it requires. Its five conditions:

1. **Prior prohibition.** The old verdict violated [§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation), under which the bytes do not depend on the working directory with the default `--path-base=project`, and a difference that cannot be traced to the tree, the config or the invocation is a bug. Here the working directory decided which files were read, and on Windows the platform decided it, and neither is one of the three inputs. That prohibition already applied when every release that read the global file this way shipped, and it names git's global `core.excludesFile` as part of the tree's ignore state.
2. **Accepted proof.** This record, at [§DF-global-excludes-anchor-at-the-repository-top.4](DF-global-excludes-anchor-at-the-repository-top.md#4-what-this-costs-and-why-it-may-be-taken).
3. **Named release.** The release notes name the verdict change, where it moves, and the three ways a passing tree can fail.
4. **Actionable findings.** Each finding that replaces the old verdict is located and clearable. The dangling citation names its file and line. The uncited declaration and the ungrounded file are named where they are, and the failing rule names the file it holds. The action for each is to move the declaration out of what the global excludes file ignores, or to re-include it with a `!` line in the repository's own ignore files, which take precedence over the global one. A refused stub names the global file and its pattern, with the same remedy.
5. **No new licence.** This route cannot justify anything broader: nothing is tightened, no ignore rule is added, and no prohibition is invented by the correcting change. [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path) does not fit, because there is no old form to keep working beside the new one: the patterns and the config stay as written, and only the root they are matched against is corrected. Keeping the old reading for a release would keep the working directory a hidden input for that release, which is what the prohibition forbids. [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations) does not fit either, because there is no command to ship: the file that moves the verdict is the user's global excludes file, outside every repository, and whether to move a file out of it or re-include it is the repository's choice.

- [§FS-scan.scope.ignore-files.global](../../functional-spec/FS-scan.md#scopeignore-filesglobal-a-global-excludes-pattern-anchors-at-the-top-of-its-paths-repository), [§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation), [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids), [§DF-global-excludes-anchor-at-the-repository-top](DF-global-excludes-anchor-at-the-repository-top.md#df-global-excludes-anchor-at-the-repository-top-a-global-excludes-pattern-anchors-at-the-repository-top-wherever-grund-runs-from): **a pattern in git's global `core.excludesFile` now anchors at the top of the repository, as git anchors it, wherever grund runs from and on every platform.** grund rooted that matcher at the working directory, so an anchored pattern such as `notes/gen/` ignored nothing when `grund` ran from a subdirectory of the repository, from outside it, or under a `grund.toml` above the repository top, and on Windows it ignored nothing from anywhere; an unanchored pattern such as `gen/` was unaffected. **Who this affects:** a project with files such a pattern ignores, run from one of those places. Those files are no longer read, so the verdict moves there: a citation that resolved only to a declaration in one now dangles and `check` exits 1, a declaration only one of them cited may go uncited, a citation rule only one of them satisfied may fail, and a finding inside one is no longer reported. From the repository top on Linux and macOS nothing changes. A stub to such a target is refused from every directory, the `broken-stub` refusal of 0.19.0. Every finding that replaces the old verdict names its location and the action to take: move the file out of what the global excludes file ignores, or re-include it with a `!` line in the repository's `.gitignore`. Closes [issue #785](https://github.com/agent-grounds/grund/issues/785).
