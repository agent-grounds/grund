# REL-name-resolution: name resolution and robust locations, references that survive edits

Name resolution links each reference in a program to the declaration it names, and robust
locations keep a reference into a document working after the document is edited. Both
bear on the address grund keeps, one that survives a moved file and a reworded heading
([§GRUND-schema.2](../grund.md#2-keeping-it)).

## work: What the work is

Pierre Neron, Andrew Tolmach, Eelco Visser and Guido Wachsmuth, *A Theory of Name
Resolution*, ESOP 2015, LNCS 9032, pages 205–231, DOI 10.1007/978-3-662-46669-8_9
([Springer](https://link.springer.com/chapter/10.1007/978-3-662-46669-8_9)), introduce scope graphs and split
resolution in two: "First a language-independent scope graph is constructed using
language-specific rules from an abstract syntax tree. Then references in the scope graph
are resolved to corresponding declarations using a language-independent resolution
process." Each reference and declaration "is distinguished not just by its name, but also
by its position in the program's AST". The resolution calculus finds every resolution
path: "Ambiguous references correspond naturally to multiple resolution paths starting from
the same reference node; unresolved references correspond to the absence of resolution
paths." Ambiguity is admitted on purpose: even where several resolutions make a program
erroneous, the calculus identifies them all, "since IDEs and other front-end tools need to
be able to represent erroneous programs". The authors give "a resolution algorithm that is
sound and complete with respect to the calculus", build "language-independent definitions
of α-equivalence and rename refactoring" on it, and illustrate the approach "using a small
example language with modules" and a model of "name binding patterns in existing
languages".

Leon Moonen, *Generating Robust Parsers Using Island Grammars*, WCRE 2001, pages 13–22,
DOI 10.1109/WCRE.2001.957806 ([doi.org](https://doi.org/10.1109/WCRE.2001.957806)),
described here from its abstract, addresses extractors that must tolerate "syntactic
errors, incomplete source code, language dialects and embedded languages". An island
grammar "combines the detailed specification possibilities of grammars with the liberal
behavior of lexical approaches": the constructs an extractor needs, the islands, are parsed
in detail, and the text around them is treated liberally. The article describes MANGROVE,
"a generator for source model extractors based on island grammars", and "its application
to a number of case studies".

Thomas A. Phelps and Robert Wilensky, *Robust Intra-Document Locations*, Computer
Networks 33, 2000, the WWW9 proceedings, DOI 10.1016/S1389-1286(00)00043-8
([WWW9 copy](https://web.archive.org/web/2001id_/http://www9.org/w9cdrom/312/312.html)),
start from "external hyperlinks, annotations, and transclusions", which "rely on
references to locations within another resource", and aim "that locations continue to
function even as documents change chaotically". Links between whole documents are outside
their scope. A user makes the annotation or link, and the location descriptors "will have
to be automatically generated by clients, rather than hand-crafted by humans". A robust
location holds several descriptors. A Unique Identifier is "a name unique within the
document, as per ID attributes in SGML/XML"; it survives "the most violent document
changes, except its own deletion", but is "available only through the foresight of the
document author". A Tree Walk is "the path from the root of the document, through
internal structural nodes, to a point within media content at a leaf", and Context is "a
small amount of previous and following information". Reattachment "first uses the unique
identifier, then the tree walk descriptor, and then the context descriptor"; where none
resolves directly, it uses heuristics "to hypothesize the intended location, along with a
measure of the degree of confidence". "In practice, tree walks are the central component
of robust locations." The evidence is informal testing, which the authors call "no
substitute for actual measurement": with an earlier, less sophisticated implementation in
the TkMan manual-page browser, "of 754 annotations that needed repositioning", "742
annotations were automatically repositioned"; they also mutated documents of their own,
and annotations they posted on the DARPA home page reattached through more than a year of
changes to it. The companion, Phelps and Wilensky's *Robust Hyperlinks and Locations*,
D-Lib Magazine 6(7/8), 2000, DOI 10.1045/july2000-wilensky
([doi.org](https://doi.org/10.1045/july2000-wilensky)), names the approach "permissive, but
robust" against "strict, but fragile", reached "by providing multiple, independent
descriptions", with "no guarantee that references will remain coherent".

Unison's *The big idea*, project documentation, unversioned, checked 2026-10-13, and not
peer-reviewed ([unison-lang.org](https://www.unison-lang.org/docs/the-big-idea/)), takes
the opposite course and addresses a definition by its content: "Each Unison definition is
identified by a hash of its syntax tree." Names "are just separately stored metadata that
don't affect the function's hash", which gives "instant non-breaking renames", and "A
Unison codebase is never in a broken state, even midway through a refactoring."

## agrees: Where grund agrees

- Phelps and Wilensky's unique identifier is grund's whole address. A grund ID is a name
  declared once in the project, written on the line that declares it, and a section is
  addressed by the number or name written on its own heading; neither the file path nor
  the title text is part of the address, so it survives a moved file and a reworded
  heading ([§GRUND-schema.2](../grund.md#2-keeping-it), [§FS-declarations.checks.duplicate](../functional-spec/FS-declarations.md#checksduplicate-duplicate-declaration)). It costs the foresight they
  name: an author writes the ID.
- As grund reads scope graphs, they split the work the way grund does: a language-specific
  step, then one language-independent resolver. What grund knows of each host language is
  its comment forms ([§AR-scanner.4.3](../architecture/AR-scanner.md#43-the-recognized-doc-comment-forms)), and the marker, the section grammar and the resolver
  are the same in every host ([§GOAL-polyglot-citation.1](../goals.md#1-what-cleanly-means)).
- Like the scope-graph calculus, grund finds every candidate. A number-only shorthand that
  matches several declarations is reported with the sorted, complete list of them
  ([§FS-check.3.13.3](../functional-spec/FS-check.md#3133-one-finding-per-site-in-three-forms)).
- grund's scanner works the way an island grammar's name suggests: it recognises
  declarations and `§` citations in Markdown and in source files, and passes over the text
  around them without parsing it ([§AR-scanner.2.3](../architecture/AR-scanner.md#23-citation-detection), [§AR-scanner.4.2.2](../architecture/AR-scanner.md#422-recognition-not-parsing)).

## departs: Where grund departs

- Scope graphs build resolution from a program's syntax, telling occurrences apart by their
  position in the syntax tree, and island grammars generate parsers. grund parses no code
  and knows no scopes: it reads comments with one line-oriented pass, and an ID resolves
  against the project's declarations wherever the citation stands ([§FS-non-goals.3](../functional-spec/FS-non-goals.md#3-code-ast-parsing),
  [§AR-scanner.5](../architecture/AR-scanner.md#5-why-regex-not-a-parser)).
- Scope graphs define rename refactoring through α-equivalence, and Unison makes a rename
  non-breaking by keeping names beside a content hash. grund offers no rename: an ID is
  permanent, and changing one is a deliberate edit, not an automated operation
  ([§FS-non-goals.4](../functional-spec/FS-non-goals.md#4-cross-workspace-id-renaming)). Nor is its address its content. The text under a stable ID may change,
  and grund fingerprints text only in the section lock, to tell an edit in place from text
  that left for another address ([§FS-section-lock](../functional-spec/FS-section-lock.md#fs-section-lock-a-cited-relative-section-keeps-its-text-or-check-says-where-the-text-went)).
- The scope-graph calculus admits ambiguous resolutions by design. In grund ambiguity is an
  error and nothing resolves through it: two declarations of one ID, two headings claiming
  one section path, and a shorthand matching several declarations are each reported, never
  ranked ([§REQ-no-wrong-citation.1](../requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution), [§DF-duplicate-section-path.2.1](../decisions/functional/DF-duplicate-section-path.md#21-the-collision-is-an-error-in-fs-declarationschecksduplicates-shape)).
- Robust locations fall back from the identifier to a tree walk and to surrounding text,
  and hypothesize a location with a confidence. grund never reattaches: a citation resolves
  to exactly the declaration its ID names, or it is reported ([§REQ-no-wrong-citation](../requirements/REQ-no-wrong-citation.md#req-no-wrong-citation-a-citation-never-resolves-to-a-guess)). The
  one place a grund address leans on structure is a relative heading, which takes its path
  from its parent; when a cited section's text turns up at another address, the section
  lock reports it rather than following it ([§FS-declarations.section.relative](../functional-spec/FS-declarations.md#sectionrelative-a-heading-may-write-only-the-component-it-adds),
  [§FS-section-lock](../functional-spec/FS-section-lock.md#fs-section-lock-a-cited-relative-section-keeps-its-text-or-check-says-where-the-text-went)). In the companion's terms, grund takes the strict side.
