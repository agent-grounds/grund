# DF-config-migrate-opted-out-block: a version-1 block with include_root = false migrates to its envelope and workspace table, held by the report gate

## status: Accepted

## 1. Context

Issue #1142 shows a version-1 block that only lists members: `[workspace] include_root = false` and `members = ["a"]`, under a version-2 root, with no `requirements.md`, `docs`, `e2e` or `src` of its own. `grund config migrate --to 2 group --write` refuses it twice. The first refusal is that named sections are off ([§FS-config-migrate.3.1.1](../../functional-spec/FS-config-migrate.md#311-named-sections-off)). The second is that the default `include` names four paths that do not exist ([§FS-config-migrate.3.1.3](../../functional-spec/FS-config-migrate.md#313-an-include-entry-that-does-not-exist)). Once both repairs are made, it writes 219 lines of version-1 defaults ([§FS-config-migrate.3.3](../../functional-spec/FS-config-migrate.md#33-defaults-are-written-out)). The block is not a project, and nobody reads its own files ([§FS-check.4.10.1](../../functional-spec/FS-check.md#4101-nobody-reads-the-blocks-own-files)). Both refusals guard a reading that does not happen, and the defaults describe a scan that never runs. The migration contract holds every version-1 file to a project's terms, and nothing in it asks whether the file is a project at all.

## 2. Decision

A block with `include_root = false` whose version-1 default scope is empty on disk, and which authors nothing a project would read, migrates **compactly**. Its candidate is the version line and the keys that have force on any block, and nothing else. Every other authored key, and the defaults left unwritten, are reported as `dropped:` notices in the shape the report already has. Named sections are never refused on such a block. The rule is stated once, at [§FS-config-migrate.8.1](../../functional-spec/FS-config-migrate.md#81-a-block-with-include_root--false). Every other block keeps the conservative path, and so does every project.

Both gates still run. On a compact block the records gate compares only what the candidate keeps: the workspace records, the project name and the description. The rest of the difference between the version-1 file and its candidate is held by the report gate alone. That is the "comparing reports alone" that [§DF-config-migrate.2.2](DF-config-migrate.md#22-two-gates-records-first) rejected, because a report that matches on one tree proves nothing about another ([§FS-config-v2.mapping](../../functional-spec/FS-config-v2.md#mapping-what-the-records-keep-apart)). It is accepted for this scope because the records it gives up have one reader there, the unread-block probe ([§FS-check.4.10.2](../../functional-spec/FS-check.md#4102-what-counts)). That probe reads no declaration and checks no citation. It asks only whether the block's own tree holds one file a scan would read. The report gate runs that probe on this tree, before and after, so any file version 2 would newly find unread changes the report and refuses the write. A `README.md`, or the `AGENTS.md` that `grund init` writes, is exactly such a file. A block holding one reaches the report gate in one run and stays on version 1 until the file moves into a member or the block becomes a project. Whether that warning should pass the gate is a separate question, and this decision leaves the gate as it is.

On a later tree, a file added to the block meets version 2's whole-root default scope rather than version 1's four entries. The only effect is that the unread-block warning may name the block. No declaration is read, and no citation is checked or left unchecked, on either version. Switching the block to `include_root = true` makes it a project, and that is a deliberate configuration of its own. Version 2 has no spelling for the intent of an empty `include` either: a migrated project with `include = []` reads the whole root today ([§FS-config-v2.schema.places.complement](../../functional-spec/FS-config-v2.md#schemaplacescomplement-code-is-the-complement-by-name)). So the compact path gives up nothing a project migration keeps.

## 3. Compatibility and alternatives

The refusals, the candidate and the report of `grund config migrate` are covered promises under [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered). The change is argued there. Nothing is renamed, and no tree's verdict moves. `check`, `config show` and every other command read a version-1 block exactly as before. Nothing about a block changes until someone runs `--write`, and that write still passes the report gate on the current tree. On the blocks this covers, a refusal becomes a success, and a written file shrinks to the envelope and `[workspace]` table. A script that relied on the refusal, or on the defaults written into such a block, sees the new behaviour, and the release note says so. The licence of [§REQ-backwards-compatibility.4](../../requirements/REQ-backwards-compatibility.md#4-what-was-never-a-promise) is for a surface renamed without an alias before 1.0, and it is not used here.

Three alternatives were rejected. One kept both refusals and only reworded them to name the block. That leaves the bare block refused, and it still writes 219 lines once the repairs are made. Another wrote the compact file but kept the `include` refusal. A block holding a `README.md` would then be sent through a repair that ends at the same gate. A third exempted such a block from the report gate as well, which would let a write change the unread-block warning without anyone being told.

## release-note: Release note

- `grund config migrate --to 2` on a version-1 block with `include_root = false`, whose own default scope is empty, now writes only the version line and its `[workspace]` table and reports the dropped defaults as `dropped:` notices. It no longer refuses on `[id] named_sections` or a missing default `[scan] include`, and the report gate still holds the write.
