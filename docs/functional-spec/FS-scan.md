# FS-scan: what a path argument means, which projects a run loads, and which files it reads

What a run is handed and what it reads, defined once for every command that scans a tree: what each command's `<path>` argument means, which projects a run loads and so whose kinds and declarations it reads, which files a walk reads, which path names a file it read, and which text a file has. The `[scan]` keys and their defaults are [§FS-config.3.5](FS-config.md#35-scan--what-gets-scanned)'s, and which project owns a directory is [§FS-workspace.6.2](FS-workspace.md#62-the-boundary-is-mutual)'s; this page cites both rather than restating them. Serves [§GOAL-no-dangling-refs](../goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration), whose verdicts are only as good as the files a run read, and [§GOAL-token-economy](../goals.md#goal-token-economy-give-an-agent-the-right-amount-of-spec-not-the-whole-file), because one point answers what a run reads.

## terms: Terms

Leans on [§FS-terms.terms.4](FS-terms.md#terms4-scanning-and-project-structure) (scan, scope, config root, workspace, member).

- **kind home** — The `folder` or `file` a `[[kinds]]` row names ([§FS-config.3.4](FS-config.md#34-kinds--recognized-kinds)): the place its declarations live.
- **scan root** — Where a walk starts: an `include` entry, a kind home, or an explicit path. Which rules it outruns is [§FS-scan.scope.roots](FS-scan.md#scoperoots-a-scan-root-outruns-every-rule-about-descent).
- **resolution scope**, **report scope** — The two scopes `check` tells apart for an explicit path, defined at [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports).
- **narrowed scan** — One scan of the enclosing project below its config root, with no workspace loaded: what `cover` runs for a path narrower than its config root ([§FS-scan.path.cover](FS-scan.md#pathcover-cover-runs-one-narrowed-scan)).
- **buffer** — The text an editor holds open for a file, saved or not, which a run reads as that file ([§FS-scan.text.buffer](FS-scan.md#textbuffer-a-files-text-is-what-a-save-would-write)).

## requirements: What every scan holds to

One requirement on what a run reads as a whole, carrying a mark of [§FS-config.requirements](FS-config.md#requirements-what-the-config-contract-holds-to). Four more are left out because they are stated elsewhere: *every region a run leaves unread is named and can be looked into* is [§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded); *every command answers a kind name from one reading of the configs* is [§REQ-one-answer.identity.kinds](../requirements/REQ-one-answer.md#identitykinds-every-command-reads-one-kind-verdict); *a run given a path fails what the whole run fails about the files it reports* is [§FS-check.requirements.narrow-never-lenient](FS-check.md#requirementsnarrow-never-lenient-a-narrower-run-never-passes-what-a-wider-run-fails-about-the-files-it-reports--realized), and `list`, `show` and `id` resolve as it does, so no difference between the commands' paths is left at [§REQ-one-answer.differences.scope](../requirements/REQ-one-answer.md#differencesscope-scope); and *the machine's global git excludes are the one input from outside the checkout that decides which files are read* is [§FS-config.requirements.8](FS-config.md#requirements8-a-projects-meaning-is-self-contained--realized).

### requirements.spelling: How a tree is reached changes neither what is read nor what a finding names — realized

A repository reads the same however a run arrives at it. A file reached through a link is named by the path the run met — the in-tree link, the explicit argument, the root as handed — never by its physical target, even where that target lies outside the config root ([§FS-scan.identity.link-path](FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path), [§FS-scan.identity.root-path](FS-scan.md#identityroot-path-the-scan-root-keeps-the-path-the-run-was-handed)); a physical file reached by two spellings is read once, and the reading belongs to the physical file while the reported path belongs to the spelling, so sort order and the name a run was handed decide neither what the file is read as nor which names a finding carries ([§FS-scan.identity.read-once](FS-scan.md#identityread-once-one-physical-file-is-read-once), [§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it), [§FS-scan.identity.findings](FS-scan.md#identityfindings-a-finding-about-a-file-with-two-names-names-each-spelling-once)), and an editor buffer is that file whichever spelling it was opened under ([§FS-scan.identity.buffers](FS-scan.md#identitybuffers-a-buffer-is-the-file-at-its-physical-location)); and which directory links are followed is decided by the project's canonical root, which stays the fence when the repository itself was reached through a link ([§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed)). So a checkout reached through a symlinked directory, as macOS reaches `/private/var` through `/var`, reads the files and reports the findings it does at its physical path, each spelled as its reader wrote it. Serves [§GOAL-friendliness-first.1](../goals.md#1-hard-requirements), whose `path:line` is one a reader can act on, and [§FS-non-goals.13](FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree).

## path: What a path argument means

Every command that takes a `<path>` but `init`, whose `<path>` is the directory it writes in ([§FS-init.1](FS-init.md#1-inputs)), discovers its configuration from it ([§FS-scan.path.discovery](FS-scan.md#pathdiscovery-a-path-is-where-discovery-starts)), and a run given none covers the project discovery finds from the current directory ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)). `check`, `list`, `show` and `id` then resolve against the project the path discovers, read as `check`'s resolution scope is ([§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports)), and the path narrows only what they report ([§DF-one-answer-rulings-run](../decisions/functional/DF-one-answer-rulings-run.md#df-one-answer-rulings-run-a-path-narrows-the-report-a-stub-reads-what-the-walk-reads-and-a-file-is-one-file-however-it-is-spelled-or-held), ruling D1); each one's leaf below says what that is. `cover` and `refs` give the path the meaning their own leaf states. Rows R01 and R02, the two places the commands' paths disagreed, closed with [§DF-path-narrows-the-report-in-0-19](../decisions/functional/DF-path-narrows-the-report-in-0-19.md#df-path-narrows-the-report-in-0-19-in-0190-a-path-narrows-what-show-list-and-id-report-not-what-they-resolve-and-workspace-check--resolves-every-project-it-sees) in grund 0.19.0 ([§REQ-one-answer.differences.scope](../requirements/REQ-one-answer.md#differencesscope-scope)). Resolving against the owning project costs a path narrower than its config root one read of that project, the cost `check` already pays ([§FS-check.1.3.6.3](FS-check.md#1363-a-file-the-wider-walk-could-not-read-is-said-out-loud)) and grund 0.18.0 paid for the warnings this resolution replaced ([§GOAL-fast-feedback](../goals.md#goal-fast-feedback-grund-must-be-as-fast-as-possible)). A run with no path, or with one at or above its config root, reads what it read before.

### path.discovery: A path is where discovery starts

An explicit `<path>` argument (e.g. `grund list apps/api`, `grund refs FS-x apps/api`, `grund complete ids --path apps/api`) behaves as if the command were invoked from that path in what it discovers: a `<path>` inside a member is member-scoped, not workspace-aggregate, even when a workspace exists above it ([§FS-scan.projects.discovery](FS-scan.md#projectsdiscovery-the-nearest-config-decides)). What the run covers is another matter: invoked from that path with no `<path>`, it covers the project discovery finds ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)); given the path, it is narrowed to it. `cover`, whose `<path>` bounds a scan, runs one narrowed scan below the config root instead ([§FS-scan.path.cover](FS-scan.md#pathcover-cover-runs-one-narrowed-scan)).

### path.none: A run with no path covers the project discovery finds

With no `<path>`, the current directory is where discovery starts ([§FS-config.1](FS-config.md#1-file-location-and-discovery)). Where no config is found, the run's scope is that directory, on the canonical defaults. Where one is found, the current directory decides nothing more about what the run covers: its scope is the default scope of the config root discovery finds, however far below that root the run started. Inside a member that is the member ([§FS-scan.projects.member](FS-scan.md#projectsmember-a-member-run-loads-the-member)); at a workspace root, or below one outside every member, it is every project the workspace-root run loads ([§FS-scan.projects.discovery](FS-scan.md#projectsdiscovery-the-nearest-config-decides), [§FS-scan.projects.workspace-root](FS-scan.md#projectsworkspace-root-a-run-at-the-workspace-root-loads-every-project)). Started anywhere below that config root, the run is the one given the root's own directory as its `<path>`, so it is the run that writes section locks ([§FS-section-lock.write.rules](FS-section-lock.md#writerules-add-refresh-drop)) and the one [§FS-fmt.7.1](FS-fmt.md#71-scope-equivalence) calls the default scope.

Only an explicit `<path>` narrows a run's scope, to what the command's own leaf says. From a directory `sub/` below the config root discovery finds, `grund <command>` and `grund <command> .` are therefore two different runs wherever the path bounds what is scanned or reported, the first covering the project and the second `sub/` alone: `check`, `fmt`, `cover`, `list`, `refs` in each of its modes, `show --batch --all`, and `complete ids` ([§FS-completions.2.1](FS-completions.md#21-arguments-and-candidate-modes)). Where the path only chooses the project that answers, as for `show` of one coordinate, `id`, `config` and `schema`, the two runs give one answer, and "`.` by default" stays true of them. A page describing a path that bounds what is scanned or reported cites this point for the run given none, rather than naming a directory the path defaults to.

### path.check: `check` reads more than it reports

A run given an explicit path reads the declarations and the citations its project's ordinary run reads, and reports findings only for the files at or under the path — or, where a finding spans several sites, for a finding naming one of them ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)). Two scopes, and telling them apart is the whole rule. The **resolution scope** is the set of files the run reads so that citations resolve and citation edges count: the enclosing project's ordinary scope — `[scan] include` plus every walked kind home ([§FS-scan.scope.include](FS-scan.md#scopeinclude-include-is-scanned-from-the-config-root), [§FS-scan.scope.homes](FS-scan.md#scopehomes-every-configured-kind-home-is-scanned)) — **union the path itself**, because a path may lie outside `include` and must still be read. The **report scope** is exactly the path. Every rule runs over the resolution scope, and a diagnostic anchored at a file outside the report scope is dropped before the report is written, unless it also names a site inside it ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)). Which projects the run loads is [§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)'s, and where it loads several the resolution scope is each one's. So for `check` a path narrows the report and not what the run resolves against; which verdicts that moves is [§FS-check.1.3.6.1](FS-check.md#1361-a-path-scope-narrows-the-report-not-the-resolution)'s to say. Decided in [§DF-path-scope-resolves-project-wide](../decisions/functional/DF-path-scope-resolves-project-wide.md#df-path-scope-resolves-project-wide-a-path-scoped-check-resolves-against-the-whole-project-and-reports-only-the-path).

### path.cover: `cover` runs one narrowed scan

Of the commands [§FS-workspace.8](FS-workspace.md#8-other-commands) covers, `cover` is the one whose `<path>` bounds a **scan** rather than choosing which config answers ([§FS-cover.1](FS-cover.md#1-inputs)): a scope narrower than the config root is one narrowed scan of the enclosing project, no workspace loaded and no `project` field. `grund check <dir>` drew the line there too until grund 0.19.0 gave it the projects a run from `<dir>` sees ([§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)); `cover` is outside the ruling that moved it ([§DF-one-answer-rulings-run](../decisions/functional/DF-one-answer-rulings-run.md#df-one-answer-rulings-run-a-path-narrows-the-report-a-stub-reads-what-the-walk-reads-and-a-file-is-one-file-however-it-is-spelled-or-held), ruling D1), so it keeps the narrowed scan. Widening `grund cover src/` back to every project would answer a question the caller did not ask, and an explicit path deliberately bypasses `[scan] include`, so the narrowing is the only thing that put those files in scope at all.

### path.warning: Where the path changed an answer, the run said so

Retired in grund 0.19.0: `list`, `show` and `id` resolve against the owning project ([§FS-scan.path.list](FS-scan.md#pathlist-list-reports-the-paths-entries-and-resolves-against-the-project), [§FS-scan.path.show](FS-scan.md#pathshow-show-resolves-the-id-against-the-project-the-path-discovers), [§FS-scan.path.id](FS-scan.md#pathid-id-numbers-from-the-project-the-path-discovers)), so no answer is left for a line to announce, and none is printed. grund 0.18.0 printed one `warning:` line on stderr wherever the answer computed against the owning project differed, as [§DF-path-narrowing-warns](../decisions/functional/DF-path-narrowing-warns.md#df-path-narrowing-warns-a-path-that-narrows-what-show-list-and-id-resolve-or-what-check--resolves-an-alias-against-says-so-for-one-release) records. This address is kept so citations written before the change still resolve.

#### path.warning.shape: A text line after everything else on stderr

Retired in grund 0.19.0 with [§FS-scan.path.warning](FS-scan.md#pathwarning-where-the-path-changed-an-answer-the-run-said-so): no such line is printed. This address is kept so citations written before the change still resolve.

#### path.warning.cost: Only a narrowed path reads more

Retired in grund 0.19.0 with [§FS-scan.path.warning](FS-scan.md#pathwarning-where-the-path-changed-an-answer-the-run-said-so): what a narrowed path reads is said in [§FS-scan.path](FS-scan.md#path-what-a-path-argument-means). This address is kept so citations written before the change still resolve.

#### path.warning.release: One named release, held by a test

Retired in grund 0.19.0 with [§FS-scan.path.warning](FS-scan.md#pathwarning-where-the-path-changed-an-answer-the-run-said-so): the release the line named has shipped, and no constant or test holds it. This address is kept so citations written before the change still resolve.

### path.list: `list` reports the path's entries and resolves against the project

For `list`, `<path>` is the directory or file whose entries are reported; with none, every entry of the project the run covers ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)). Discovery is the same as every other subcommand (walk up to a `grund.toml`, else defaults — [§FS-config.1](FS-config.md#1-file-location-and-discovery)).

The path bounds which entries print: those declared at or under it. Everything said about an entry is the owning project's answer, read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads it: its JSON `refs` count every citation of it in the project, `--unused` drops an entry cited anywhere in the project, by a citation that counts as use and never by a kind's own index entry alone ([§FS-list.1.3](FS-list.md#13---unused)), and an entry with another home outside the path carries the duplicate note ([§FS-list.2.6](FS-list.md#26-duplicate-declarations)). The `--size` rows ([§FS-list.3.4](FS-list.md#34---size--per-coordinate-lead-and-full-body-measurements)) and the `--summary` counts ([§FS-list.3.3](FS-list.md#33---summary)) are of the same entries, with the same answers. So `list sub --unused` and `check sub` agree about which declarations under `sub` are cited, and `list sub` over a `sub/` that declares nothing prints nothing. A run that loads a workspace prints these entries in the shape of the catalog [§FS-workspace.8.3](FS-workspace.md#83-grund-list) states, with qualified IDs, a JSON `project`, and that catalog's `--size` and `--summary` rows, and the path bounds them there as it does in one project: from a directory below the workspace root and outside every member, `list .` prints the entries of the members under it and nothing where it holds none, as `check .` reports only that directory ([§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)).

### path.show: `show` resolves the ID against the project the path discovers

For `show`, `<path>` chooses the project the ID resolves in; with none, the project the run covers ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)). Discovery is the same as every other subcommand (walk up to a `grund.toml`, else defaults — [§FS-config.1](FS-config.md#1-file-location-and-discovery)).

The ID resolves against that project read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads it, so a path narrower than its config root moves no answer: an ID the project declares outside the path prints its body, exit `0`, and one it declares both inside and outside the path is ambiguous ([§FS-show.2.2.1](FS-show.md#221-ambiguous-id)). A short form ([§FS-show.1.2](FS-show.md#12-the-number-only-shorthand)) is matched over the same project, so its candidates are the project's ([§FS-show.2.2.1.1](FS-show.md#2211-an-ambiguous-shorthand-names-its-candidates)), and under `--batch` every query resolves the same way. What `show` reports is the declaration the query names, so the path bounds nothing more, with one exception: `--batch --all` generates its queries from the entries `list <path>` prints ([§FS-scan.path.list](FS-scan.md#pathlist-list-reports-the-paths-entries-and-resolves-against-the-project)), and each of them still resolves against the whole project.

### path.refs: `refs` scans the path's tree

An ID operand resolves against the selected project's declarations, read as
[§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads
them, including declarations retained for read compatibility under
[§FS-config.3.2.6](FS-config.md#326-resolving-an-off-grammar-citation). A declaration
outside the explicit path can therefore authorize that operand, but one in
another project cannot. The path selects the reported sites, not whether the
operand resolves: a compatible ID succeeds with exactly those sites, including
an empty selection. Inline sections and ambiguity use the same project catalog
([§FS-refs.4](FS-refs.md#4-exit-codes)).
The correction to path-dependent compatibility refusal is recorded in
[§DF-refs-compatible-id-project-scope](../decisions/functional/DF-refs-compatible-id-project-scope.md#df-refs-compatible-id-project-scope-a-refs-path-selects-sites-while-the-project-resolves-a-compatible-id).

For `refs`, in each of its modes ([§FS-refs.1.1](FS-refs.md#11-three-modes-one-path)), `<path>` is the directory or file whose tree is scanned, the project's with none ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)), discovered as by every other subcommand ([§FS-config.1](FS-config.md#1-file-location-and-discovery)). A `--from` source resolves against the project the path discovers, as `show`'s ID does ([§FS-scan.path.show](FS-scan.md#pathshow-show-resolves-the-id-against-the-project-the-path-discovers)), and the sites it lists are those of the tree the path scans. A run that loads a workspace lists the sites of the path's tree too, not the workspace's: from a directory below the workspace root and outside every member, `--from` lists only the sites at or under it, as it does in one project ([§FS-refs.from](FS-refs.md#from---from-lists-what-one-point-cites)), and every other mode those and the ones a stub there lends ([§FS-declarations.stubs.target.5](FS-declarations.md#stubstarget5-what-a-target-outside-the-include-gives-and-what-stays-unjudged)), as `list` bounds its entries there ([§FS-scan.path.list](FS-scan.md#pathlist-list-reports-the-paths-entries-and-resolves-against-the-project)).

### path.id: `id` numbers from the project the path discovers

For `id`, `<path>` is the directory whose project is numbered; it defaults to the current directory and is resolved as by every `grund` command ([§FS-cli.3](FS-cli.md#3-cross-subcommand-flags)): config discovery walks up to `grund.toml`, else takes the defaults.

The next free number is one past the highest number of the kind the project declares, read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads it, wherever under it that declaration lies; under a number-less format ([§FS-id.4.1](FS-id.md#41-number-less-id-formats)) a proposal the project already declares is refused ([§FS-id.5](FS-id.md#5-collision-check)) wherever it lies. So a path narrower than its config root proposes what a run at the config root proposes.

## projects: Which projects a run loads

Which projects a run loads decides whose kinds and declarations it reads. Which project owns a directory is [§FS-workspace.6.2](FS-workspace.md#62-the-boundary-is-mutual)'s, and this chapter does not restate it.

### projects.discovery: The nearest config decides

Discovery follows the same walk-up rule as `grund check` ([§FS-config.1](FS-config.md#1-file-location-and-discovery)): from the CWD (or from an explicit `<path>` argument, [§FS-scan.path.discovery](FS-scan.md#pathdiscovery-a-path-is-where-discovery-starts)), walk up to the nearest `grund.toml` in either discovery form. If the nearest config is a member's own config, the command runs member-local — qualified `<alias>/<ID>` cannot resolve, the same way `check` errors at the member scope ([§FS-workspace.5.1](FS-workspace.md#51-a-member-run)). A scope inside a member with no config of its own is member-local all the same, on [§FS-workspace.2](FS-workspace.md#2-workspace-configuration)'s canonical defaults with the member directory as the config root. Which member a scope lies in is judged on the path discovery climbs ([§FS-config.1.5](FS-config.md#15-the-ancestor-search-keeps-the-path-through-directory-links)), so `m/cases/b` is member `m`'s even where `m/cases` links out of the workspace or into another member; only a path in no member as written is judged where it resolves. Only outside every member does a nearest config at the workspace root run the command workspace-wide.

### projects.workspace-root: A run at the workspace root loads every project

`grund check` run at a workspace root checks the root project (unless `include_root = false`, [§FS-workspace.2](FS-workspace.md#2-workspace-configuration)) and all configured members, aggregates findings, and prints the same explicit-channel `<path>:<line>: <channel>: <message>` shape as a normal check ([§FS-check.2.1](FS-check.md#21-report-format)). Paths are rendered relative to the workspace root when `[output] relative_paths = true`.

### projects.member: A member run loads the member

`grund check <member>` (or `grund check` invoked from inside a member tree) discovers the member's own config first and, for a member that declares no `[workspace]` block of its own, validates it as an independent project; one that does runs its own subtree ([§FS-workspace.6.1](FS-workspace.md#61-nested-workspaces)). What a qualified citation earns there is [§FS-workspace.5.1](FS-workspace.md#51-a-member-run)'s.

### projects.narrowed: A path below the config root loads what a run from it would see

`grund check <path>` with a `<path>` narrower than the config root loads the projects a run from `<path>` would load ([§FS-scan.projects.discovery](FS-scan.md#projectsdiscovery-the-nearest-config-decides), [§FS-workspace.8.8](FS-workspace.md#88-discovery-follows-grund-checks-walk-up)), resolves each of them completely, and reports only the path ([§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports)). Inside a member that is the member ([§FS-scan.projects.member](FS-scan.md#projectsmember-a-member-run-loads-the-member)): a member directory still means a member run, which refuses a qualified citation as [§FS-workspace.5.1](FS-workspace.md#51-a-member-run) says. In a project with no workspace it is that project. Below a workspace root and outside every member it is every project the root run loads ([§FS-scan.projects.workspace-root](FS-scan.md#projectsworkspace-root-a-run-at-the-workspace-root-loads-every-project)), so a qualified citation the root run resolves resolves here too. Decided by [§DF-one-answer-rulings-run](../decisions/functional/DF-one-answer-rulings-run.md#df-one-answer-rulings-run-a-path-narrows-the-report-a-stub-reads-what-the-walk-reads-and-a-file-is-one-file-however-it-is-spelled-or-held), ruling D14, and landed by [§DF-path-narrows-the-report-in-0-19](../decisions/functional/DF-path-narrows-the-report-in-0-19.md#df-path-narrows-the-report-in-0-19-in-0190-a-path-narrows-what-show-list-and-id-report-not-what-they-resolve-and-workspace-check--resolves-every-project-it-sees).

What such a run prints below a workspace root is the root run's report narrowed to the path: each finding the root run makes that is anchored at or under the path, or names a site there ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)), kept whole — the same bytes, its path rendered against the workspace root, and an unknown alias with the outermost root's candidates ([§FS-check.3.8.2](FS-check.md#382-candidates-at-the-outermost-root)). Under `--format json` each is the object the root run writes, which carries no `project` field there either ([§FS-check.2.1](FS-check.md#21-report-format)). The run-level findings, the workspace run warnings among them, carry no path and print as the root run prints them ([§FS-check.1.3.6.1](FS-check.md#1361-a-path-scope-narrows-the-report-not-the-resolution)).

#### projects.narrowed.alias: A refused alias the workspace root resolved said so

Retired in grund 0.19.0: a run below a workspace root and outside every member loads the workspace ([§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)), so an alias the root run resolves resolves there too and no refusal is left to annotate. grund 0.18.0 appended the clause [§DF-path-narrowing-warns](../decisions/functional/DF-path-narrowing-warns.md#df-path-narrowing-warns-a-path-that-narrows-what-show-list-and-id-resolve-or-what-check--resolves-an-alias-against-says-so-for-one-release) records. A member run still refuses qualified citations ([§FS-workspace.5.1](FS-workspace.md#51-a-member-run)); its verified enclosing-workspace guidance is defined by [§FS-workspace.5.1.1](FS-workspace.md#511-verified-enclosing-workspace-guidance). This address is kept so citations written before the change still resolve.

### projects.kinds: Whose kinds a run reads

A run reads the kinds of the projects its configuration declares: its own config's `[[kinds]]` and, where that config declares a `[workspace]`, each member's ([§FS-config.3.4](FS-config.md#34-kinds--recognized-kinds), [§FS-workspace.2](FS-workspace.md#2-workspace-configuration)). It reads them from the configs alone, before any file is read, so a narrowed scan ([§FS-scan.path.cover](FS-scan.md#pathcover-cover-runs-one-narrowed-scan)), which loads no member's files, still reads the kinds its declared workspace configures and judges its `[citations]` targets against them ([§FS-config.3.9.5.2](FS-config.md#3952-a-pinned-target-is-judged-against-its-projects-kinds)). A rule object there is judged in the projects the run loads, so a namespaced one stays unverifiable, as [§FS-rules.4.1](FS-rules.md#41-a-rule-this-scope-cannot-verify) says. Every question a command asks about a kind name is answered from that one reading, never from a set the command builds for itself.

The question is always asked within a **scope**, a set of the projects the run read. Each command keeps the scope it documents, so two commands may accept different names; within one scope, a name has exactly one verdict, whichever command asks, except `code` where no row names the homeless kind, as [§REQ-one-answer.differences.identity](../requirements/REQ-one-answer.md#differencesidentity-identity) lists:

| Who asks | Scope |
|---|---|
| `list --kind`, `list --selector`, `list --size --selector` | the selected projects: every loaded project, or those `--project` names ([§FS-list.1.2](FS-list.md#12---project)) |
| a rule subject, on `check`, `check --rule` and in the editor | the project whose configuration reads the rule ([§FS-rule-refusals.sentences.named-sections](FS-rule-refusals.md#sentencesnamed-sections-a-subject-that-needs-named-sections-is-answered-with-one-they-make-valid)) |
| a rule object, or a `[citations]` target | the local project for a bare `KIND`, the aliased project for `alias/KIND`, every project for `*/KIND` ([§FS-config.3.9.5](FS-config.md#395-validation)) |
| `grund id <KIND>` | the project the run loads ([§FS-id.1.1](FS-id.md#11-unknown-and-non-citable-kinds)) |

The verdict is one of four:

1. **citable** — a project in scope configures the name as a citable kind;
2. **configured but not citable** — a project in scope configures it with `citable = false` ([§FS-config.3.4.1](FS-config.md#341-citable--kinds-that-declare-no-ids)), and none in scope has it citable; the verdict carries that project's kind home, and its refusal is [§FS-errors.2.5.1](FS-errors.md#251-a-kind-that-declares-no-ids);
3. **unknown** — no project in scope configures it;
4. **unverifiable here** — the scope names a project alias and the run holds no workspace that could say what that project configures, as [§FS-rules.4.1](FS-rules.md#41-a-rule-this-scope-cannot-verify) defines it for a rule object.

Where two projects in one scope configure a name differently, citable wins, as [§FS-list.1.1](FS-list.md#11---kind) already says for `--kind`. The `known kinds:` line a refusal ends in names the citable kinds of the same scope, once each, in configuration order.

A kind's named sections are read under the project that configures it. A named chapter subject of `KIND` ([§FS-rules.2](FS-rules.md#2-subject-selectors)) is accepted where that project sets `[id] named_sections = true`, whatever the root or another loaded project sets, so `list --selector API.terms` at a workspace root answers whatever `grund api/API-a.terms` answers ([§FS-declarations.section.map](FS-declarations.md#sectionmap-the-section-map-is-the-declarations-body-span)). Where two projects in scope configure `KIND`, the subject is accepted when either has named sections on, and it matches only the declarations of a project that has them on.

`--unused` leaving out end-to-end cases, the kind titles a project lists, and where a non-citable kind's own files must cite are other questions, and stay their own points' ([§FS-config.3.4.1](FS-config.md#341-citable--kinds-that-declare-no-ids)). The rulings this point carries out are [§DF-one-answer-rulings-grammar](../decisions/functional/DF-one-answer-rulings-grammar.md#df-one-answer-rulings-grammar-one-grammar-keeps-the-documented-refusal-bytes-and-order-and-one-kind-universe-keeps-each-commands-vocabulary)'s D18, and the routes it took [§DF-one-kind-verdict](../decisions/functional/DF-one-kind-verdict.md#df-one-kind-verdict-every-command-reads-one-kind-verdict-in-its-own-scope-and-refuses-a-rule-sentence-for-the-first-stage-it-fails).

## scope: Which files a run reads

`include` is the set of paths scanned from the config root ([§FS-scan.scope.include](FS-scan.md#scopeinclude-include-is-scanned-from-the-config-root)), beside every configured kind home ([§FS-scan.scope.homes](FS-scan.md#scopehomes-every-configured-kind-home-is-scanned)). `exclude` is the set of directory names skipped at any depth — one path component each, so an entry containing `/` is refused rather than accepted as a path ([§FS-config.3.5.16](FS-config.md#3516-an-exclude-entry-containing--is-refused)) — `extensions` filters which files are read ([§FS-scan.scope.extensions](FS-scan.md#scopeextensions-an-extension-makes-a-file-readable-not-declarable)), and `respect_gitignore` has the scan honor the ignore files as well ([§FS-scan.scope.ignore-files](FS-scan.md#scopeignore-files-respect_gitignore--the-ignore-files)). A hidden file is not read ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)), and `include` is a scope, not a fence ([§FS-scan.scope.not-a-fence](FS-scan.md#scopenot-a-fence-include-is-a-scan-scope-not-a-fence)). A scan that ends up reading no files at all is reported, not silently passed ([§FS-check.2.2](FS-check.md#22-empty-scan)). In a loaded workspace a scan also stops at every directory another project owns ([§FS-workspace.6.2](FS-workspace.md#62-the-boundary-is-mutual)).

### scope.include: `include` is scanned from the config root

`include` is scanned **from the config root** — the directory the discovered `grund.toml` was found at ([§FS-config.1](FS-config.md#1-file-location-and-discovery)), or, when no config was discovered, the current working directory (never a subdirectory that merely happened to be passed as `grund`'s path argument). So in a config-less repo `grund` (no path) and `grund check .` both scan `requirements.md`, `docs/`, `e2e/`, `src/` relative to the cwd; what an explicit path adds is each command's own ([§FS-scan.path](FS-scan.md#path-what-a-path-argument-means)). A plain parent-relative entry such as `../shared` intentionally names external content and is still scanned; [§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed)'s project-root boundary applies only when a **directory symlink** carries traversal outside the project.

### scope.homes: Every configured kind home is scanned

**Every configured kind home is scanned, whether or not `include` names it** ([§FS-config.3.4](FS-config.md#34-kinds--recognized-kinds)). A home is the repository saying "declarations and citations live here", so `include` names the *extra* roots — `src`, `crates`, a `README.md` — rather than having to repeat the homes the `[[kinds]]` table already spelled. A home that does not exist scans as nothing and earns no finding, so a fresh repository whose default homes are not scaffolded yet stays silent; a home that may exist but cannot be looked up is not that home ([§FS-scan.scope.homes.lookup](FS-scan.md#scopehomeslookup-a-home-that-cannot-be-looked-up-is-a-scan-failure-not-an-absent-home)). The one home that is not a scan root is the one the config says so about: `scan = false` ([§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned)) lists a place without scanning it.

#### scope.homes.lookup: A home that cannot be looked up is a scan failure, not an absent home

A home does not exist only when its lookup says so: the path is not found, a component above it is a regular file, or the file system refuses the name itself as one it cannot hold, such as a `*` on Windows or a component over its length limit: in each, nothing can exist there. A lookup that fails for any other reason says nothing about the home, so the run does not read it as absent. The failure is reported at the home as a scan failure ([§FS-check.2.4](FS-check.md#24-an-incomplete-run)), with the reason [§FS-check.2.4.1](FS-check.md#241-one-reason-for-one-scan-io-failure) derives, the scan goes on, and the run exits `2`, at every severity the kind's rows carry. The home's parent is a different path: a parent that cannot be listed while the home is still looked up and read is a failure at the parent alone, and where both fail they are two failures, each reported once ([§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)). The rule is the walk's for every root, so an `include` entry whose lookup fails is reported the same way. Decided in [§DF-home-lookup-failure-fails-at-the-home](../decisions/functional/DF-home-lookup-failure-fails-at-the-home.md#df-home-lookup-failure-fails-at-the-home-a-root-whose-lookup-fails-for-a-reason-other-than-absence-fails-at-the-root-and-exits-move-with-it), which names the exits this moved.

##### scope.homes.lookup.outward: A root link leaving the project answers to its gate first

Where a root's lookup fails, the root's boundaries are still judged first, on where the root goes as far as the disk answers: each link on the way is read, and what lies behind the directory that refused keeps its written names. So a root that is a directory link going outside the project gets the verdict it gets when its target opens: the walk prunes it in silence, as [§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed) prunes it, and a kind's folder place on version 2 never reaches the walk, because config load refuses it first ([§FS-config-v2.schema.places.boundaries.3.1](FS-config-v2.md#schemaplacesboundaries31-judged-as-far-as-the-disk-answers)). Either way a directory that refuses the lookup out there is none of the inputs that decide the run's bytes ([§REQ-deterministic-output.2](../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation)). A root that resolves into another project stays that project's ([§FS-workspace.6](FS-workspace.md#6-nested-project-boundary)). Only the link's name can say what it names when the target cannot be looked up, so a link whose name the walk would read as a file is not taken for a directory: file links are followed wherever they resolve, the file is a hole in what the run answers from, and the failure is reported at the root. An inward link, a root that is not a link, and a root written below a linked ancestor are reported at the root by the rule above.

##### scope.homes.lookup.path: A path the command is given is missing only when its lookup says so

A `<path>` given to a command is a root the walk starts from ([§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports)), so the rule above is its rule too. The run says `error: path does not exist: <path>`, prints nothing on stdout and exits `2` only where the lookup of the path says nothing can stand there: it is not found, a component on the way is a regular file, or the file system refuses the name as one it cannot hold. A lookup refused for lack of permission, on the path itself or on any directory on the way to it, says nothing about the path, so the run never says that the path does not exist, which would send the reader looking for a file that is in front of them. It reports the refusal as the scan failure of [§FS-check.2.4](FS-check.md#24-an-incomplete-run), located at the path as given, never at the directory that refused the lookup or under a name the path resolves to ([§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)), with the reason `permission denied` ([§FS-check.2.4.1](FS-check.md#241-one-reason-for-one-scan-io-failure)) and the fix of its place ([§FS-check.2.4.3](FS-check.md#243-what-failed-and-where-decide-the-code-and-the-fix)), which for a path that made the run read it is `passed`. It does so on every surface that publishes a scan failure, the `io` record of `--format json` among them, and the run exits `2`. With `.r` at mode `000`, `grund check .r/sub/x.md` prints `error: .r/sub/x.md: permission denied; make the path readable, or keep it out of the scan by not passing it, because exclude does not prune a path the command is given`, the line `grund check .r` prints at `.r`. That holds whether the path names a file or a directory, and whether or not anything stands behind the refusal: `grund check .r/sub` and `grund check .r/sub/nothere.md` are the same report at their own paths, because the run cannot tell. It holds for every command that scans from a `<path>`: `list`, `cover`, `fmt`, `show`, `refs` and `id` as well as `check`, where `id` refuses with the path and the reason alone, the underlying error a failed scan stops it with ([§FS-id.4](FS-id.md#4-next-number-derivation)). A link given as the path is such a path too, and is reported with the line its link earns ([§FS-scan.scope.links.owed.refused](FS-scan.md#scopelinksowedrefused-a-target-the-lookup-is-refused-on-the-way-to-is-not-a-broken-link)).

#### scope.homes.why: Why every home is scanned

Scanning every home closes a trap that had nothing to do with non-citable kinds and everything to do with why one would be configured: a `folder` or `file` outside `include` was never scanned, so its declarations did not exist and its citations were **invisible rather than dangling** — no resolution, no finding, nothing to notice. A kind whose entire content is "this directory matters" would have fallen into it on its first line of config. **Upgrade note:** a repository that had a home outside `include` starts seeing that home's findings; they were always true of the tree, and the run was simply not reading it.

### scope.roots: A scan root outruns every rule about descent

A home is a **scan root**, and no scan root is pruned by `exclude`, an ignore file, or the hidden-directory rule ([AR-scanner.1](../architecture/AR-scanner.md#1-tree-walk)) — so a home the repository also excludes is read, while everything *below* it is filtered as usual. That is the honest reading of a config that says both: the `[[kinds]]` entry names the directory, and `exclude` was written about descendants. All three are rules about a descent, which is why a root outruns them. Two rules are about a file's own name, and a root does not outrun either: the hidden-file rule ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)) and the `extensions` list ([§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)). A file root either name rule refuses is not read, and `check` names it rather than passing over it.

### scope.not-a-fence: `include` is a scan scope, not a fence

A citation in a file that neither `include` nor a kind home brings into the scan is invisible rather than merely unchecked ([§FS-check.1.3](FS-check.md#13-the-full-tree-scope---full)), so `grund check --full` scans the whole config root past this key. The flag cancels `include` and, with it, the `scan = false` prune of [§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned), and nothing else: every other rule of this chapter applies to that scan unchanged ([§FS-check.1.3.1](FS-check.md#131-the-scan-covers-the-whole-config-root)), and what it reports outside the default scope is [§FS-check.1.3](FS-check.md#13-the-full-tree-scope---full)'s to say.

### scope.hidden: A hidden file is not read, and the rule is not about descent

The scan skips a hidden directory by not descending into it; it skips a file whose own name begins with `.` by the name that file wears, before `extensions` is consulted at all ([AR-scanner.1](../architecture/AR-scanner.md#1-tree-walk)). So `docs/.notes.md` is not scanned though `md` is listed, and a citation inside it neither resolves nor dangles — it is invisible the way one outside `include` is, and `grund check --full` does not reach it either ([§FS-scan.scope.not-a-fence](FS-scan.md#scopenot-a-fence-include-is-a-scan-scope-not-a-fence)). Being a rule about a name rather than about a descent, it also reaches a scan **root**, the one exception to [§FS-scan.scope.roots](FS-scan.md#scoperoots-a-scan-root-outruns-every-rule-about-descent): a `file` home whose name is hidden, like an `include` entry naming one, is not read as a root, and `check` names it at the row that made it a root ([§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read)), so a configuration that names a dotfile to read never passes as `success`. It is a blind spot the repository can see and plan around ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)): what decides is the file's own name, so a document that must be checked is one not named as a dotfile, and a run handed such a file whose extension `extensions` *does* allow says so rather than blaming the list ([§FS-check.2.2](FS-check.md#22-empty-scan)).

### scope.extensions: An extension makes a file readable, not declarable

Listing an extension makes a file *readable*, not declarable. A prose markup format other than Markdown — AsciiDoc, reStructuredText, LaTeX — has its citations checked as soon as its extension appears in `extensions`, because the citation grammar is format-agnostic; its native heading syntax still declares nothing, since a declaration is a `#`-prefixed heading or a comment-prefixed line. Whether those formats should be declaration homes of their own is an open discussion ([§DISC-markup-format-declarations](../discussions/proposals/2026-05-25-markup-format-declarations.md#disc-markup-format-declarations-declarations-in-asciidoc-restructuredtext-latex-and-similar-markup-document-formats)), not a configured behavior.

#### scope.extensions.default: The `extensions` default follows the language table

With no `extensions` key, a run reads `md` followed by every extension grund's built-in language table names, in that table's order: each extension [§FS-inline-citation-style.1.1.2](FS-inline-citation-style.md#112-languages) assigns a doc-comment recognizer, and each language read through a comment prefix alone ([§FS-languages](FS-languages.md#fs-languages-how-a-source-files-lines-are-read), which pairs each prefix with its extensions). There is no second list to keep in step with it, so a language the table gains is read by default in the same release, and a project that wrote no `extensions` is never told `success` over a file in a language grund classifies but did not open ([§REQ-no-missed-citation.3](../requirements/REQ-no-missed-citation.md#3-proven-per-host-language)). A language the table gains is appended, which keeps every earlier default a prefix of the current one. Extensions match case-sensitively, so `r` and `R` are two entries. An explicit `extensions` still replaces the default whole. Why the default widens rather than warns is [§DF-default-extensions-follow-language-table](../decisions/functional/DF-default-extensions-follow-language-table.md#df-default-extensions-follow-language-table-the-scan-extensions-default-reads-every-language-grund-classifies).

#### scope.extensions.root: A file root whose extension is unlisted is not read, and `check` says so

A scan root that is a single file — a `[[kinds]]` `file` home, a version-2 `files` entry, or an `[scan] include` entry naming a file — is read only if its extension is one `extensions` lists, or in a version-2 file one a language of `[schema.sources] languages` reads. A file with no extension at all, such as `NOTES`, is refused by the same rule, unless a version 1 list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)). The list is not widened for a root: an unlisted extension has no comment prefixes to read the file with, and a row may name a file only as a place in the Project map. What the root earns instead is a report: every `grund check` that has the root in its configured scope prints the warning of [§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read), located at the row that made the file a root, so a configuration that names a file to read and a list that keeps it out never passes as `success` ([§REQ-no-missed-citation.1](../requirements/REQ-no-missed-citation.md#1-no-silent-skips)).

Three such files earn nothing. A row marked `scan = false` is not a root ([§FS-scan.scope.homes](FS-scan.md#scopehomes-every-configured-kind-home-is-scanned)), and a home that does not exist scans as nothing. A value row's home that is a value source ([§FS-values.terms](FS-values.md#terms-terms)), JSON or YAML, is read too, by the value pass rather than the walk ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)), so a `.yaml` `file` home on a value row is no unread root. A directory root is filtered file by file, which is what `extensions` means, so it earns nothing either. The other commands that scan — `list`, `refs`, `show`, `cover`, `fmt` — read the same files and say nothing about the root: the fact is about the coverage of `check`'s verdict ([§DF-unread-scan-root](../decisions/functional/DF-unread-scan-root.md#df-unread-scan-root-a-configured-file-root-whose-extension-is-unlisted-is-named-not-read)).

A file root whose name is hidden is refused by [§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent) as well, and is named by the same warning, not passed over: where its extension is unlisted too, that one warning names both rules ([§DF-unread-hidden-root](../decisions/functional/DF-unread-hidden-root.md#df-unread-hidden-root-a-configured-file-root-with-a-hidden-name-is-named-not-read)).

#### scope.extensions.empty: In version 1, an empty string in the list reads a file with no extension

A version 1 `[scan] extensions` that holds the empty string, as `extensions = ["md", ""]` does, reads each file whose extension is missing, empty or not UTF-8: `NOTES`, `FACTS.`, and a name in which what follows the last dot is not UTF-8. Every reader of the list gets this one answer, so such a file is read wherever the list is asked about it: as a file root, which then earns no warning of [§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read); as a file in a directory the scan walks; as a buffer; and as a stub's target. What the scan reports of a file it reads, it reports of this one too, down to a link that does not resolve and bytes that do not decode. The hidden-file rule is asked first ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)), so `.FACTS` stays unread under the entry, and a list without the entry reads none of these names ([§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)).

Version 1 keeps this reading for good, under [§FS-config.5.2](FS-config.md#52-every-older-version-keeps-its-meaning), and meets the rule at `config migrate` ([§FS-config.requirements.5](FS-config.md#requirements5-a-mistake-in-the-config-fails-loudly--realized-one-case-deferred), [§FS-config-migrate.3.1.9](FS-config-migrate.md#319-an-empty-string-in-scan-extensions)). The entry earns no warning of its own: the version 1 caution ([§FS-config.5.3](FS-config.md#53-a-version-1-config-is-cautioned-and-never-retired)) already sends the file to the command that names it ([§DF-v1-empty-extension-reading](../decisions/functional/DF-v1-empty-extension-reading.md#df-v1-empty-extension-reading-version-1-keeps-reading-a-file-with-no-extension-through-an-empty-string-in-scan-extensions-and-the-specification-is-corrected-to-say-so)). Version 2 has no such entry, and refuses an empty suffix at load ([§FS-config-v2.schema.sources.extensions](FS-config-v2.md#schemasourcesextensions-schemasourcesextensions-maps-a-suffix-to-a-language)).

### scope.ignore-files: `respect_gitignore` — the ignore files

`respect_gitignore` (default `true`) makes the scanner honor every form of ignore file the `ignore` crate recognizes — `.gitignore` at any depth, `.git/info/exclude`, the global `core.excludesFile`, and `.ignore` files. Set to `false` only when you genuinely need to scan ignored paths. The directory-level `exclude` list is applied **in addition** to ignore-file rules, never instead of them. A global pattern anchors at the top of its path's repository, whatever directory the run starts from ([§FS-scan.scope.ignore-files.global](FS-scan.md#scopeignore-filesglobal-a-global-excludes-pattern-anchors-at-the-top-of-its-paths-repository)). See [AR-scanner.1.1](../architecture/AR-scanner.md#11-respecting-gitignore-and-friends).

#### scope.ignore-files.unparsed: An ignore file the walk cannot parse fails the run, unless the run does not apply it

A line of an ignore file that does not parse takes its rule with it, so the run's view of the tree is incomplete. It is a scan failure: one line at the ignore file and exit `2` ([§FS-check.2.4](FS-check.md#24-an-incomplete-run), [§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)), in whichever directory the walk meets the file, whether a walk root sits at it, above it or below it. Whether a kind home happens to lie below the file does not change the answer.

Two kinds of file cost the walk that met them no rule, so a line of theirs that does not parse is no failure of that walk, and the tests are asked whichever way it met the file. One walk that reads under the file is enough to report it, still as one line.

1. A `.ignore` or `.gitignore` that governs nothing the walk reads: `exclude` keeps out whatever the file's directory holds, or whatever the walk root holds where that root lies below the file, by the test any file there faces on the way down from the walk root ([§FS-config-v2.schema.sources.exclude.roots](FS-config-v2.md#schemasourcesexcluderoots-how-exclude-composes-with-the-other-filters)). So `vendor/**` clears `vendor/.ignore`. `.ignore`, `.*` or `vendor/*.md` does not, because what the directory holds is still read under the file's rules: `exclude` keeps a file from being read as a source and leaves its rules in force ([§FS-scan.scope.ignore-files](FS-scan.md#scopeignore-files-respect_gitignore--the-ignore-files)). Nor does a list holding a `!` negation, which may rescue any name. `exclude = ["vendor/"]` prunes the directory, so a walk from above never meets the file, while a walk from a kind home at `vendor/sub` reads under it and reports it: the two differ because what they read differs. `.git/info/exclude` governs its whole repository, so this test says nothing of it.
2. A `.gitignore` no repository encloses. A walk applies a `.gitignore` only inside a repository, except a mounted root's, which reads one git checkout or not ([§FS-remote-projects.ignore](FS-remote-projects.md#ignore-ignore-isolation)). A `.ignore` is applied with or without a repository, so it fails the run either way. Only the absence of a repository is carved out: a `.gitignore` the walker passes over for another reason, one above a nested repository, still fails the run.

The record of this verdict is [§DF-unparsed-ignore-file-at-any-depth](../decisions/functional/DF-unparsed-ignore-file-at-any-depth.md#df-unparsed-ignore-file-at-any-depth-an-ignore-file-the-walk-cannot-parse-fails-the-run-at-any-depth-unless-the-run-does-not-apply-it).

#### scope.ignore-files.global: A global excludes pattern anchors at the top of its path's repository

An ignore file means what git means by it, and the global `core.excludesFile` is no exception. git reads each of its patterns relative to the top of the repository the path belongs to. grund anchors them at the top the `ignore` crate counts, and at nothing else: the nearest directory above the path that holds `.git` or a Jujutsu `.jj`, the same top that bounds the `.gitignore` files. That is git's top, except in a jj workspace with no `.git` nested inside a git repository: git anchors there at the outer top, and grund at the workspace, where it already bounds the `.gitignore` files. So an anchored pattern, one with a `/` before its end such as `notes/gen/`, ignores `<top>/notes/gen/` and nothing at another depth, while an unanchored one such as `gen/` matches at any depth below that top. The directory grund runs from does not move the top, whether that is the repository top, a subdirectory or a directory outside the repository. A config root or scan root above the repository top does not move it either. Nor does the spelling a platform gives the paths it walks, so a run on Windows, whose walk reads canonical `\\?\` paths, ignores what a run on Linux ignores. Where a scan walks into a repository nested inside another, a path anchors at the top of the innermost repository that holds it.

Nothing else about the global file changes. A path below no such top is matched by none of its patterns, as git matches none outside a repository. Precedence stays git's: `.ignore` files, then the `.gitignore` files up to the repository top, then that repository's `info/exclude`, which a top holding only `.jj` does not have, then the global file. A `!` re-include in any of the first three still keeps a file the global file ignores. The walk and a stub target's eligibility read the one anchoring, so a file the walk does not read is not a stub target either ([§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing)). Which files a run reads does not depend on where the run was started ([§REQ-deterministic-output.2](../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation)). Why this correction may move a verdict is [§DF-global-excludes-anchor-at-the-repository-top](../decisions/functional/DF-global-excludes-anchor-at-the-repository-top.md#df-global-excludes-anchor-at-the-repository-top-a-global-excludes-pattern-anchors-at-the-repository-top-wherever-grund-runs-from).

#### scope.ignore-files.pathname: The global excludes filename is the one Git resolves

When `respect_gitignore = true`, grund loads the existing readable global excludes file at the pathname Git resolves. A `~` anywhere except a leading home abbreviation (`~/` or `~user/`) is a literal pathname character, including in Windows short names such as `RUNNER~1`. Expanding a leading abbreviation does not expand literal tildes in the resulting home pathname again. Thus `/work/a~b/global.ignore` names that file, and `~/global.ignore` under a home named `/work/h~me` names `/work/h~me/global.ignore`.

The scan, its probe of an individual path, and a stub target's eligibility use that same resolved file. This changes neither global-file discovery and configuration precedence nor pattern anchoring and ignore precedence ([§FS-scan.scope.ignore-files.global](FS-scan.md#scopeignore-filesglobal-a-global-excludes-pattern-anchors-at-the-top-of-its-paths-repository)); `respect_gitignore = false` still opts out. The verdict correction and its remedies are recorded in [§DF-global-excludes-literal-tilde](../decisions/functional/DF-global-excludes-literal-tilde.md#df-global-excludes-literal-tilde-preserve-literal-tildes-in-the-global-excludes-pathname). This point defines pathname resolution for a readable file, not a new diagnostic or exit policy for missing or unreadable global files.

### scope.links: A symlink in the tree is followed

A **file symlink** inside a scanned tree is followed wherever its target resolves. A **directory symlink** is followed only while its canonical target remains inside the independently checked project's canonical root; when the target is outside that root, the directory is pruned and no file below it is scanned. The same gate applies when a configured or explicit scan root is itself a directory symlink. Decided in [§DF-symlink-scan](../decisions/functional/DF-symlink-scan.md#df-symlink-scan-a-symlink-in-the-scanned-tree-is-followed-and-the-report-names-the-link).

This is a boundary on link traversal, not on scan paths generally: a non-symlink parent-relative `include` may still name external content. Nor does resolving the project's own config root make it an outward link: when the repository itself was reached through a symlink, its canonical root is the fence and its tree remains readable. In-root directory links keep their in-tree spelling and are followed as before. A loaded workspace adds the stronger ownership boundary of [§FS-workspace.6](FS-workspace.md#6-nested-project-boundary), so a link into another loaded project is pruned even when that project is physically inside the current project's root.

#### scope.links.names: The directory rules apply under the link name

The directory rules of [§FS-scan.scope](FS-scan.md#scope-which-files-a-run-reads) still apply to a followed directory under its **link** name, so `docs/node_modules -> ../../node_modules` is excluded exactly as a real directory of that name would be. The two boundaries that are *not* name rules are another project's root, which a link may not carry a scan across in any direction ([§FS-workspace.6](FS-workspace.md#6-nested-project-boundary)), and an E2E case directory, whose fixture tree stays out of the host scan however a link reaches it ([§FS-config.3.4.4.3](FS-config.md#3443-e2e-is-configured-not-a-default)).

#### scope.links.unresolvable: A link the scan cannot resolve is reported, and not scanned into

A link the scan cannot resolve is not a silent skip: a broken target, or a loop such as `docs/self -> .`, is the per-file scan failure of [§FS-check.2](FS-check.md#2-outputs) — reported at the link's own path, the scan continuing past it, the run exiting `2` ([§REQ-no-missed-citation.1](../requirements/REQ-no-missed-citation.md#1-no-silent-skips)). Past it, and never *into* it: a loop is pruned where it is met, including the kind whose target reaches back over the scan root itself (`docs/up -> ..`), so the run never reports findings out of a tree it has just called unreadable and `include` still bounds what was read.

##### scope.links.unresolvable.unopenable: A directory link whose target cannot be opened fails at the link, once

A directory link whose target exists but cannot be opened, because this user may not list it (a target at mode `000`), is a link the scan cannot resolve too. Its failure is located the way any other is: at the link's own path, where the same unreadable directory would be reported had it stood there in place of the link ([§FS-check.2.4](FS-check.md#24-an-incomplete-run)). It is never located at the scan root or the home the walk happened to start from, because neither of those is what failed. One link is one place, so the failure is reported once, however many walk roots reach it: the config root, and each home the link lies under. It is one place too under every name that reaches it, so with `e2e -> realE` the link `realE/link` and the path `e2e/link` are one entry and one line ([§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)). A target that the scan also reaches inside the project is a second unreadable directory, with a line of its own. With `docs/ext -> ../real` and `real` unreadable, the run reports `docs/ext` and `real`, and nothing else. A link the walk is told not to read stays silent wherever it points, because no walk reaches it: a hidden name, a `[scan] exclude` entry or an ignore file that covers the link keeps it out of the walk ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)), and a target another walk does read keeps the line that walk earns. A link standing at a home the config lists without walking ([§FS-config.3.4.7.2](FS-config.md#3472-not-scanned-however-the-scan-arrives)) is not one of those: no declared blind spot covers it, so it is reported at the link. Decided in [§DF-unopenable-link-fails-at-the-link](../decisions/functional/DF-unopenable-link-fails-at-the-link.md#df-unopenable-link-fails-at-the-link-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-or-is-pruned-and-exits-move-with-it-in-both-directions), which names the exits this moved.

##### scope.links.unresolvable.named: A looping link named as the path is reported at the link, not as missing

A run handed a looping link ([§FS-scan.scope.links.owed.cycle](FS-scan.md#scopelinksowedcycle-a-link-whose-resolution-loops-is-a-loop-whatever-its-name)) as its `<path>`, as in `grund check docs/self`, was handed a path that exists: the link is there, and only resolving it fails. So the run reports the failure the walk reports for that link, at the link's own path, and exits `2`. It never says `path does not exist`, which would send the reader looking for a file that is in front of them. That holds whatever the link's extension: `grund check docs/self.md` is the same report.

#### scope.links.owed: Which unresolvable links are owed a report

That report is owed only where the scan would otherwise have read through the link, judged by the same rules as any other entry: the ignore files for both kinds, and `extensions` as well for a broken link, which names a file where a loop names a directory. So a dangling `docs/logo.png -> nowhere`, and a link of either kind that `.gitignore` covers, stay silent — the scan was never going to read them. A directory-only pattern such as `docs/ext/` covers a link that names a directory whether or not its target opens, a loop and a directory link whose target cannot be opened alike, just as it covers the followed link when its target opens ([§FS-scan.scope.links.names](FS-scan.md#scopelinksnames-the-directory-rules-apply-under-the-link-name)); a dangling link names a file, and such a pattern does not cover it.

##### scope.links.owed.fence: The project-root fence is judged on the target, opened or not

The rules a directory link answers to include the project-root fence of [§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed) and the ownership boundary of [§FS-workspace.6](FS-workspace.md#6-nested-project-boundary). Both are judged on the link's canonical target. That target is worked out from the directories on the way to it, never from the target's own contents, so it is known whether or not the target can be opened.

A directory link whose target cannot be opened, and whose target lies outside the project and in no tree the run reads, is pruned in silence, as it would be if the target were readable: the scan was never going to read through it, and that directory's mode is none of the three inputs that decide the run's bytes ([§REQ-deterministic-output.2](../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation)). That holds whichever walk root meets the link. An inward link whose target cannot be opened is inside the fence and is owed its report ([§FS-scan.scope.links.unresolvable.unopenable](FS-scan.md#scopelinksunresolvableunopenable-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-once)). A link named as the scan root itself is the root's gate, as [§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed) says, not this one.

A link whose target lies in a tree the run does read, a project of the run or an import's tree ([§FS-imports.mount](FS-imports.md#mount-an-import-is-a-mounted-root-read-live-and-read-only)), is owed its report at the link too, though the walk does not read through it: project-wide resolution reads that tree, so the failure is a hole in what the run answers from. Decided in [§DF-unopenable-link-fails-at-the-link](../decisions/functional/DF-unopenable-link-fails-at-the-link.md#df-unopenable-link-fails-at-the-link-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-or-is-pruned-and-exits-move-with-it-in-both-directions), which names the exits this moved.

##### scope.links.owed.cycle: A link whose resolution loops is a loop, whatever its name

A link the filesystem cannot resolve because resolving it loops is a loop, not a broken link. That is the link that reaches back to a directory above it (`docs/up -> .`), and equally the link that names itself (`docs/self -> self`) and each link of a cycle of links (`docs/a2 -> b` beside `docs/b -> a2`), whose resolution never arrives at a target at all. A broken link's name is asked what the target would have been only because the target does not exist and cannot say; here the filesystem says what went wrong, a loop rather than a missing target, so the name is not asked. A looping link is judged as a loop is judged, by what a directory faces: the ignore files as a directory, a hidden name and `[scan] exclude`, a version 2 pattern as well as a version 1 name, and never `extensions`. So `docs/self -> self`, `docs/self.md -> self.md` and `docs/logo.png -> logo.png` are each owed their report, while `.gitignore` covering `docs/self`, or the hidden `docs/.self -> .self`, keeps it silent. The extensionless blind spot of [§FS-scan.scope.links.blind-spot](FS-scan.md#scopelinksblind-spot-a-broken-link-with-no-extension-is-a-declared-blind-spot) is the broken link's alone. Why, and the exits it moved: [§DF-looping-link-is-a-loop](../decisions/functional/DF-looping-link-is-a-loop.md#df-looping-link-is-a-loop-a-link-whose-resolution-loops-is-a-loop-whatever-its-name-judged-by-the-ignore-files-as-a-directory-and-exits-move-with-it-in-both-directions).

##### scope.links.owed.refused: A target the lookup is refused on the way to is not a broken link

A link is broken only when the lookup of its target says nothing can stand there, the answer [§FS-scan.scope.homes.lookup](FS-scan.md#scopehomeslookup-a-home-that-cannot-be-looked-up-is-a-scan-failure-not-an-absent-home) asks of a home: the target is not found, or a component on the way is a regular file. A lookup refused for lack of permission, on the target or on any directory on the way to it, says nothing about the target, so the link is not broken, whatever its name. With `docs/x -> ../.r/sub` and `.r` at mode `000`, neither the `extensions` test above nor the blind spot of [§FS-scan.scope.links.blind-spot](FS-scan.md#scopelinksblind-spot-a-broken-link-with-no-extension-is-a-declared-blind-spot) applies to `docs/x`: it is the unopenable link of [§FS-scan.scope.links.unresolvable.unopenable](FS-scan.md#scopelinksunresolvableunopenable-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-once), reported at the link with the line a link to a target at mode `000` earns, and judged by every other rule here, the fence on where it goes as far as the disk answers ([§FS-scan.scope.homes.lookup.outward](FS-scan.md#scopehomeslookupoutward-a-root-link-leaving-the-project-answers-to-its-gate-first)). That holds whether or not anything stands behind the refusal, because the run cannot tell. A link given as the path itself, `grund check docs/x`, is the same link, reported at the link the same way, and its refused lookup is no missing path ([§FS-scan.scope.homes.lookup.path](FS-scan.md#scopehomeslookuppath-a-path-the-command-is-given-is-missing-only-when-its-lookup-says-so)). Decided in [§DF-refused-link-lookup-is-not-a-broken-link](../decisions/functional/DF-refused-link-lookup-is-not-a-broken-link.md#df-refused-link-lookup-is-not-a-broken-link-a-directory-link-whose-target-lookup-is-refused-on-the-way-is-unopenable-not-broken-and-exits-move-with-it), which names the exits this moved.

#### scope.links.blind-spot: A broken link with no extension is a declared blind spot

A broken link with **no extension at all** is silent for the same reason, unless a version 1 list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)), and is worth naming, because it is the one case where that answer can be wrong: `docs/shared -> ../nonexistent-dir` would have been a directory to descend into had it resolved. Nothing on disk distinguishes it from `bin/tool -> nowhere`, since the target does not exist and only the target could have said which it was, and reporting every extensionless dangling link is the noise this gate exists to prevent. That is a declared, bounded blind spot ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)) and not a silent one: a link you need scanned is one you need to resolve. A link whose resolution loops is not broken and is not in this blind spot: its target is not missing, and it is owed its report by [§FS-scan.scope.links.owed.cycle](FS-scan.md#scopelinksowedcycle-a-link-whose-resolution-loops-is-a-loop-whatever-its-name) whatever its name.

## identity: Which path names a file a run read

A file a run reaches through a link is named by the path the run met, and a physical file is read once, one way.

### identity.link-path: A finding names the in-tree link path

Every finding from a link met **inside a scanned tree** is reported at the in-tree link path, never the target's: that is the path a reader can act on, and it is what keeps `relative_paths` output ([§FS-config.3.6](FS-config.md#36-output--report-format)) and the additivity rule of [§FS-check.1.3](FS-check.md#13-the-full-tree-scope---full) meaningful. An explicit path argument follows the same reporting rule: resolving `grund check docs/beta.md` identifies and reads the target, but every text and JSON report names `docs/beta.md` as reached through the configured CLI base. This remains true when the target resolves outside the config root — the in-tree link is the bounded, actionable spelling and the external physical path never becomes report output. Named is not the same as named first: where the run also reaches the file by another name, a finding about the file's content is the whole run's one line, so `grund check notes/link.md` may print `notes/link.md` as the second name on it ([§FS-scan.identity.findings.content](FS-scan.md#identityfindingscontent-a-content-finding-is-one-line-naming-every-name)).

### identity.root-path: The scan root keeps the path the run was handed

The same rule reaches the **scan root itself**: a repository whose own path is reached through a link — a symlinked `~/work`, macOS resolving `/var` to `/private/var` — is scanned and reported under the path the run was handed, never the physical one it resolves to. Resolving a root is how a run recognizes that a scope *is* the config root; it is not a decision about what the report calls it, and a finding spelled physically is one `relative_paths` ([§FS-config.3.6](FS-config.md#36-output--report-format)) cannot render and no reader of that repository ever wrote.

### identity.read-once: One physical file is read once

One **physical** file is read once however many spellings reach it, and the run keeps every spelling that reached it. Spellings are listed the earlier root's first, and within a single root lexicographically ([§FS-check.1.3](FS-check.md#13-the-full-tree-scope---full), [§FS-errors.4](FS-errors.md#4-determinism)). That order picks only the name listed first: not what the file is read as ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)), not the homes it is judged in ([§FS-config-v2.schema.places.ownership](FS-config-v2.md#schemaplacesownership-a-listed-file-then-the-deepest-folder), [§FS-declarations.checks.misplaced-declaration](FS-declarations.md#checksmisplaced-declaration-misplaced-declaration-configured-kind-home)), and not which names a finding carries ([§FS-scan.identity.findings](FS-scan.md#identityfindings-a-finding-about-a-file-with-two-names-names-each-spelling-once)). Two names are one file exactly where they resolve to one path, a file link and anything below a directory link alike. Hard links resolve to two paths and are two files, so a declaration in one is a duplicate of itself in the other ([§FS-declarations.checks.duplicate](FS-declarations.md#checksduplicate-duplicate-declaration)).

### identity.reading: How a file is read belongs to the file, not to the name that reached it

A file inside the config root is read as its own name reads, when that name claims a reading. Any other file keeps the reading of the name that reached it. If two in-tree names of such a file read differently, it is refused ([§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)).

So with `txt` configured as Rust, `fs/m-real.md` and a link `fs/a-link.txt -> m-real.md` both read as Markdown, because the file's own name says so: the same declarations and the same `fmt` bytes under any name the link is given, in a whole run and in a run naming either spelling. Conversely `fs/m.md -> z.txt` reads as Rust, so a link named `.md` never gets a Rust file's string literals rewritten ([§FS-fmt.2.3](FS-fmt.md#23-what-is-never-rewritten)). Decided in [§DF-one-file-one-reading](../decisions/functional/DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name).

#### identity.reading.claims: A name claims a reading when the configuration admits and reads that name

Under version 2 a name claims a reading when an admitted language reads it ([§FS-config-v2.schema.sources.extensions](FS-config-v2.md#schemasourcesextensions-schemasourcesextensions-maps-a-suffix-to-a-language)). Under version 1 it does when the extension list holds its extension. So `LICENSE` claims nothing, and neither does `real.txt` where `txt` is not admitted, and each keeps the reading of the name that reached it: `docs/license.md -> ../LICENSE` stays Markdown. A version 1 list holding the empty string reads `LICENSE` ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)), so there `LICENSE` does claim a reading and that link stops being Markdown.

Only the name counts. A file whose own spelling is ignored, excluded, hidden or under no source still claims by its name, so `docs/fs/gen.md -> ../../build/gen.rs` reads as Rust with `build/` ignored.

#### identity.reading.outside: An outside name has no say

A target outside the config root is in the tree only through its link ([§FS-fmt.2.3.2](FS-fmt.md#232-a-link-that-leaves-the-config-root-is-not-written-through)), and its name decides the reading no more than it decides a reported path ([§FS-scan.identity.link-path](FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path)). Under `txt = "rust"`, `fs/spec.md -> /elsewhere/spec.txt` reads as Markdown and keeps its declarations.

#### identity.reading.plain: A name only `--full` or a handed path reaches decides nothing

A file's names are judged over the names the plain run reaches ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)), when it reaches any. A name reached only by `--full`, or only by being handed to a run, decides nothing: not the reading, not a refusal ([§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)), not a move ([§FS-scan.checks.reading-moved](FS-scan.md#checksreading-moved-a-link-is-read-as-its-targets-own-name-reads)), and not the name a finding stands at. That is what keeps `--full` additive and a run naming a path in agreement with the whole run. So with `include = ["docs"]`, `docs/license.md -> ../LICENSE` and `other/license.rs -> ../LICENSE`, the file is Markdown in `check`, in `check --full` and in `check other/license.rs`, a finding in it is `docs/license.md:3` from all three, and `list other/license.rs` and `fmt other/license.rs --write` read it as Markdown too. A handed path under a directory the configuration excludes is such a name as well: a plain walk of its root passes it over.

Where the plain run reaches none of a file's names there is nothing to agree with, so the names the run met are judged among themselves, and the line stands in the out-of-scope tier a wider scan's findings belong to ([§FS-check.3.14](FS-check.md#314-out-of-scope-unresolvable-citation---full-only)):

```text
other/a.md:1: error: outside [scan] include: other/a.md and other/a.rs are one file that reads two ways, as markdown and as rs; keep one name, or give the file a name that claims a reading
```

#### identity.reading.entry: Whether a spelling enters the scan is judged by the name met

The hidden-file rule and the extension list decide whether a spelling enters the scan, and they ask the spelling ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent), [§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)). Only what the file is read as moves. With `txt` not admitted, `notes.txt -> spec.md` stays unread and no finding names it.

#### identity.reading.every-caller: Every run and every reader gets the one answer

Whole runs and runs naming any spelling agree. `check`, `list`, `show` and `id` already read the whole project and the path narrows only the report ([§FS-scan.path](FS-scan.md#path-what-a-path-argument-means)). A narrow `fmt`, `cover` or `refs` run that meets a link to a file whose own name claims nothing does one project walk to collect the file's other names, so `fmt docs/license.rs --write` cannot rewrite a file another name reads as Markdown. A tree with no link pays nothing for this.

Every reader of the file asks the same rule: the text scan, the value reader, the checker, the formatter, `show` and the editor. The value reader takes JSON or YAML from it, so `values/a.json -> limits.yaml` is YAML. A text-named link to a value source is still read by the value reader, once ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)). A stub's written name is still judged as written ([§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing)), and its target's text is read through this rule.

### identity.findings: A finding about a file with two names names each spelling once

A file reached by two names has one set of declarations and citations, and a finding about it repeats no line and names no spelling twice. How it names them depends on whether the finding depends on where the file sits. `decl.file` and `cite.file` hold the name listed first, and `list`, `refs` and `show` print one row at that name, while an ambiguous `show` names both ([§FS-declarations.checks.duplicate](FS-declarations.md#checksduplicate-duplicate-declaration)). A run of those three naming a path lists the name it was handed first, as [§FS-scan.identity.link-path](FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path) requires, so `grund list notes/link.md` prints `notes/link.md:1` where `grund list` prints the name listed first; `check` alone prints the whole run's line, because a finding's sites keep it in scope ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)). The editor shows a content finding on every name of the file it has open, once on each, and a place finding at its own spelling only.

#### identity.findings.place: A place finding is judged at each spelling

A rule that asks which row owns a file asks it of every spelling at its own path: misplaced declarations, citation directions of a file, grounding, indexes and stubs ([§FS-config-v2.schema.places.ownership](FS-config-v2.md#schemaplacesownership-a-listed-file-then-the-deepest-folder), [§FS-config.3.9.2](FS-config.md#392-the-homeless-kind)). Each finding is located at the spelling it holds at. So `docs/ar/x.md -> ../fs/x.md` holding `# FS-x` gets one error at `docs/ar/x.md:1` and none at `docs/fs/x.md:1`, whichever directory sorts first. A link in a second folder of the same row owes that folder's index an entry, and the finding stands at the spelling in that folder: `zz/x.md -> ../aa/x.md` is told at `zz/x.md:1`. The same holds where the name listed first is in no home at all: with `include = ["docslink"]` and `docslink -> docs`, the file a kind's home holds owes its index an entry at `docs/functional-spec/x.md:1`, because a kind's home is a plain root ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)), and an entry written in that index answers it under either name. The maintainer adds the entry, and `fmt --write` links a bare one; it adds none itself. A run naming a path narrows a place finding by the name it stands at, so `grund check tests/e2e/n.rs` prints that link's line and not its target's, and a run that reaches the file by no in-tree name, through a link outside the root, keeps the finding at the file's own name. A citation direction asked of a declaration is no place finding: the obligation follows the declaration's own kind, so it holds at any spelling and is a content finding ([§FS-scan.identity.findings.content](FS-scan.md#identityfindingscontent-a-content-finding-is-one-line-naming-every-name)).

#### identity.findings.content: A content finding is one line naming every name

A finding about what the file holds, with `notes/link.md -> ../docs/fs/a.md`, is one line at the name listed first, the others in a closing clause, and JSON carries them all in `sites`:

```text
docs/fs/a.md:5: error: unknown reference FS-gone (also at notes/link.md:5)
```

```json
{"severity":"error","path":"docs/fs/a.md","line":5,"code":"dangling","message":"unknown reference FS-gone (also at notes/link.md:5)","sites":[{"path":"docs/fs/a.md","line":5},{"path":"notes/link.md","line":5}],"authority":null}
```

A citation-direction finding about a declaration is one of these, whether the declaration owes a citation or holds one it must not, while the same code about a file stays at its spelling ([§FS-scan.identity.findings.place](FS-scan.md#identityfindingsplace-a-place-finding-is-judged-at-each-spelling)):

```text
docs/fs/a.md:1: error: FS-a must cite GOAL (citation direction); add such a citation within it (also at notes/link.md:1)
```

Whatever else a content finding names is named as the whole run names it. A duplicate's other sites, and the declaration a value mismatch points at, are the first names of those files from every scope, and a literal the author wrote is the author's and stays as written.

Those sites keep the finding in scope ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)), and it names only the spellings the plain run reaches ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)).

#### identity.findings.judged: A finding that resolves from the file's directory names the spelling it was judged at

A finding that resolves a relative path from the file's directory, such as a stub's link, can hold at one spelling and fail at the other. It carries no closing clause and names only the spelling it was judged at, the name listed first. That is the limit [§FS-fmt.2.3.2.2](FS-fmt.md#2322-a-link-inside-the-config-root-is-written-through) names, which stays.

### identity.buffers: A buffer is the file at its physical location

An editor buffer is the file at the physical location its path resolves to, under whatever spelling the editor opened it and whatever spelling a stub or the walk reaches that file by. Where `alias -> notes`, a buffer the editor opened as `notes/a.md` is the text of `alias/a.md`, and one opened as `alias/a.md` is the text of `notes/a.md`, so a stub that writes `../alias/a.md` reads the buffer either way, as it would read the saved file ([§FS-scan.text.buffer](FS-scan.md#textbuffer-a-files-text-is-what-a-save-would-write)). Identity decides which text a spelling reads and what that text is read as ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)), and nothing else: the name a stub wrote is still judged as written ([§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing)), a finding still names the in-tree link path ([§FS-scan.identity.link-path](FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path)), and the file is read once ([§FS-scan.identity.read-once](FS-scan.md#identityread-once-one-physical-file-is-read-once)). Where the run holds a refusal for the file ([§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)), the editor offers no on-type edit in it. Decided in [§DF-a-buffer-is-the-file](../decisions/functional/DF-a-buffer-is-the-file.md#df-a-buffer-is-the-file-an-editor-buffer-is-the-file-it-names-under-every-spelling-and-with-no-file-saved-behind-it).

### identity.unresolved: A path that does not resolve keeps its components, and nothing is appended

A path the filesystem cannot resolve to its end has a spelling all the same: the canonical form of its longest existing prefix, followed by the components that did not resolve, in their order, and by nothing else. That covers a buffer with no file behind it ([§FS-scan.text.buffer-only](FS-scan.md#textbuffer-only-a-buffer-with-no-file-behind-it-is-a-file)), a broken link, and an entry under a directory that cannot be searched. A path whose every component exists but whose canonical form the filesystem will not give keeps its lexical form under the same rule.

So the text ends in the path's last component and never in a separator: `<root>/real/unsaved.md`, not `<root>/real/unsaved.md/`, however many components are missing. A trailing separator says "directory" about a name that may be a file, and a caller reading the path as text would see a path nobody wrote, even though a comparison by component cannot tell the two apart. This binds what a caller is handed: `canonical_snapshot_path`'s return value and the `path` of every finding in an `lsp_snapshot` report.

## text: Which text a file has

Every reader in a run reads one text per file, the one a save would write. The command line holds no buffers, so for it that text is the disk; an editor hands its run the buffers it holds open, and each one is the file it names ([§FS-scan.identity.buffers](FS-scan.md#identitybuffers-a-buffer-is-the-file-at-its-physical-location)).

### text.buffer: A file's text is what a save would write

A file's text is what saving it would write: the editor's open buffer where there is one, and the disk only where there is none. That holds for every reader a run has, the walk's scan of each file, a stub's target ([§FS-declarations.stubs.target.1](FS-declarations.md#stubstarget1-the-target-is-read-as-a-save-would-write-it)) and the body `show` slices out of it ([§FS-show.2.3.7](FS-show.md#237-a-stubs-target-is-found-by-its-id)) among them, so an unsaved edit moves every answer at once, exactly as saving it would ([§REQ-one-answer.text.targets](../requirements/REQ-one-answer.md#texttargets-a-stubs-target-answers-as-its-saved-text-would)).

### text.buffer-only: A buffer with no file behind it is a file

A buffer with no file on disk behind it, a new file the editor has not saved, is a file of the run. It exists for a stub, so a stub to it is never `stub link target missing` and is judged on the buffer's text ([§FS-declarations.stubs.target.1](FS-declarations.md#stubstarget1-the-target-is-read-as-a-save-would-write-it)). The walk reads it or skips it by the rules of [§FS-scan.scope](FS-scan.md#scope-which-files-a-run-reads) exactly as it would the saved file: `include` and the kind homes bring it in, and a hidden name, an unlisted extension, `exclude`, an ignore file of any form [§FS-scan.scope.ignore-files](FS-scan.md#scopeignore-files-respect_gitignore--the-ignore-files) names, a `scan = false` home and another project's root keep it out. Where the editor holds a buffer for a file the walk skips, the walk's rule wins: the buffer is the file, and the file is not read. A stub's target outside `include` is read as if it were scanned ([§FS-show.2.3.7](FS-show.md#237-a-stubs-target-is-found-by-its-id)), a buffer as much as a saved file, and only by the name and extension rules of [§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing).

## checks: Checks

### checks.reading-conflict: Two names of one file read it differently

Two in-tree names of a file whose own name claims no reading, or whose own name lies outside the config root, that read it differently leave nothing to decide by ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)). The run refuses the file, with code `reading-conflict`, one finding, located at the name listed first:

```text
docs/license.md:1: error: docs/license.md and docs/license.rs are one file that reads two ways, as markdown and as rust; keep one name, or give the file a name that claims a reading
```

The readings are named in the names' order, and the name of a reading is its language's under version 2. Under version 1 it is the extension, `markdown` for `md`, and `source with no extension` for a name with none. Two names of one language, or a name and a file whose own name claims a reading, are no conflict.

JSON `sites` names both spellings, each once, and the finding is in scope at either ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)), so a whole run and a run naming either spelling print the same line. The names judged are those [§FS-scan.identity.reading.plain](FS-scan.md#identityreadingplain-a-name-only---full-or-a-handed-path-reaches-decides-nothing) gives a say: a name only `--full` or a handed path reaches refuses nothing, and where the plain run reaches no name the line stands in the out-of-scope tier. The file is read under neither name, because reading it under both would duplicate its declarations against themselves, so a citation elsewhere to what it declares is also reported as `unknown reference`.

Neither selection axis hides it ([§FS-check.2.1.2](FS-check.md#212-selection-filters-the-complete-report)), and it contributes exit `1`. `fmt` leaves the file alone ([§FS-fmt.2.3.2.3](FS-fmt.md#2323-a-file-two-names-read-differently-is-not-written)). Decided in [§DF-one-file-one-reading](../decisions/functional/DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name).

### checks.reading-moved: A link is read as its target's own name reads

A link whose reading moved under [§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it) earns one warning with code `reading-moved`. A reading moved where the name listed first is a link, and the reading of that name differs from what the file is now read as. That name is the one that decided the file before grund 0.22.0, so a link listed after its target earns nothing, and a file earns at most one. The names listed are those [§FS-scan.identity.reading.plain](FS-scan.md#identityreadingplain-a-name-only---full-or-a-handed-path-reaches-decides-nothing) gives a say, as for a refusal:

```text
docs/fs/gen.md:1: warning: read as rust, as its target's own name reads, not as markdown (since 0.22.0); rename the target or copy the file
```

The name of a reading is the one [§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently) gives. It leaves the exit code alone and stands in place of the `success` line. `--only reading-moved` and `--ignore reading-moved` select it by the ordinary rules ([§FS-check.1.4](FS-check.md#14-selecting-findings-with---only-and---ignore)). It is what makes a declaration that drops out of a green tree a located finding, which is the finding [§DF-one-file-one-reading](../decisions/functional/DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name) owes.

#### checks.reading-moved.1: A warning in 0.22.x, and gone in 0.23.0

The warning stands for one minor release. grund 0.23.0 removes it: from there the code is spent, as the catalog says of a spent code, and the rule of [§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it) stands alone.

### checks.unread-scan-root: A configured file root is not read

A scan root that is a single file — a `[[kinds]]` `file` home, a version-2 `files` entry, or an `[scan] include` entry naming a file — whose name is hidden ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)), or whose extension the extension list leaves out ([§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)). A root refused by both rules earns one warning, not two ([§DF-unread-hidden-root](../decisions/functional/DF-unread-hidden-root.md#df-unread-hidden-root-a-configured-file-root-with-a-hidden-name-is-named-not-read)). Nothing in the file was read: no declaration in it reached a catalog and no citation in it was resolved or reported, so the configuration names a file to check and the run checks none of it. Saying so is this finding's whole job ([§REQ-no-missed-citation.1](../requirements/REQ-no-missed-citation.md#1-no-silent-skips)).

It is one located warning per unread root, at the line of the row that made the file a root ([§FS-scan.checks.unread-scan-root.location](FS-scan.md#checksunread-scan-rootlocation-one-warning-per-unread-root-at-its-rows-line)), in the exact bytes of [§FS-scan.checks.unread-scan-root.message](FS-scan.md#checksunread-scan-rootmessage-the-message). Some roots earn nothing ([§FS-scan.checks.unread-scan-root.silent](FS-scan.md#checksunread-scan-rootsilent-what-stays-silent)). It is printed on stdout and moves no exit code ([§FS-scan.checks.unread-scan-root.channel](FS-scan.md#checksunread-scan-rootchannel-a-located-finding-on-stdout-and-the-exit-code-does-not-move)), it is asked of the configured scope by `check` alone ([§FS-scan.checks.unread-scan-root.scope](FS-scan.md#checksunread-scan-rootscope-asked-of-the-configured-scope-by-check-alone)), its JSON form is [§FS-scan.checks.unread-scan-root.json](FS-scan.md#checksunread-scan-rootjson-its-json-form-is-on-stdout), and it stands in place of the empty-scan caution ([§FS-scan.checks.unread-scan-root.empty-scan](FS-scan.md#checksunread-scan-rootempty-scan-it-stands-in-place-of-the-empty-scan-caution)).

- **Code:** `unread-scan-root` ([§FS-errors.5.5](FS-errors.md#55-the-check-code-catalog)).

#### checks.unread-scan-root.location: One warning per unread root, at its row's line

One warning per unread root, located in the `grund.toml` that configured it, at the line of the key that named the file: the `file` key of its `[[kinds]]` row, the `files` key of its version-2 row, or the `[scan] include` key. Two entries of one `include` array share that line and sort by message ([§FS-errors.4](FS-errors.md#4-determinism)). The path is spelled as every located finding in that config spells it ([§FS-cli.3.4](FS-cli.md#34---path-base--where-report-paths-are-spelled-from)).

#### checks.unread-scan-root.message: The message

The message is `<row> is not read — <reason>, so nothing in it is checked. <fix>.` The row names the file as the configuration wrote it:

| Root | `<row>` |
|---|---|
| a `[[kinds]]` `file` home | ``[[kinds]] <KIND> home `<file>` `` |
| an `[scan] include` entry | ``[scan] include entry `<entry>` `` |
| a version-2 `files` entry | ``[schema.kinds.<KIND>] file `<file>` `` |

For a root whose name is not hidden, the reason names the extension as the file name spells it, the part after the last `.`, or says there is none:

| Configuration | The file has an extension | The file has none |
|---|---|---|
| version 1 | `extension <ext> is not in [scan] extensions` | `it has no extension, and [scan] extensions reads a file only by its extension` |
| version 2 | ``no language in [schema.sources] languages reads `.<ext>` `` | `it has no extension, and [schema.sources] languages reads a file only by its extension` |

This table is the one wording of why a name is not read. The warning and the broken-stub line of [§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing) both say its cell for the configuration and the name, and a name ending in `.` has no extension.

The fix is the one edit that makes the row say what it means. Listing the extension is offered only where there is one to list, so a file with none is never told to add it:

| Root | The file has an extension | The file has none |
|---|---|---|
| a version-1 `[[kinds]]` home | `Add "<ext>" to [scan] extensions, or give the file an extension the list holds` | `Rename the file to an extension the list holds` |
| an `[scan] include` entry | `Add "<ext>" to [scan] extensions, or drop the entry` | `Rename the file to an extension the list holds, or drop the entry` |
| a version-2 `files` entry | `Give the file an extension a listed language reads` | `Give the file an extension a listed language reads` |

For a root whose name begins with `.`, the reason says so first, and names the extension as well where the list refuses it too, so one warning names every rule that keeps the file out:

| The hidden file | Reason |
|---|---|
| has an extension the list holds, or has none and the list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)) | `` its name begins with `.`, and grund reads no hidden file `` |
| has one it does not, version 1 | ``its name begins with `.`, and extension <ext> is not in [scan] extensions`` |
| has one it does not, version 2 | ``its name begins with `.`, and no language in [schema.sources] languages reads `.<ext>` `` |
| has none, such as `.notes`, and the list does not hold the empty string | `` its name begins with `.`, and it has no extension `` |

Its fix is one edit, the rename, and it names everything the new name must satisfy, because renaming the file alone would leave the extension refusal standing and listing the extension alone changes nothing:

| Root | Only the name refuses it | The list refuses it too, whether it has an extension or none |
|---|---|---|
| a version-1 `[[kinds]]` home | `Rename the file to a name that is not hidden` | `Rename the file to a name that is not hidden and an extension the list holds` |
| an `[scan] include` entry | `Rename the file to a name that is not hidden, or drop the entry` | `Rename the file to a name that is not hidden and an extension the list holds, or drop the entry` |
| a version-2 `files` entry | `Rename the file to a name that is not hidden` | `Rename the file to a name that is not hidden and an extension a listed language reads` |

A home on a row with `citable = false` may name the file only as a place in the Project map, so its fix also offers the key that says so ([§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned)): the last `, or` of the version-1 fix becomes `,`, and the fix ends ``, or set `scan = false` on the row if it only lists a place``. A version-2 row's single fix, and a hidden home's single rename, gain the same ending. So, for one root of each shape:

```
grund.toml:10: warning: [[kinds]] TXT home `notes.txt` is not read — extension txt is not in [scan] extensions, so nothing in it is checked. Add "txt" to [scan] extensions, or give the file an extension the list holds.
grund.toml:9: warning: [scan] include entry `extra.txt` is not read — extension txt is not in [scan] extensions, so nothing in it is checked. Add "txt" to [scan] extensions, or drop the entry.
grund.toml:7: warning: [[kinds]] NOTES home `NOTES` is not read — it has no extension, and [scan] extensions reads a file only by its extension, so nothing in it is checked. Rename the file to an extension the list holds, or set `scan = false` on the row if it only lists a place.
grund.toml:8: warning: [schema.kinds.TXT] file `notes.txt` is not read — no language in [schema.sources] languages reads `.txt`, so nothing in it is checked. Give the file an extension a listed language reads.
```

#### checks.unread-scan-root.silent: What stays silent

A row marked `scan = false` is not a root and earns nothing ([§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned)), and neither does a home or entry that does not exist ([§FS-scan.scope.homes](FS-scan.md#scopehomes-every-configured-kind-home-is-scanned)). A hidden file *inside* a directory root earns nothing: nothing in the configuration named it, and a directory is filtered file by file; a hidden home that does not exist earns nothing either. A value row's home that is a value source ([§FS-values.terms](FS-values.md#terms-terms)), of either format, is read by the value pass whatever the list says ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)), so it earns nothing either. A directory root is filtered file by file, which is what the extension list means; a directory whose files are all unlisted earns nothing here, and the empty-scan caution still speaks when the run read nothing at all ([§FS-check.2.2](FS-check.md#22-empty-scan)).

#### checks.unread-scan-root.channel: A located finding on stdout, and the exit code does not move

It is a warning, so the exit code stays `0` and `success` is withheld ([§FS-check.2.1.3](FS-check.md#213-the-success-line)), and like [§FS-check.4.9](FS-check.md#49-a-workspace-member-declared-optional-is-absent) it is a located finding on stdout rather than a CLI-level caution ([§FS-check.4.9.4](FS-check.md#494-a-located-finding-on-stdout-not-a-cli-level-caution)): a statement about the coverage of a report belongs in the report. It is not an error, because nothing the run read is wrong; what is at stake is only how much the verdict covers. It names no release and stays a warning, like [§FS-check.4.9.6](FS-check.md#496-it-names-no-release): a row that names a file a name rule keeps out is a configuration that says two things, and the edit that makes it say one is the repository's to choose. `--ignore unread-scan-root` and `--only` select it like any code ([§FS-check.2.1.2](FS-check.md#212-selection-filters-the-complete-report)).

#### checks.unread-scan-root.scope: Asked of the configured scope, by `check` alone

Every `check` run that loads the configuration asks it of every configured file root, `--full` included: `--full` keeps the configured roots ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)), so it prints the same warnings and no finding from inside the file, which it does not read either. A run given an explicit path reports it only where the path covers the `grund.toml` that holds the row, like any located finding ([§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports)); `grund check notes.txt` keeps the caution of [§FS-check.2.2.2.2](FS-check.md#2222-an-explicit-path) instead, and `grund check docs/.notes.md` that of [§FS-check.2.2.2.3](FS-check.md#2223-a-hidden-file): a path typed on the command line has no row behind it. In a workspace each project is asked on its own, and the warning is located in that project's own `grund.toml`. `list`, `refs`, `show`, `cover` and `fmt` read the same files and do not say it ([§DF-unread-scan-root.2.1](../decisions/functional/DF-unread-scan-root.md#21-check-alone-says-it)).

#### checks.unread-scan-root.json: Its JSON form is on stdout

Under `--format=json` it is one warning finding on stdout with `path` and `line` set and `sites` null, like every other located finding ([§FS-errors.5](FS-errors.md#5-json-format)), carrying the message of [§FS-scan.checks.unread-scan-root.message](FS-scan.md#checksunread-scan-rootmessage-the-message) byte for byte.

#### checks.unread-scan-root.empty-scan: It stands in place of the empty-scan caution

It is a finding about the default scope, so where the unread root was the only thing the run would have read, it suppresses the generic empty-scan caution ([§FS-check.2.2.3](FS-check.md#223-exit-code-json-and-what-suppresses-it)) and the run's stderr is empty. That caution points at `include` and `grund init --scaffold`, the wrong fix for a file the configuration already names; this warning names the row and the edit.
