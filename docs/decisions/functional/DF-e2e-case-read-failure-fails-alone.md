# DF-e2e-case-read-failure-fails-alone: a failure reading one E2E case is that case's alone, and path-scoped exits move with it in both directions

**Date:** 2026-11-05

## status: Accepted

## 1. Context

The walk over the E2E cases returned at its first failure, so one case it could not read ended the walk: a manifest that could not be read or decoded, an `expected.exit` that did not parse, or fixtures that could not be listed. Every case sorted after that one went unread, though nothing was wrong with it. A correct citation of one was reported as `unknown reference`, with `did you mean` offering a different case; its findings went unreported, and `grund list` left it out. Reported as [issue #1256](https://github.com/agent-grounds/grund/issues/1256). [§FS-check.2.4](../../functional-spec/FS-check.md#24-an-incomplete-run) already promised otherwise for a failure during the scan: "the scan continues over the remaining files".

For a whole-project run that is a defect with no verdict in it: `grund check` and `grund list` exit `2` before and after. This record exists for the runs narrowed to a path. A path scope reads what its project's ordinary run reads and reports only the path ([§FS-check.1.3.6.1](../../functional-spec/FS-check.md#1361-a-path-scope-narrows-the-report-not-the-resolution)), so a case the walk never reached was missing from the narrowed run too, and reading it moves that run's exit.

## 2. Decision

A failure reading one case is that case's alone ([§FS-declarations.e2e-case.failure](../../functional-spec/FS-declarations.md#e2e-casefailure-a-case-that-cannot-be-read-fails-alone)): every other case is read wherever it sorts, and each failing case is reported.

### 2.1 Exits move in both directions

Measured on the ticket's tree: cases `a` and `c` healthy, `b` holding the bytes `ff fe` in `expected.exit`, and `notes.md` citing `E2E-a` and `E2E-c`. "Before" is `grund 0.21.0`. Every run below also prints the [§FS-check.1.3.6.3](../../functional-spec/FS-check.md#1363-a-file-the-wider-walk-could-not-read-is-said-out-loud) caution, on both builds: `warning: e2e/cases: stream did not contain valid UTF-8 — outside the report scope, so a citation declared there may be reported as unresolved`.

| Run | Before | Now |
|---|---|---|
| `grund check e2e/cases/c` | `warning: nothing to scan — …`, exit `0` | `e2e/cases/c:1: error: E2E-c is not listed in e2e/cases/README.md …`, exit `1` |
| `grund check notes.md` | `notes.md:3: error: unknown reference E2E-c; did you mean E2E-a?`, exit `1` | nothing further, exit `0` |

The same tree, changed as the first column says, moves these as well, and none of these paths names a single case:

| What changes | Run | Before | Now |
|---|---|---|---|
| `twin.md` declares `E2E-c` as well | `grund check twin.md` | nothing further, exit `0` | `e2e/cases/c:1: error: duplicate declaration of E2E-c (also declared at twin.md:1)`, exit `1` |
| Under `shorthand = "accepted"` and `id_format = "{kind}-{number}-{slug}"`, cases `001-a`, `001-m` (the bad one) and `001-z`, and `n.md` whose only citation is the number `001` | `grund check n.md` | nothing further, exit `0` | `n.md:3: error: shorthand citation … is ambiguous: E2E-001-a, E2E-001-z; write the full ID it means`, exit `1` |
| Under the same config, cases `001-a`, `002-m` (the bad one) and `003-z`, and `n.md` whose only citation is the number `003` | `grund check n.md` | `n.md:3: error: shorthand citation … matches no declaration; write the full ID it means`, exit `1` | nothing further, exit `0` |
| With `FS` and `RULE` kinds configured, a rule declaration `RULE-c` the index lists, titled `E2E-c must be cited by at least one FS.` | `grund check rules/RULE-c.md` | `rules/RULE-c.md:1: error: RULE-c is not a valid rule: literal subject E2E-c does not resolve`, exit `1` | only the `declared but never cited` warning both builds print, exit `0` |
| With an `FS` kind configured and `notes.md` citing only `E2E-a`, the same sentence on the command line | `grund check notes.md --rule "E2E-c must be cited by at least one FS."` | `error: --rule is not a valid rule: literal subject E2E-c does not resolve`, exit `1` | nothing further, exit `0` |
| `src/x.rs`, whose only citation is `E2E-c` | `grund check src/x.rs --require-grounding` | `unknown reference E2E-c` and `ungrounded source file`, exit `1` | nothing further, exit `0` |
| `[schema.kinds.E2E] folders = ["tests/cases"]`, the cases under it, and an index listing only `E2E-a` | `grund check tests/cases` | nothing further, exit `0` | `tests/cases/c:1: error: E2E-c is not listed in tests/cases/README.md …`, exit `1` |

These tables are measured on this change alone. [§DF-e2e-case-failure-at-the-file](DF-e2e-case-failure-at-the-file.md#df-e2e-case-failure-at-the-file-a-failure-reading-an-e2e-case-is-located-at-the-file-that-failed-and-path-scoped-exits-move-with-it-in-both-directions), in the same release, moves the failure to the file that failed, so the caution names `e2e/cases/b/expected.exit` rather than `e2e/cases`, and a run whose path holds that file exits `2`: the last row's `grund check tests/cases` is one, and exits `2` in the release.

In general, reading a case sorted after a bad one gives a path-scoped run the answers a tree with no bad case gives about that case's ID. From `0` to `1`: a run whose path holds such a case, but not the file that failed, when that case has a finding of its own; a run naming a file that declares the same ID, on the duplicate; and, under `shorthand = "accepted"`, a run citing a number-only shorthand such a case makes ambiguous. From `1` to `0`: a run whose only errors said such a case's ID does not resolve, as `unknown reference`, as `shorthand citation … matches no declaration`, or as an `invalid-rule` line saying `literal subject … does not resolve`, together with the `ungrounded source file` that follows from those citations. A hook or CI step narrowed to paths notices, over a tree holding a bad case. That the whole run already fails does not take these out of the guarantee: a narrowed run's exit is a verdict of its own, as [§DF-narrowed-check-judged-nothing.3](DF-narrowed-check-judged-nothing.md#3-consequences) and [§DF-path-scope-resolves-project-wide.2.3](DF-path-scope-resolves-project-wide.md#23-the-verdict-moves-in-both-directions-and-the-added-finding-is-correct) ruled.

### 2.2 The whole-project run moves in bytes only

`grund check` and `grund list` exit `2` on both builds. The false `unknown reference` goes, later cases' findings print and `grund list` names them. A second failing case gets its own `error:` line, its own `io` entry under `check --format json`, and on a path-scoped run its own caution. A language binding's `show` fails with a structured failure that lists every one under `details.scan_errors`; `grund show` on the command line prints the first alone, under `--format json` too.

### 2.3 What does not move

- `grund check e2e/cases/b`, the scope naming the bad case, exits `0` on both builds and calls the failure outside the report scope, though the failing file is under the path. That is a defect of its own, which this change does not repair, because the failure is still located at the cases root. [§DF-e2e-case-failure-at-the-file](DF-e2e-case-failure-at-the-file.md#df-e2e-case-failure-at-the-file-a-failure-reading-an-e2e-case-is-located-at-the-file-that-failed-and-path-scoped-exits-move-with-it-in-both-directions) repairs it.
- A citation of the failing case itself keeps its `unknown reference`, which [§FS-declarations.e2e-case.failure](../../functional-spec/FS-declarations.md#e2e-casefailure-a-case-that-cannot-be-read-fails-alone) leaves unspecified. So does a citation of a case that does not exist, which `check-e2e-case-undecodable-unknown-reference-stays` pins, as `check-unreadable-file-continues`, `symlink-loop` and `symlink-loop-above-root` pin it for a citation of any ID that points at nothing. This is why the repair reads the later cases rather than silencing `unknown reference` beside a scan failure.
- `grund show` and `grund id` stay strict: on a tree whose scan failed they print a failure and exit `2`, so `grund show` cannot read a healthy case until the bad one is repaired.

## 3. The correction route

These exits flip a shipped verdict, which [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered) allows only by a named route. [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids) is the route, and all five conditions hold.

1. *Prior prohibition.* The old exit `1` violated [§REQ-no-wrong-citation.2](../../requirements/REQ-no-wrong-citation.md#2-no-false-alarms): `grund check notes.md` reported a citation that resolves and is written in canonical form as broken, and told its reader to rewrite it. `E2E-c` does resolve: its case directory is intact, and repairing the bad manifest, or moving the same bytes into an ordinary `bad.md`, resolves it with nothing about the case changed. The old exit `0` violated [§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips): `grund check e2e/cases/c` had not read the one case it was asked about and still passed, where an incomplete report "never passes as if it were". The old exit `0` of a run naming a file that declares a later case's ID, or citing a shorthand such a case makes ambiguous, violated [§REQ-no-wrong-citation.1](../../requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution): duplicate declarations are reported rather than ranked and ambiguity is an error, while `grund 0.21.0` lists the twin as `E2E-c` and reads the number `001` as `E2E-001-a`. The other exits that go from `1` to `0` are [§REQ-no-wrong-citation.2](../../requirements/REQ-no-wrong-citation.md#2-no-false-alarms)'s false alarm in other words: `matches no declaration` says it of a citation that resolves, `ungrounded source file` follows from the false `unknown reference` as [§FS-check.1.3.6.1](../../functional-spec/FS-check.md#1361-a-path-scope-narrows-the-report-not-the-resolution) says of its own case, and `literal subject E2E-c does not resolve` says it of a declaration that exists. Each of those sections belongs to a separately declared hard requirement, in every release since `v0.10.1`, and the project-wide read that produces these exits first shipped in `v0.15.0`, so each prohibition already applied when the old verdict shipped.
2. *Accepted proof.* This record, which cites those sections and proves the conflict above. [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path)'s deprecation path does not fit, because there is no old form to carry beside a new one: only a wrong answer, which nothing a user writes selects. [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations)'s mechanical migration does not fit either, because nothing a user wrote is at fault for the move, so there is no command to run on anyone's behalf.
3. *Named release.* The release note below names each of these exits, who notices and what to do.
4. *Actionable findings.* Where `0` becomes `1`, what replaces the old verdict is the later case's own finding, the one it earns once the bad manifest is repaired, located at the case and naming the action: `e2e/cases/c:1`, and the entry to write in the index. On a duplicate it is the error naming both declaration sites, the pair a maintainer has to choose between; on a shorthand it is the error at the citation, listing the candidates and saying to write the full ID. Where `1` becomes `0`, nothing replaces it: the false line goes, and the caution both builds print stays. The failure line prints on both builds and replaces nothing, so it is not the finding this condition asks about; [§DF-e2e-case-failure-at-the-file](DF-e2e-case-failure-at-the-file.md#df-e2e-case-failure-at-the-file-a-failure-reading-an-e2e-case-is-located-at-the-file-that-failed-and-path-scoped-exits-move-with-it-in-both-directions) moves it to the file that failed.
5. *No new licence.* This route cannot justify ordinary policy tightening, feature removal, or a prohibition invented by this change, and it is used for none of them: no check, rule or code changes, and a later case earns only what it earns on a tree where no case is bad.

**The weak point.** The old run did print a warning, and that is the objection to each prohibition.

For the exit `1`, [§REQ-no-wrong-citation.2](../../requirements/REQ-no-wrong-citation.md#2-no-false-alarms) excuses a finding the spec knowingly scopes if it stays legible as such, [§FS-check.1.3.6.3](../../functional-spec/FS-check.md#1363-a-file-the-wider-walk-could-not-read-is-said-out-loud) says the citation whose declaration lay in an unread file is reported as unresolved, and the caution said of `e2e/cases`, under which `E2E-c` lies, that a citation declared there may be reported as unresolved. But that point scopes a declaration that lay in the file that failed, and `E2E-c` lay in a directory no failure touched; the caution reaches it only because it locates the failure at the cases root. And the line is not legible as a statement about a scope: `did you mean E2E-a?` asks for a correct citation to become a citation of a different test, the reading [§DF-path-scope-resolves-project-wide.1](DF-path-scope-resolves-project-wide.md#1-context) gave `unknown reference FS-widget`. A rule's literal subject is not a citation on the page, so [§REQ-no-wrong-citation.2](../../requirements/REQ-no-wrong-citation.md#2-no-false-alarms) reaches that line by its reason rather than its words: a checker that reports a declaration that exists as missing cries wolf under any code.

For the exit `0` the ground is narrower. [§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips) opens on a file the scan cannot read, and nothing in case `c` is unreadable: what failed is in `b`, and [§FS-check.1.3.6.3](../../functional-spec/FS-check.md#1363-a-file-the-wider-walk-could-not-read-is-said-out-loud) rightly keeps that out of this run's exit code. Nor was the run silent, and both its warnings were true: `nothing to scan` is what a clean case prints too, read or not, because a case directory holds no file the walk recognizes. The exit rests on the clause that a report which is not complete "never passes as if it were", and on [§FS-check.1.3.6.3](../../functional-spec/FS-check.md#1363-a-file-the-wider-walk-could-not-read-is-said-out-loud)'s own reason for leaving the exit alone, that a run whose report is the path "is complete about the path". This run was not: it was asked about one case and never read it, and its lines could not say so. On `grund 0.21.0` a case with a finding of its own and a case with none print the same two warnings and exit `0`, so a reader could not tell a case passed over from a clean one. An objector can still hold that a warning is enough, and this record refuses that position rather than disproving it. No narrower fix would satisfy them: once the walk reads `c` its finding is a finding under the path, and keeping the old `0` would take a rule that hides a case's findings from a run narrowed to it because a sibling failed.

## release-note: Release note

- [§FS-declarations.e2e-case.failure](../../functional-spec/FS-declarations.md#e2e-casefailure-a-case-that-cannot-be-read-fails-alone), [§DF-e2e-case-read-failure-fails-alone](DF-e2e-case-read-failure-fails-alone.md#df-e2e-case-read-failure-fails-alone-a-failure-reading-one-e2e-case-is-that-cases-alone-and-path-scoped-exits-move-with-it-in-both-directions), [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids): **a failure reading one E2E case is that case's alone, so path-scoped exits move in both directions.** A `command.args`, `expected.exit` or `spec.refs` that cannot be read or decoded, an `expected.exit` that does not parse, or fixtures that cannot be listed no longer end the walk over the cases: every other case is read wherever it sorts, and each failing case is reported. A run narrowed to a path now gets the answers a tree with no bad case gives about those cases' IDs. **Exits move from `0` to `1`:** `grund check <path>` fails where its path holds a case sorted after a bad one, but not the file that failed, and that case has a finding of its own; where it names a file declaring the same ID as such a case, on `duplicate declaration`; and, under `shorthand = "accepted"`, where such a case makes a number-only citation ambiguous. Each passed without reading the case: do what the finding says. **Exits move from `1` to `0`:** `grund check <path>` whose only errors said such a case's ID does not resolve now passes, whether they read `unknown reference`, `shorthand citation … matches no declaration` or, for a rule naming the case, `literal subject … does not resolve`, along with the `ungrounded source file` that follows from those citations. Those citations and rules were correct: leave them alone, and repair the bad case to clear the warning that still stands in place of `success`. **Who notices:** a hook or CI step narrowed to paths in a tree holding a bad case, and a script reading a whole-project report, which still exits `2` but now carries later cases' findings and IDs, and one `error:` line, and under `check --format json` one `io` entry, per failing case. The verdict moves by the correction route of [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids), because the old exit `1` broke [§REQ-no-wrong-citation.2](../../requirements/REQ-no-wrong-citation.md#2-no-false-alarms) and the old exit `0` broke [§REQ-no-missed-citation.1](../../requirements/REQ-no-missed-citation.md#1-no-silent-skips) or, for a duplicate or an ambiguous shorthand, [§REQ-no-wrong-citation.1](../../requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution); every finding that replaces it names its location and the action to take. Closes [issue #1256](https://github.com/agent-grounds/grund/issues/1256).
