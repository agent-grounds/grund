# DF-outward-place-refused-when-denied: a version 2 folder place that links out of the project is refused whether or not its target can be looked up, and exits move with it

**Date:** 2026-11-10

## status: Accepted

## 1. Context

Under a version 2 config, config load refuses a kind's folder place that is a directory link leaving the project root ([§FS-config-v2.schema.places.boundaries.3](../../functional-spec/FS-config-v2.md#schemaplacesboundaries3-decided-on-the-path-as-written)). It judged the link on its canonical target, and refused only when that target could be computed. Where a directory on the way to the target, itself already outside the project, refused the lookup (mode `000`), the place was neither refused nor reported: the walk then pruned it in silence ([§FS-scan.scope.homes.lookup.outward](../../functional-spec/FS-scan.md#scopehomeslookupoutward-a-root-link-leaving-the-project-answers-to-its-gate-first)), the kind the place was home to was not read, and every command exited `0`. The same tree and config exited `2` as soon as that directory's mode let the lookup through. [§DF-home-lookup-failure-fails-at-the-home](DF-home-lookup-failure-fails-at-the-home.md#df-home-lookup-failure-fails-at-the-home-a-root-whose-lookup-fails-for-a-reason-other-than-absence-fails-at-the-root-and-exits-move-with-it) recorded the split as a gap of config load's. Reported as [issue #1332](https://github.com/agent-grounds/grund/issues/1332).

Two verdicts would make the two modes agree: refuse the place in both, or prune it in both. Pruning in both would move the shipped refusal of the open mode, which every release since 0.18.0 has given; refusing in both moves only the run whose answer depended on a mode outside the project.

## 2. Decision

A folder place whose lookup fails for a reason other than absence is judged on where it goes as far as the disk answers, the way the walk already judges a root, and is refused at load when that has left the project root ([§FS-config-v2.schema.places.boundaries.3.1](../../functional-spec/FS-config-v2.md#schemaplacesboundaries31-judged-as-far-as-the-disk-answers)). The refusal is the line the open mode prints.

### 2.1 Exits that move

Measured on one fixture: `[schema.kinds.FS] folders = ["docs"]` holding `FS-a`, `[schema.kinds.CONST] folders = ["vals"]`, `vals` a link to `../ext/par000/t` beside the project, and `chmod 000 ext/par000`, as a non-root user on Linux. "Before" is 0.22.2-dev at 65fbe40245; "Now" is what the open mode prints on that build, which this change makes the denied mode print.

| Config | Run | Before | Now |
|---|---|---|---|
| Version 2, an outward folder place behind a denied directory | `grund check`, `check --full`, `check --format json`, `list`, `cover`, `fmt --check`, `refs FS-a`, `show FS-a`, `config validate` | exit `0`; `check` prints the unused-declaration warning for `FS-a` | ``error: grund.toml:9: place `vals` in `[schema.kinds.CONST] folders` links out of the project root``, exit `2` |
| Version 2, an outward folder place whose target does not exist past the denied directory (`vals` a link to `../ext/par000/missing`) | the same runs | exit `0`; `check` prints the unused-declaration warning for `FS-a` | the same refusal, exit `2` |

### 2.2 What does not move

- The open mode: refused with the same line and exit `2`, before and now.
- A folder place whose lookup answers that it does not exist, a dangling link included wherever it points, is quiet ([§FS-config-v2.schema.places.boundaries.4](../../functional-spec/FS-config-v2.md#schemaplacesboundaries4-a-missing-place-is-quiet)): exit unchanged. A dangling link whose lookup a directory refuses is not in this row: it is the second row of 2.1.
- A folder place linking inside the project behind a denied directory is not refused; its lookup failure is the scan failure at the home ([§FS-scan.scope.homes.lookup](../../functional-spec/FS-scan.md#scopehomeslookup-a-home-that-cannot-be-looked-up-is-a-scan-failure-not-an-absent-home)), exit `2` before and now.
- Two places are one place only when both targets resolve ([§FS-config-v2.schema.places.boundaries.3](../../functional-spec/FS-config-v2.md#schemaplacesboundaries3-decided-on-the-path-as-written)); a partial resolution decides no duplicate.
- Version 1, which has no load-time gate on a home's link: an outward root link is pruned in both modes, exit `0` before and now.

## 3. The correction route

The denied run's exit flips from `0` to `2`, a verdict [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered) lets move only by a named route. [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids) is the route, and all five conditions hold.

1. *Prior prohibition.* The old exit `0` violated [§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation): the tree, the config and the invocation decide the bytes, and "a difference that cannot be traced to one of the three is a bug". Holding all three fixed, the run printed a refusal and exited `2`, or a clean report and exited `0`, by the mode of a directory outside the project. [§FS-scan.scope.homes.lookup.outward](../../functional-spec/FS-scan.md#scopehomeslookupoutward-a-root-link-leaving-the-project-answers-to-its-gate-first) already names such a directory as none of the inputs that decide the run, citing that section. That requirement already applied when the old verdict shipped: it was declared on 2026-08-21, and the refusal it leaves out first shipped in 0.18.0.
2. *Accepted proof.* This record, which cites that section and proves the conflict above. [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path)'s deprecation path does not fit, because nothing a user writes selects the old exit: the config is one the tool already refuses whenever it can look. [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations)'s mechanical migration does not fit either, because no command can rewrite a directory's mode, or a link's target, on anyone's behalf.
3. *Named release.* The release note below names the exits, who notices and what to do.
4. *Actionable findings.* What replaces the old verdict is the refusal the open mode already gives, located at the place's line in `grund.toml` and naming the place, its row and its key, so the entry to change is the one it points at: make the place a directory inside the project, or remove it from the row.
5. *No new licence.* This route cannot justify ordinary policy tightening, feature removal or a prohibition invented by this change, and it is used for none of them: the refusal was already [§FS-config-v2.schema.places.boundaries.3](../../functional-spec/FS-config-v2.md#schemaplacesboundaries3-decided-on-the-path-as-written)'s, and this change adds no check and no message.

**The weak point.** Two readings press on it, and two limits stand beside them. First, [§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation) does not bound the tree at the project root, so an objector can count a link's target, and the modes on the way to it, as part of the tree. The answer is that the open mode refuses this place precisely because its target is not the project's to read, so the verdict cannot then take its answer from what lies out there; [§FS-scan.scope.homes.lookup.outward](../../functional-spec/FS-scan.md#scopehomeslookupoutward-a-root-link-leaving-the-project-answers-to-its-gate-first) already drew the line there. Second, the refusal line names the place but no action in words, which condition 4 asks of the finding; the location is the action here, and rewording a shipped line is a byte change [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered) sends down the deprecation path, so it is not made here. The first limit: a dangling outward link is now split by mode: with the directory on the way open, its lookup answers absence and it stays quiet, exit `0`; with that directory denied, nothing tells a missing target from a present one, so it is refused, exit `2`. The split is inherent in what the disk will say, and it errs toward the refusal the open mode gives a present target, rather than toward the silent pass this record removes; refusing every dangling outward link instead would move the open mode's quiet exit, which this report does not ask. The second: on Windows the canonical root carries the `\\?\` verbatim prefix and the partial resolution does not, so a place inside the project whose lookup is denied may be refused there as linking out rather than reported as the scan failure at the home; the crate has no helper that makes the two like with like, and the fixtures that exercise a denied lookup run on Unix only, so it is recorded rather than changed.

## release-note: Release note

- [§FS-config-v2.schema.places.boundaries.3.1](../../functional-spec/FS-config-v2.md#schemaplacesboundaries31-judged-as-far-as-the-disk-answers), [§DF-outward-place-refused-when-denied](DF-outward-place-refused-when-denied.md#df-outward-place-refused-when-denied-a-version-2-folder-place-that-links-out-of-the-project-is-refused-whether-or-not-its-target-can-be-looked-up-and-exits-move-with-it), [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids): **a version 2 folder place that links out of the project is refused even when a directory on the way to its target cannot be searched.** Such a place already printed ``error: grund.toml:<line>: place `<p>` in `[schema.kinds.<NAME>] folders` links out of the project root`` and exited `2` when its target could be looked up; when a directory outside the project refused the lookup, every command exited `0` and the kind was silently not read. **Exits move to `2`:** from `0` for `grund check`, `check --full`, `list`, `cover`, `fmt --check`, `refs`, `show` and `config validate` on such a config. **Who notices:** a gate on a tree whose folder place links outside the project, run by a user who cannot search a directory on the way. Make the place a directory inside the project, or remove it from the row. The same holds for such a link whose target does not exist past the denied directory, since the lookup cannot say so. A place whose lookup answers that it does not exist, a dangling link included, is still quiet. The verdict moves by the correction route, because the old exit let the mode of a directory outside the project decide the run, which [§REQ-deterministic-output.2](../../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation) forbids. Every finding that replaces the old verdict names its location and the action to take. Closes [issue #1332](https://github.com/agent-grounds/grund/issues/1332).
