# DF-one-file-one-reading: A file reached by two names is read as its own name reads, and judged and reported at each name

**Date:** 2026-11-07

## status: Accepted

## 1. Context

A file and a link to it are one physical file with two names. Which name stood for the file was decided twice, by sort order both times: the walk kept the first-sorted spelling, and the value scan read `paths[0]`. Everything after that followed the surviving name. So renaming a link changed whether a file was Markdown, what `fmt --write` wrote, whether a declaration existed on a green `check`, and whether a misplaced-kind error was printed ([issue #1274](https://github.com/agent-grounds/grund/issues/1274), [issue #1216](https://github.com/agent-grounds/grund/issues/1216), [issue #1248](https://github.com/agent-grounds/grund/issues/1248)). [§FS-scan.requirements.spelling](../../functional-spec/FS-scan.md#requirementsspelling-how-a-tree-is-reached-changes-neither-what-is-read-nor-what-a-finding-names--realized) says how a tree is reached changes neither what is read nor what a finding names.

## 2. Decision

The reading belongs to the physical file and the reported path to the spelling ([§FS-scan.identity.reading](../../functional-spec/FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)). A file inside the config root is read as its own name reads, when that name claims a reading ([§FS-scan.identity.reading.claims](../../functional-spec/FS-scan.md#identityreadingclaims-a-name-claims-a-reading-when-the-configuration-admits-and-reads-that-name)). Any other file keeps the reading of the name that reached it, and an outside name has no say ([§FS-scan.identity.reading.outside](../../functional-spec/FS-scan.md#identityreadingoutside-an-outside-name-has-no-say)). If two in-tree names of such a file read differently, sort order does not come back: the file is refused and both are named ([§FS-scan.checks.reading-conflict](../../functional-spec/FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)). That is the only reader conflict that needs a finding. The names with a say are those the plain run reaches, when it reaches any: a name only `--full` or a handed path reaches decides nothing, so `--full` stays additive ([§FS-scan.identity.reading.plain](../../functional-spec/FS-scan.md#identityreadingplain-a-name-only---full-or-a-handed-path-reaches-decides-nothing), [§FS-check.1.3.2](../../functional-spec/FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)).

Each home rule judges each spelling at its own path, in version 1 and version 2, for text files and value sources alike ([§FS-scan.identity.findings.place](../../functional-spec/FS-scan.md#identityfindingsplace-a-place-finding-is-judged-at-each-spelling)). A content finding is one line naming each spelling once, and a line names only what the plain run reaches ([§FS-scan.identity.findings.content](../../functional-spec/FS-scan.md#identityfindingscontent-a-content-finding-is-one-line-naming-every-name)). The same behaviour lives in one place under one name: the table of spellings is `sources`' and the rule is `config`'s ([§AR-scanner.1.8](../../architecture/AR-scanner.md#18-one-physical-file-is-read-once), [§AR-config.1.6](../../architecture/AR-config.md#16-a-files-reading-is-asked-through-one-rule)).

## 3. Alternatives

- **Report every two-name file as a conflict.** Renaming a link would then fail trees where the file's own name already says what it is, and [§FS-scan.requirements.spelling](../../functional-spec/FS-scan.md#requirementsspelling-how-a-tree-is-reached-changes-neither-what-is-read-nor-what-a-finding-names--realized) already makes the split between the reading and the path, so it needs no such finding.
- **Keep first-sorted and say so.** That point would then have to answer for [§FS-scan.requirements.spelling](../../functional-spec/FS-scan.md#requirementsspelling-how-a-tree-is-reached-changes-neither-what-is-read-nor-what-a-finding-names--realized), and a name's sort order would still decide whether a declaration exists.
- **Let a whole run and a narrow run differ for a file whose own name claims nothing.** This rested on the cost of a walk the narrow run does not make. Such a link is rare, and the difference would let `fmt docs/license.rs --write` rewrite a file another name reads as Markdown, so a narrow `fmt`, `cover` or `refs` run does one project walk instead ([§FS-scan.identity.reading.every-caller](../../functional-spec/FS-scan.md#identityreadingevery-caller-every-run-and-every-reader-gets-the-one-answer)).
- **Judge every name the run met.** A file the plain run reads as Markdown would then be refused under `check --full` because of a name only `--full` reaches, which is the wider scan hiding what the plain run found ([§FS-check.1.3.2](../../functional-spec/FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)), and `check other/license.rs` would disagree with `check`.
- **Keep a list of files on every declaration and citation.** It changes every reader to serve a rare case. One table on `Run.spellings`, which the catalog reads and does not copy, costs the common tree nothing.

## 4. The bytes of existing findings

Four byte changes come with no verdict change: the `(also at …)` clause and JSON `sites` on a content finding; a citation-direction finding about a declaration, which printed one line at the spelling a run met first and is now a content finding, with that clause and those sites in a whole run ([§FS-scan.identity.findings.content](../../functional-spec/FS-scan.md#identityfindingscontent-a-content-finding-is-one-line-naming-every-name)); `check notes/link.md`, which printed `notes/link.md:5` and now prints the whole run's line ([§FS-check.1.3.6.2](../../functional-spec/FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)); and the editor's report, whose finding at a file with a second name named the file's physical path and now names the spelling, so its diagnostic reaches an open link. They strain [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered). They are taken under the pre-release licence of [§REQ-backwards-compatibility.4](../../requirements/REQ-backwards-compatibility.md#4-what-was-never-a-promise): an alias would mean printing both shapes of a line for a release, which costs more than the rename in a report whose line-for-line agreement across scopes is the point ([§REQ-one-answer.scope.narrowed](../../requirements/REQ-one-answer.md#scopenarrowed-a-narrowed-run-answers-as-the-whole-run-does), [§REQ-one-answer.text.parity](../../requirements/REQ-one-answer.md#textparity-the-editor-answers-as-the-command-line-does)). `list`, `show` and `refs` naming a path keep the bytes grund 0.21.0 printed, the name handed first ([§FS-scan.identity.link-path](../../functional-spec/FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path)).

## 5. The correction route

This change takes [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids) for the verdicts it moves.

- **Prior prohibition.** The old verdict violated [§REQ-no-data-loss.2](../../requirements/REQ-no-data-loss.md#2-writers-touch-only-what-they-own), which requires that `fmt --write` touch only the citation tokens it names and no other byte. With `build/` ignored and `docs/fs/gen.md -> ../../build/gen.rs`, the old reading rewrote `x = "<§>FS-a"` in the Rust file's string literal. The requirement already applied when the old verdict shipped in grund 0.21.0, because [§FS-fmt.2.3](../../functional-spec/FS-fmt.md#23-what-is-never-rewritten) has always bound the writer to the tokens of the file as it is.
- **Accepted proof.** This record shows the conflict above. [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path) does not fit, because a deprecation window would keep rewriting those bytes for one more release. [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations) does not fit either, because there is no one command that migrates a tree: which name a file should bear is the maintainer's call.
- **Named release.** The release note below names the verdict change.
- **Actionable findings.** Every finding that replaces the old verdict names its location and the action. A refusal names both spellings and says to keep one name or give the file a name that claims a reading ([§FS-scan.checks.reading-conflict](../../functional-spec/FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)). A home error is located at the spelling and is the existing message. A declaration that drops out of a green tree would have had no finding at all, so [§FS-scan.checks.reading-moved](../../functional-spec/FS-scan.md#checksreading-moved-a-link-is-read-as-its-targets-own-name-reads) is the finding condition 4 asks for: a warning for one release at each link whose reading moved, naming the link and the action, removed in grund 0.23.0 ([§FS-scan.checks.reading-moved.1](../../functional-spec/FS-scan.md#checksreading-moved1-a-warning-in-022x-and-gone-in-0230)).
- **No new licence.** This route cannot justify ordinary policy tightening or feature removal. The verdict moves only for a repository with a link in it, and only where the name that sorted first was deciding what a file means.

Who breaks, all of them repositories with a link in them:

- **Reading moves.** A link whose target's own name reads differently, including `txt = "rust"` where a link's extension used to speak for the target. With `build/` ignored, `docs/fs/gen.md -> ../../build/gen.rs` now reads as Rust: a declaration it held is gone, and a citation to it goes red. Where nothing cites it the tree stays green, and the warning names the link. A value source moves the same way: under `txt = "rust"`, `values/a.json -> ../data/x.txt` is no value source, and the warning names `values/a.json`. A narrow `fmt` handed a name the plain run does not reach reads the file as that run does: with `docs/license.md` and `other/license.rs` both links to `LICENSE`, `fmt other/license.rs --check` now reports what `fmt docs/license.md --check` reports, where it read the file as Rust.
- **A version 1 list holding the empty string.** Such a list reads `LICENSE` ([§FS-scan.scope.extensions.empty](../../functional-spec/FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)), so there `LICENSE` claims a reading and `docs/license.md -> ../LICENSE` stops being Markdown.
- **New refusal.** Two links that read a file of the second sort differently. That tree was green. Where the plain run reaches only one of those names, nothing is refused, and `check --full` stays as green as `check` ([§FS-scan.identity.reading.plain](../../functional-spec/FS-scan.md#identityreadingplain-a-name-only---full-or-a-handed-path-reaches-decides-nothing)). Where it reaches neither, a run that meets both, `check --full` or a run naming the directory that holds them, prints the refusal in the out-of-scope tier and exits 1. `check` itself stays green, and so does a run naming one of those files, which meets no second name.
- **New home errors.** A link in another kind's home, or in `tests/e2e/`, is now judged there. A link in a second folder of the same row now owes that folder's index an entry: the maintainer adds it, and `fmt --write` links a bare one.
- **A link outside every home, listed first.** With `include = ["docslink"]` and `docslink -> docs`, the walk used to meet `docs/functional-spec/x.md` only as `docslink/functional-spec/x.md`, and that name in no home shielded the file from its index. A kind's home is a plain root whatever `include` says, so the file now owes that index an entry, at `docs/functional-spec/x.md:1`, as the same tree with no link always did. That tree was green. The maintainer adds the entry, and `fmt --write` links a bare one.
- **An index shared by two folders.** With `aa/README.md` and `zz/README.md` links to `shared/README.md`, an entry for `aa/`'s declaration used to let `zz/`'s go unlisted, because the one file was asked about the first folder alone. Each folder now owes its own entry in it ([§FS-scan.identity.findings.place](../../functional-spec/FS-scan.md#identityfindingsplace-a-place-finding-is-judged-at-each-spelling)), so `zz/b.md:1` is red where that tree was green, and it names the entry to write. The maintainer adds the entry, and `fmt --write` links a bare one.

## release-note: Release note

- [§DF-one-file-one-reading](DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name), [§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids), [§REQ-no-data-loss.2](../../requirements/REQ-no-data-loss.md#2-writers-touch-only-what-they-own): **a file reached by two names is read as its own name reads, and judged and reported at each name.** Verdicts change for a repository with a link in it, under the correction route, because the old reading let the name that sorted first rewrite bytes `fmt` does not own. A link whose target's own name reads differently is read as the target reads, including under `txt = "rust"` and under a version 1 `[scan] extensions` holding `""`, where `LICENSE` claims a reading and `docs/license.md -> ../LICENSE` stops being Markdown: a declaration only the Markdown reading found is gone, and a citation to it goes red. Two names that read a file whose own name claims nothing differently are refused with `reading-conflict`, which neither `--only` nor `--ignore` hides. A link in another kind's home earns that home's error, and a link in a second folder of a row owes its index an entry. A file in a kind's home owes its index an entry even where a link outside every home is the name listed first, as with `include = ["docslink"]` and `docslink -> docs`: that tree was green. An index shared by two folders owes each of them its own entry: that tree was green too. Add the entry, and `fmt --write` links a bare one. A name only `--full` or a handed path reaches decides nothing about a file the plain run reaches by another name, and a refusal where the plain run reaches no name stands in the out-of-scope tier. Every finding replacing the old verdict names its location and the action, including the one-release `reading-moved` warning at a link whose reading moved, which grund 0.23.0 removes. A content finding names each spelling, with `(also at …)` in text and in JSON `sites`, including a citation direction asked of a declaration, and `check <link>` prints the whole run's line. The editor shows a finding at the spelling it stands at, and a content finding on each name open. Closes [issue #1274](https://github.com/agent-grounds/grund/issues/1274).
