# DF-grouping-block-config-findings: At a workspace root, `check` and `config validate` name the config findings of each `include_root = false` block the expansion reaches

**Date:** 2026-11-04

## status: Accepted

## context: Context

A block with `include_root = false` is no project ([§FS-workspace.2.1.2.2](../../functional-spec/FS-workspace.md#2122-include_root--false-has-nothing-to-lose)), but it is a config the run reads: workspace expansion loads it to learn its members, and then kept it only to pose the unread-files warning ([§FS-check.4.10](../../functional-spec/FS-check.md#410-include_root--false-leaves-the-blocks-own-files-unread)). The three config findings were named for the root's config and each project the expansion returns ([§FS-check.4.11.3](../../functional-spec/FS-check.md#4113-once-per-config-not-once-per-scope)), so at a workspace root nothing named such a block's config. A block on version 1 drew no caution from `check` or `config validate` there, and `config migrate --to 2` at a version 2 root reports only its own file, so every command run at the root said there was nothing left to move while the block was still read as version 1 ([issue #1138](https://github.com/agent-grounds/grund/issues/1138)). The caution exists so that a workspace can be moved to version 2 completely ([§FS-config.5.3](../../functional-spec/FS-config.md#53-a-version-1-config-is-cautioned-and-never-retired)), and [§DF-config-version-1-caution](DF-config-version-1-caution.md#df-config-version-1-caution-a-config-file-on-version-1-is-cautioned-once-in-place-of-success-with-no-deadline) already promised one line per version 1 config in a workspace.

## decision: Decision

The set a workspace root names is the root's config, each project the expansion returns, and each block with `include_root = false` the expansion reaches, at any depth and whether or not any of its members is present ([§FS-check.4.11.3](../../functional-spec/FS-check.md#4113-once-per-config-not-once-per-scope)). `check` and `config validate` both name it, in the bytes, order and report base they already use for a member, with the block's own directory after `--to 2` ([§FS-check.checks.config-version-1](../../functional-spec/FS-check.md#checksconfig-version-1-a-config-file-read-as-version-1), [§FS-config.4.1.1](../../functional-spec/FS-config.md#411-at-a-workspace-root)). The block stays what it was: no project, no scan, no alias. A narrowed run inside a member names nothing of a block above it, and a consumer names no block of an imported tree. No message, code, flag or key is added.

### decision.migrate: Rejected: naming the rest from `config migrate`

`config migrate --to 2` at a version 2 root keeps its one line, which speaks of the one file it names ([§FS-config-migrate.6.6](../../functional-spec/FS-config-migrate.md#66-a-second-run-is-a-no-op)), and its `member:` lines stay the members the root's own `[workspace]` lists ([§FS-config-migrate.8](../../functional-spec/FS-config-migrate.md#8-workspaces)). Once the ordinary members are moved, `check` prints `success`, so nobody has a reason to run migrate at a root already on version 2; naming the blocks there alone would not close the gap, and naming them there as well would be a second copy of `check`'s list.

### decision.projects: Rejected: returning the blocks as projects

Every reader of the expansion's projects would then treat a block as one: scan it, give it an alias, and count it in `list` and `cover`. The blocks are kept beside the projects instead.

## consequences: Consequences

A new finding is a verdict change under [§REQ-backwards-compatibility.1](../../requirements/REQ-backwards-compatibility.md#1-what-is-covered), and the route is the deprecation warning of [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path): each of the three findings is a warning that keeps the old form working, and the version 1 caution names no release ([§FS-config.5.3](../../functional-spec/FS-config.md#53-a-version-1-config-is-cautioned-and-never-retired)). No verdict flips and no verdict another requirement forbade is corrected, so neither the loud migration nor the correction route applies. The cost is [§FS-check.4.11.6](../../functional-spec/FS-check.md#4116-it-stands-in-place-of-the-success-line)'s: where the block's line is a run's only finding it stands in place of `success`, and `--ignore` with the finding's code gives back the old bytes. This amends [§DF-workspace-config-findings](DF-workspace-config-findings.md#df-workspace-config-findings-at-a-workspace-root-config-validate-names-every-configs-findings-that-check-names-and-config-show-names-only-its-own), whose consequence that neither `check` nor `config validate` names such a block's config no longer holds.

## release-note: Release note

- [§FS-check.4.11.3](../../functional-spec/FS-check.md#4113-once-per-config-not-once-per-scope), [§FS-check.checks.config-version-1](../../functional-spec/FS-check.md#checksconfig-version-1-a-config-file-read-as-version-1), [§FS-config.4.1.1](../../functional-spec/FS-config.md#411-at-a-workspace-root), [§DF-grouping-block-config-findings](DF-grouping-block-config-findings.md#df-grouping-block-config-findings-at-a-workspace-root-check-and-config-validate-name-the-config-findings-of-each-include_root--false-block-the-expansion-reaches), [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path), [§FS-check.4.11.6](../../functional-spec/FS-check.md#4116-it-stands-in-place-of-the-success-line): **At a workspace root, `grund check` and `grund config validate` name the config findings of each `include_root = false` block the workspace expansion reaches, as they name a member's.** Such a block on version 1, read from `.agents/grund.toml`, or beside an `.agents/grund.toml` nothing reads now earns its `warning:` line on stderr, at its path from the root, at any depth: `warning: group/grund.toml is version 1; migrate it with grund config migrate --to 2 group`. Where that is `check`'s only finding it replaces the `success` line, and stdout is empty; a `--format=json` run carries it as one warning finding on stderr; the Node and Python `check` carry it in `report.warnings`, the Node `validateConfig` in `runCautions` and the Python `validate_config` in `warnings`. **What does not move:** every exit code, every message, `grund config migrate`, `grund config show`, and a run narrowed to a member. **Who this affects:** a script that compares `grund check`'s stdout to `success`, or expects an empty stderr, at a workspace root holding such a block; pass `--ignore` with the finding's code (`config-version-1`, `deprecated-config-location` or `redundant-config`), or migrate the block. Closes [issue #1138](https://github.com/agent-grounds/grund/issues/1138).
