# DF-stub-heading-from-unscanned-target: a bare-ID link through a stub anchors on its target's heading whether or not the scan reaches it

**Status:** Accepted
**Date:** 2026-10-09

## 1. Context

`grund fmt --cross-refs` links a bare-ID citation to the file that holds the declaration, at the anchor of the declaration's own heading ([§FS-fmt.6.2.1](../../functional-spec/FS-fmt.md#621-the-anchor-names-the-cited-heading), [§DF-declaration-anchor](DF-declaration-anchor.md#df-declaration-anchor-a-bare-id-markdown-link-points-at-the-declarations-heading-anchor)). For an ID a stub declares, that file is the stub's target. Where the walk did not reach the target, because it lay outside `[scan] include` or was ignored, the only record of the ID was the stub's, and a stub's record carries no title, so the heading `fmt` slugified was the bare ID. With a stub `# FS-a: [../notes/a.md](../notes/a.md)` and a target outside the scan that opens `# FS-a: A`, `grund fmt --write` linked the citation to `../notes/a.md#fs-a`, a fragment no heading in that file carries. The heading slugs to `fs-a-a`: the link the same build wrote once the target was scanned, and the anchor `grund show FS-a --format=json` reports for the same tree ([§FS-show.3.1.3.1](../../functional-spec/FS-show.md#3131-the-heading-anchor)).

Nothing reported it. `check` was clean, because grund validates no fragment ([§FS-non-goals.1](../../functional-spec/FS-non-goals.md#1-markdown-link-validation)), and on GitHub a fragment that matches no heading opens the file at its top. A `.<section>` citation of the same ID already anchored on the target's heading, because a stub's sections are its target's, scanned or not ([§FS-check.3.2.1](../../functional-spec/FS-check.md#321-a-stubs-sections-are-its-targets-scanned-or-not)); only the bare ID still read the stub. Reported as [issue #549](https://github.com/agent-grounds/grund/issues/549).

## 2. Decision

[§FS-fmt.6.2.1.1](../../functional-spec/FS-fmt.md#6211-through-a-stub-the-declarations-heading-is-the-targets): a bare-ID citation through a stub anchors on the declaration's heading in the stub's target, whether or not the walk reaches it. Where it does not, `fmt` reads the target as `check` and `show` read it ([§FS-check.3.2.1](../../functional-spec/FS-check.md#321-a-stubs-sections-are-its-targets-scanned-or-not), [§FS-show.2.3.7](../../functional-spec/FS-show.md#237-a-stubs-target-is-found-by-its-id)), so the anchor is the one `show` reports and the link is the one the same tree takes with the target scanned, through one stub or several to the same target. This is [§DF-declaration-anchor](DF-declaration-anchor.md#df-declaration-anchor-a-bare-id-markdown-link-points-at-the-declarations-heading-anchor)'s rule reaching a home the scan does not, and it extends [§DF-stub-sections-from-unscanned-target](DF-stub-sections-from-unscanned-target.md#df-stub-sections-from-unscanned-target-a-stubs-sections-are-its-targets-whether-or-not-the-scan-reaches-it) from a stub's sections to its declaration's own heading: the scan scope decides neither the link nor the anchor.

The target lends its heading only where it declares the ID once, which is the reading `show` takes. A target that declares the ID more than once lends none, because `show` refuses that ID as ambiguous rather than read it ([§FS-show.2.3.7](../../functional-spec/FS-show.md#237-a-stubs-target-is-found-by-its-id)), and a broken stub's target holds no declaration of the ID to lend. There `fmt` reads the stub as it did before.

## 3. Rejected alternative: drop the anchor for a target outside the scan

Writing no fragment for such a link would stop it naming a heading that is not there, without reading the target. It would take [§DF-declaration-anchor](DF-declaration-anchor.md#df-declaration-anchor-a-bare-id-markdown-link-points-at-the-declarations-heading-anchor) back for exactly the homes the scan does not reach, leaving a link that opens the file at its top, and the link would still differ from the one the scanned tree takes and from the anchor `show` reports, which [§FS-show.3.1.3.1](../../functional-spec/FS-show.md#3131-the-heading-anchor) says is the one `fmt` derives.

## 4. Rejected alternative: keep the stub's anchor

Leaving the bare ID on the stub's record moves no verdict: a tree an older grund formatted stays clean under `grund fmt --check`. It also keeps writing a link into the declaration's file at a heading that file does not carry, which is the wrong write [§REQ-no-wrong-citation.3](../../requirements/REQ-no-wrong-citation.md#3-no-wrong-write) forbids (section 6), and a tool that builds a web link from `show --format=json` ([§DF-show-anchor-data](DF-show-anchor-data.md#df-show-anchor-data-show-json-carries-the-heading-anchor-grund-already-derives)) would go on producing a URL other than the one `fmt` writes into the same docs. The workaround the issue names, adding the target's directory to `[scan] include`, fixes the link only by making the target a file `check` judges, which the user did not ask for.

## 5. Consequences

The verdict moves both ways, on `grund fmt --check` and the bare `grund fmt` dry run alone, at a line holding a bare-ID citation through a stub to a Markdown target the walk does not reach. No message changes.

- **Pass to fail.** A line an older grund linked to the stub's anchor is now a `markdown link` row ([§FS-fmt.3.5](../../functional-spec/FS-fmt.md#35-the-dry-run-report)), and the run exits 1 where it exited 0:

  ```console
  $ grund fmt --check   # docs/uses.md reads "Uses [§FS-a](../notes/a.md#fs-a)." as grund 0.16.1 wrote it
  docs/uses.md:1: markdown link
  ```

  `grund fmt --write` rewrites the link to `../notes/a.md#fs-a-a`.
- **Fail to pass.** A line that already carries the target's anchor, written by hand or by a run with the target scanned, was a `markdown link` row the old build would have rewritten to `#fs-a`. It is now clean.

Nothing else moves. `grund check` does not, nor the editor diagnostics that are its findings ([§FS-lsp.1.1](../../functional-spec/FS-lsp.md#11-diagnostics)): it validates no fragment ([§FS-non-goals.1](../../functional-spec/FS-non-goals.md#1-markdown-link-validation)), it holds an index entry to the shape of the link and never to its target ([§FS-check.3.17.2](../../functional-spec/FS-check.md#3172-the-shape-never-the-target)), and the managed block's chapter rules never link a rule declared through a stub, whose record has no title to render. The editor's document links name the declaration's line, not `fmt`'s anchor ([§FS-lsp.1.3.2](../../functional-spec/FS-lsp.md#132-document-links)). A target the walk reaches, a `.<section>` citation, a source-file target, which takes no anchor ([§FS-fmt.6.2](../../functional-spec/FS-fmt.md#62-form)), and `anchor_format = "none"` link as they did. So do a target that declares the ID more than once, which `show` refuses as ambiguous, and a broken stub, which `check` reports.

## 6. The correction route

[§REQ-backwards-compatibility.5](../../requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids) licenses the pass-to-fail move, and each of its five conditions holds.

1. *Prior prohibition.* The old link violated [§REQ-no-wrong-citation.3](../../requirements/REQ-no-wrong-citation.md#3-no-wrong-write), which already applied when that verdict shipped: its `## 3. No wrong write` is in every tag from v0.13.0 on, v0.16.0 and v0.16.1 among them.
   That section makes a persisted rewrite a resolution, so [§REQ-no-wrong-citation.1](../../requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution) binds the writer as it binds the reader: a citation resolves to exactly the declaration its ID names, never to a silent best-effort pick. In both tags the link's path is "the file containing the declaration" ([§FS-fmt.6.2](../../functional-spec/FS-fmt.md#62-form)) and, for a bare ID, its anchor is "the declaration's own heading" ([§FS-fmt.6.2.1](../../functional-spec/FS-fmt.md#621-the-anchor-names-the-cited-heading)), "derived from that declaration's heading text" ([§DF-declaration-anchor.2](DF-declaration-anchor.md#2-decision)).
   The old write took the path from the target and the heading from the stub's record, which has no title, so it persisted a link into the declaration's file at a heading that file does not carry: the stub's line stood in, unannounced, for a heading the writer never read. The declaration was never in doubt, since v0.16.1's `show` resolved the ID to the target's line on the same tree, and v0.16.1's `fmt` wrote `#fs-a-a` once the target was scanned.
   This reaches only that substitution. A target that declares the ID more than once, and a broken stub, keep their link on both builds.
2. *Accepted proof.* This record. The [§REQ-backwards-compatibility.2](../../requirements/REQ-backwards-compatibility.md#2-the-deprecation-path) deprecation path does not fit, because there is no old form to keep beside a new one: the old link is a fragment no heading carries, and nothing a user writes selects it, since the stub and the citation are right as written.
   The [§REQ-backwards-compatibility.3](../../requirements/REQ-backwards-compatibility.md#3-loud-mechanical-migrations) mechanical migration does not fit either, because the `markdown link` row `fmt --check` prints does not name the versions it moved between, although `grund fmt --write` is the one command that clears it.
3. *Named release.* The release note below names the verdict move in both directions, the line it lands on, and the command that clears it.
4. *Actionable findings.* The finding that replaces the old verdict is `fmt --check`'s existing `markdown link` row ([§FS-fmt.3.5](../../functional-spec/FS-fmt.md#35-the-dry-run-report)), which names the file and line it would rewrite, and `grund fmt --write` makes the rewrite.
5. *No new licence.* This is not a licence for anything else: nothing is tightened, no rule, finding or prohibition is new, and the anchor now written is the one [§FS-fmt.6.2.1](../../functional-spec/FS-fmt.md#621-the-anchor-names-the-cited-heading) and [§DF-declaration-anchor](DF-declaration-anchor.md#df-declaration-anchor-a-bare-id-markdown-link-points-at-the-declarations-heading-anchor) already named. A target that declares the ID more than once and a broken stub keep their old link on both builds.
