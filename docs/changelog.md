# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file and **older releases live one-per-file under `docs/changelog/`**, so a reader (human or agent) only loads the history they ask for. Nothing is written here between releases: a release writes its own section from the pull requests merged since the previous tag and the compatibility notices the decision records gained since then ([§FS-distribution.4.6](functional-spec/FS-distribution.md#46-the-release-lists-the-pull-requests-merged-since-the-previous-tag)). The changelog is part of the conformant tree, so every citation a section carries is checked (`grund check` validates them).

## 1. Conventions

### 1.1 Shape of a release

From 0.16.0 on, a release is the list of the pull requests merged since the previous tag, newest first, one line each — `- [<title>](<url>) (PR #N)`, the pull request's own title escaped so that it is text and never a citation ([§FS-distribution.4.6.2](functional-spec/FS-distribution.md#462-one-line-per-pull-request-its-title-linked)) — followed, when the release has any, by `### Compatibility notices`. Every merged pull request is listed, docs-only ones included. Releases up to and including 0.15.0 keep the Keep-a-Changelog sections they were published with — `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`, and in the first release narrative subsections such as `Baseline` or `Distribution and bindings` — and are not rewritten.

### 1.2 Compatibility notices and schema versions

A compatibility notice says what a verdict change breaks and for whom. It is written where the change is decided, as a `## release-note: Release note` section holding one bullet on the decision record, and the release that first carries it publishes it under `### Compatibility notices` ([§FS-distribution.4.6.4](functional-spec/FS-distribution.md#464-compatibility-notices-come-from-the-decisions)). A bump of `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) or of the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)) is a breaking change for the consumer, so it is announced the same way: a notice, with its migration, on the decision that bumps the schema. Up to 0.15.0 it was a `**Schema:**` bullet under **Changed**.

### 1.3 How a section is generated

`scripts/prepare_changelog_release.py prepare <version>`, which both release helpers run ([§FS-distribution.4.4](functional-spec/FS-distribution.md#44-two-helper-workflows-bump-the-version-on-a-validated-candidate)), reads every commit since the previous tag, asks the forge which merged pull request each belongs to ([§FS-distribution.4.6.1](functional-spec/FS-distribution.md#461-the-range-is-every-commit-since-the-previous-tag)), and writes the section; `preview` prints the same body and writes nothing. A forge call that fails, or answers with something that is not JSON, is tried again after one second and then two, so one dropped connection does not lose the release ([§FS-distribution.4.6.3.1](functional-spec/FS-distribution.md#4631-a-forge-call-is-tried-three-times)). When the range still cannot be read whole it refuses and writes nothing ([§FS-distribution.4.6.3](functional-spec/FS-distribution.md#463-a-refused-release-leaves-the-tree-as-it-was)). So a pull request's title is its release line, and a pull request writes nothing here.

### 1.4 Progressive discovery

Only the **most recent release** is inline. When a new release ships, its generated section takes the inline place, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md`, and a one-line link counting what it held is added under [section 3, Older releases](#3-older-releases) ([§FS-distribution.4.5](functional-spec/FS-distribution.md#45-what-the-version-bump-includes)). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

### Compatibility notices

- [§FS-check.3.1.3.2](functional-spec/FS-check.md#3132-a-key-fetch-has-nothing-to-run-for): **`check` no longer recommends `grund fetch` for a key that has nothing to run.** Where a kind's `fetch` is empty or only whitespace and no file of that name exists, a citation of an ID the kind does not hold now ends in the repair `grund fetch` itself gives, for example ``[[kinds]] `AR` fetch names no executable; name the program, or if this kind is not fetched remove the key and any `resolve`, and its missing IDs are then errors``, in place of `run grund fetch <ID>`. The code, severity and exit do not change. **Who this affects:** a script matching the words after the em dash, or the exact line, on such a project. Filter on the JSON `code` (`missing-snapshot` or `dangling`) instead. The hint under an absent value home with such a key ([§FS-fetch.4.1](functional-spec/FS-fetch.md#41-an-absent-value-home-is-refused-with-the-way-through)) likewise no longer names `grund fetch`, and reads `create the file` or `create the folder`; its first line and exit 2 do not change.
- [§FS-fetch.2.1](functional-spec/FS-fetch.md#21-a-value-that-names-no-executable), [§FS-config-v2.checks.config-fetch-names-nothing](functional-spec/FS-config-v2.md#checksconfig-fetch-names-nothing-a-rows-fetch-names-no-executable), [§FS-config-migrate.3.1.10](functional-spec/FS-config-migrate.md#3110-a-fetch-that-names-no-executable), [§REQ-backwards-compatibility.2](requirements/REQ-backwards-compatibility.md#2-the-deprecation-path): **a `fetch` key that is empty or only whitespace now warns under version 2, and becomes an error in grund 0.23.0.** `grund check`, `config validate` and `config show` print the warning at the key's line, and `grund fetch` and `config migrate` refuse the key, under both config versions, with the repair. If a kind's missing IDs are warnings only because of `[rules.resolution] <KIND> = "warn"` (version 1: `resolve = "should"`), the blank key is what lets that setting load: removing the key means removing the setting too, and those IDs are then errors.
- [§FS-scan.scope.homes.lookup](functional-spec/FS-scan.md#scopehomeslookup-a-home-that-cannot-be-looked-up-is-a-scan-failure-not-an-absent-home), [§DF-home-lookup-failure-fails-at-the-home](decisions/functional/DF-home-lookup-failure-fails-at-the-home.md#df-home-lookup-failure-fails-at-the-home-a-root-whose-lookup-fails-for-a-reason-other-than-absence-fails-at-the-root-and-exits-move-with-it), [§REQ-backwards-compatibility.5](requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids): **a root that cannot be looked up is a scan failure at the root, not an absent root.** A kind's home, a default root or an `include` entry whose lookup fails for a reason other than absence, such as a parent directory without search permission or a link to itself, now prints `error: <root>: <reason>`. **Exits move to `2`:** from `0` for `grund check`, `check --format json`, `list`, `refs` and `fmt --check`, and for `grund show` of an ID elsewhere, where no wider walk met the parent, as on most version 1 configs; from `1` for `grund show` of an ID in that home and for `grund check` on a version 2 config whose parent the walk does not read. Each of those runs had passed over a home it never read. **Who notices:** a gate on a tree holding such a directory. Make the path readable, or keep it out of the scan. A root link going outside the project is still pruned. The verdict moves by the correction route, because the old exits broke [§REQ-no-missed-citation.1](requirements/REQ-no-missed-citation.md#1-no-silent-skips). Every finding that replaces the old verdict names its location and the action to take. Closes [issue #1318](https://github.com/agent-grounds/grund/issues/1318).
- [§DF-one-site-order](decisions/functional/DF-one-site-order.md#df-one-site-order-a-duplicates-sites-have-one-order-checks-whichever-command-lists-them), [§FS-errors.4.1.1](functional-spec/FS-errors.md#411-the-order-of-a-duplicates-sites): `show` and `refs` now list an ambiguous ID's sites in `check`'s order.
- [§FS-check.2.4.3](functional-spec/FS-check.md#243-what-failed-and-where-decide-the-code-and-the-fix): **a scan failure says what failed, and offers a fix that works where it failed.** A file that was read and does not parse is now reported as `unparsable-file` rather than `io`, still exit `2`, with a fix that says what the file should hold, for example ``write the case's expected exit status in the file as one integer``. At a scan root, a path passed on the command line and a value source, `io`'s remedy keeps its words and now says how, for example ``make the path readable, or keep it out of the scan by removing it from the [schema.kinds] row that lists it, because exclude does not prune scan roots``. A section lock reads ``make the path readable``. **Who this affects:** a script filtering on `code == "io"`, or matching the remedy text in a parse or section-lock line. Filter on `code` and treat both `io` and `unparsable-file` as an incomplete run. Exit statuses are unchanged. `ApiScanError` and the Python and Node scan-failure records gain `code`. Closes [issue #1272](https://github.com/agent-grounds/grund/issues/1272).
