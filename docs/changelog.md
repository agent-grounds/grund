# Changelog

Records every notable change to `grund`. Versions follow semver; the **latest release is inline** in this file and **older releases live one-per-file under `docs/changelog/`**, so a reader (human or agent) only loads the history they ask for. Nothing is written here between releases: a release writes its own section from the pull requests merged since the previous tag and the compatibility notices the decision records gained since then ([§FS-distribution.4.6](functional-spec/FS-distribution.md#46-the-release-lists-the-pull-requests-merged-since-the-previous-tag)). The changelog is part of the conformant tree, so every citation a section carries is checked (`grund check` validates them).

## 1. Conventions

### 1.1 Shape of a release

From 0.16.0 on, a release is the list of the pull requests merged since the previous tag, newest first, one line each — `- [<title>](<url>) (PR #N)`, the pull request's own title escaped so that it is text and never a citation ([§FS-distribution.4.6.2](functional-spec/FS-distribution.md#462-one-line-per-pull-request-its-title-linked)) — followed, when the release has any, by `### Compatibility notices`. Every merged pull request is listed, docs-only ones included. Releases up to and including 0.15.0 keep the Keep-a-Changelog sections they were published with — `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`, and in the first release narrative subsections such as `Baseline` or `Distribution and bindings` — and are not rewritten.

### 1.2 Compatibility notices and schema versions

A compatibility notice says what a verdict change breaks and for whom. It is written where the change is decided, as a `## release-note: Release note` section holding one bullet on the decision record, and the release that first carries it publishes it under `### Compatibility notices` ([§FS-distribution.4.6.4](functional-spec/FS-distribution.md#464-compatibility-notices-come-from-the-decisions)). A bump of `grund_config_version` ([§FS-config.5](functional-spec/FS-config.md#5-schema-versioning)) or of the `AGENTS.md` init block version ([§FS-init.2](functional-spec/FS-init.md#2-outputs)) is a breaking change for the consumer, so it is announced the same way: a notice, with its migration, on the decision that bumps the schema. Up to 0.15.0 it was a `**Schema:**` bullet under **Changed**.

### 1.3 How a section is generated

`scripts/prepare_changelog_release.py prepare <version>`, which both release helpers run ([§FS-distribution.4.4](functional-spec/FS-distribution.md#44-two-helper-workflows-bump-the-version-on-a-validated-candidate)), reads every commit since the previous tag, asks the forge which merged pull request each belongs to ([§FS-distribution.4.6.1](functional-spec/FS-distribution.md#461-the-range-is-every-commit-since-the-previous-tag)), and writes the section; `preview` prints the same body and writes nothing. A forge call that fails, or answers with something that is not JSON, is tried again after one second and then two, so one dropped connection does not lose the release ([§FS-distribution.4.6.3.1](functional-spec/FS-distribution.md#4631-a-forge-call-is-tried-three-times)). When the range still cannot be read whole it refuses and writes nothing ([§FS-distribution.4.6.3](functional-spec/FS-distribution.md#463-a-refused-release-leaves-the-tree-as-it-was)). So a pull request's title is its release line, and a pull request writes nothing here.

### 1.4 Progressive discovery

Only the **most recent release** is inline. When a new release ships, its generated section takes the inline place, the previous "latest" section is moved verbatim to `docs/changelog/<version>.md`, and a one-line link counting what it held is added under [section 3, Older releases](#3-older-releases) ([§FS-distribution.4.5](functional-spec/FS-distribution.md#45-what-the-version-bump-includes)). The most recent release stays inline so the common reader and agent path — "what changed lately?" — is one file deep.

### Compatibility notices

- [§FS-workspace.6.1.7.5](functional-spec/FS-workspace.md#6175-an-unobtainable-members-value-leaves-the-claim-undecidable), [§FS-check.3.29.2](functional-spec/FS-check.md#3292-an-unanswered-claim-is-not-reported-and-is-asked-quietly), [§FS-workspace.6.1.5](functional-spec/FS-workspace.md#615-alias-paths-do-not-change-with-scope), [§FS-config-v2.reader.5](functional-spec/FS-config-v2.md#reader5-an-array-may-span-lines): **a `[workspace]` claim above a repository that cannot be read no longer fails the repository's `check`, and a version-2 `members` written across lines is now read.**
  **What goes quiet:** a nested `[workspace]` below an ancestor whose `members` or `optional_members` cannot be obtained, because the list never closes its bracket or the value is not a list, is no longer reported as ``this [workspace] is listed by no enclosing workspace``, since that ancestor may list it. Such a run exits `0` where it exited `1`, and a member run below such an ancestor no longer offers the ``run `grund check` from the workspace root`` remedy. The e2e cases `check-unlisted-block-under-a-broken-ancestor` and `check-unlisted-block-in-a-workspace-under-a-broken-ancestor` move from exit `1` to exit `0`.
  **What tightens:** a version-2 `members` written across lines, or ending in a trailing comma, is the list the config loads. So a run narrowed to a workspace that such an outer workspace lists now spells alias paths the way the outer root does. That run exited `0` with ``warning: ../grund.toml: cannot read [workspace] members (`members` is not a list of strings); alias paths below it may be missing a segment``. A citation spelled from the narrowed root now fails with an ``unknown project alias hub`` error at exit `1`, as the run at the outer root already did. The fix is to spell the citation as the workspace root does: `shop/hub/FS-hub` where it wrote `hub/FS-hub`.
  **What does not move:** a version-1 ancestor's value is still read on its key's line, so one written across lines or with a trailing comma still warns and is never taken as a claim. An unclosed array of any other key leaves the claim answered. Closes [issue #1010](https://github.com/agent-grounds/grund/issues/1010). (PR #1011)
- [§FS-init.2.3.4.3](functional-spec/FS-init.md#2343-cheap-grounding): **The managed block says a section read opens with its heading line.** The `grund <ID>` rung of the `grund init` block now reads that the lead is heading-less for a whole declaration, while `grund <ID>.<section>` opens with that section's heading line, as `grund show` has always printed it. The block moves from v39/v40 and v41/v42 to **v43/v44** and **v45/v46**, so `grund check` reports a block 0.20.0 wrote as outdated. **What an upgrader does:** run `grund init` once to re-render the block; unmanaged content is kept. (agent-grounds/grund#1026)
- [§FS-config-explain.1.1](functional-spec/FS-config-explain.md#11-targets): **`grund config explain` answers a dotted path that names exactly one table or key.** `grund config explain schema.sources` was refused with exit 1 and a line naming `'[schema.sources]'`. It now prints what `grund config explain '[schema.sources]'` prints, with exit 0. **Who this affects:** a script that read exit 1 from a dotted target as "unknown". A path that reads two ways, such as `schema.kinds.id_format`, and a bare name, such as `exclude`, still exit 1, and they now name every spelling that answers. Closes [issue #1005](https://github.com/agent-grounds/grund/issues/1005).
- A refused `grund config migrate --to 2` preview no longer prints the candidate, the `written:` defaults or next-init advice, and ends with `would not write: <causes>`; its exit is unchanged. `--full` brings the candidate and complete report back when only listed comments refuse, and `--drop-comments` previews that candidate with exit `0`.
- A config that declares kinds but no citation rules (`[citations]` in version 1, `[rules.citations]` in version 2) no longer gets a `### Citation directions` section with the fixed "Specs cite goals, architecture cites specs, …" sentence: the section renders only the rules a config declares, or, where grounding is on, the grounding sentence alone. `kinds = []` drops its "No kind is declared yet" paragraph the same way, and a scoped block with grounding but no rules drops its legend and closing line. The guide stays available as `grund guide citations`. This shares the v43/v44 and v45/v46 pairs this release already moves to. Existing blocks are reported outdated by `grund check` and `grund init --check`; run `grund init` to refresh them, preserving unmanaged text. No verdict over the repository's own files changes.

  declarations. A declaration whose field holds another value is outside the rule. A whose
  clause that is still refused is answered for the field or value that failed, and a
  sentence whose clause is accepted but whose quantifier, object or predicate is refused is
  answered for that; through `0.21.0` either reason follows the old `unknown kind "…"` text

- [§DF-front-matter](decisions/functional/DF-front-matter.md#df-front-matter-a-markdown-files-front-matter-is-a-region-of-its-own-owned-by-the-files-first-declaration-and-never-rewritten), [§FS-check.1.1.5.2](functional-spec/FS-check.md#1152-front-matter-holds-no-heading), [§FS-check.1.1.5.2.1](functional-spec/FS-check.md#11521-its-citations-belong-to-the-files-first-declaration), [§REQ-backwards-compatibility.5](requirements/REQ-backwards-compatibility.md#5-correcting-a-verdict-another-requirement-forbids),
  [§REQ-no-wrong-citation.1](requirements/REQ-no-wrong-citation.md#1-no-wrong-resolution), [§REQ-no-wrong-citation.2](requirements/REQ-no-wrong-citation.md#2-no-false-alarms): **A Markdown file's front matter is
  read as front matter.** A `---` or `+++` block on line 1, closed by the same delimiter or by
  `...` for `---`, holds no heading, so a `# ID: …` YAML or TOML comment declares nothing.
  Its `§` citations still resolve and now belong to the file's first declaration: `refs`
  and `cover` name it as the enclosing declaration, `refs --from`, rules and obligations
  count them, and citation directions judge them by its kind. `grund fmt` rewrites nothing
  inside the block, so a front-matter citation is no longer turned into a Markdown link that
  breaks the YAML. The verdict moves both ways. **Who this breaks:** a repository that cites
  an ID only a front-matter comment declared (now an `unknown reference`), one whose file
  opens with a `---` thematic break followed by another `---` line (the headings between
  them no longer declare), and one whose front-matter citation a `never` direction or a
  declaration-scoped rule forbids (now reported); every finding names its location and the
  fix. Closes [#1046](https://github.com/agent-grounds/grund/issues/1046).
- [§DF-front-matter-field](decisions/functional/DF-front-matter-field.md#df-front-matter-field-a-kinds-front-matter-field-holds-its-files-yaml-front-matter-with-the-blocks-top-level-keys-as-its-sections): **A kind's `front-matter` field now holds its file's YAML front
  matter, with the block's top-level keys as its sections.** Declare
  `[schema.kinds.<KIND>.fields.front-matter]` and its
  `[schema.kinds.<KIND>.fields.front-matter.keys.<key>]` tables to require keys and hold
  their values to a `one_of`. **Who this breaks:** a config that used `front-matter` as
  the name of a body chapter. Setting `title`, `position`, `after`, `content` or `one_of`
  on it, or `after = "front-matter"` on another field, now stops the config from loading,
  and a `## front-matter:` chapter of such a kind is now a `front-matter-heading` error.
  Rename the chapter and its field. A `+++` (TOML) block is read the same way
  ([§DF-toml-front-matter](decisions/functional/DF-toml-front-matter.md#df-toml-front-matter-a-kinds-front-matter-field-reads-a-toml-block-as-it-reads-a-yaml-one)). A repository that declares no `front-matter` field
  sees no change.
- A marked token that opens with a configured kind but does not match that kind's ID format, such as `<§>REQ-999` or `<§>REQ-12a` under the default `slug_pattern`, and that nothing declares, was dropped without a word, so a citation of a missing ID written this way passed `check`. It is now the `off-format-citation` error, and `out-of-scope-off-format-citation` under `--full`. It is reported wherever a dangling citation is: in prose, inline code, comments, doc-comments and source strings. A tree that carries such a token exits `1` where it exited `0`. There are two fixes: cite an ID in the kind's format, or, if the token is an illustration, escape it with the configured marker wrapped in angle brackets, `<§>REQ-999`. A token that a declaration of exactly that spelling backs is unchanged: it resolves, and only its declaration is reported. The construct had no defined meaning, so giving it one is the change licensed by [§REQ-backwards-compatibility.4](requirements/REQ-backwards-compatibility.md#4-what-was-never-a-promise), as recorded in [§DF-off-format-citation.4](decisions/functional/DF-off-format-citation.md#4-compatibility).

Closes [issue #1008](https://github.com/agent-grounds/grund/issues/1008).

- [§FS-config-v2.reader.5.commas](functional-spec/FS-config-v2.md#reader5commas-an-array-takes-one-trailing-comma-after-an-element), [§FS-config-v2.checks.config-not-toml](functional-spec/FS-config-v2.md#checksconfig-not-toml-a-version-2-config-holds-text-toml-refuses), [§REQ-backwards-compatibility.2](requirements/REQ-backwards-compatibility.md#2-the-deprecation-path): **a comma before a version-2 array's `]` with no element before it now warns, and becomes an error in grund 0.22.0.** `exclude = ["ab",,]` loaded silently as `["ab"]`, and `exclude = [,]` as the empty list, though TOML allows one trailing comma, after an element; they still load, and `check`, `config validate` and `config show` print `warning: grund.toml:9: expected string, read for now with every comma before the `]` taken off; delete each comma on line 9 that has no element before it; this warning becomes an error in grund 0.22.0`, code `config-not-toml`, naming the line the comma stands on in an array written across lines. - [§FS-values.2.2](functional-spec/FS-values.md#22-declarations-from-value-sources), [§FS-values.2.2.3](functional-spec/FS-values.md#223-how-a-yaml-source-is-read), [§FS-values.2.2.4](functional-spec/FS-values.md#224-yaml-findings-are-warnings-until-grund-0220), [§REQ-backwards-compatibility.2](requirements/REQ-backwards-compatibility.md#2-the-deprecation-path): **a value kind's home now reads YAML beside JSON.** A `.yaml` or `.yml` file in a `form = "value"` / `values = true` home declares values as a `.json` one does, comments allowed, and its IDs appear in `list`, `show`, `refs` and `cover`. **Who sees a change:** a repository with a YAML file in a value home.
