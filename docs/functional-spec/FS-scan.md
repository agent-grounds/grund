# FS-scan: what a path argument means, which projects a run loads, and which files it reads

What a run is handed and what it reads, defined once for every command that scans a tree: what a `<path>` argument means, which projects a run loads and so whose kinds and declarations it reads, which files a walk reads, which path names a file it read, and which text a file has. The `[scan]` keys and their defaults are [§FS-config.3.5](FS-config.md#35-scan--what-gets-scanned)'s, and which project owns a directory is [§FS-workspace.6.2](FS-workspace.md#62-the-boundary-is-mutual)'s. Serves [§GOAL-no-dangling-refs](../goals.md#goal-no-dangling-refs-every-cited-id-resolves-to-a-declaration), whose verdicts are only as good as the files a run read, and [§GOAL-token-economy](../goals.md#goal-token-economy-give-an-agent-the-right-amount-of-spec-not-the-whole-file).

## terms: Terms

Leans on [§FS-terms.terms.4](FS-terms.md#terms4-scanning-and-project-structure) (scan, scope, config root, workspace, member).

- **kind home** — The `folder` or `file` a `[[kinds]]` row names ([§FS-config.3.4](FS-config.md#34-kinds--recognized-kinds)): the place its declarations live.
- **scan root** — Where a walk starts: an `include` entry, a kind home, or an explicit path. Which rules it outruns is [§FS-scan.scope.roots](FS-scan.md#scoperoots-a-scan-root-outruns-every-rule-about-descent).
- **resolution scope**, **report scope** — The two scopes `check` tells apart for an explicit path, defined at [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports).
- **narrowed scan** — One scan of the enclosing project below its config root, with no workspace loaded: what `cover` runs for a path narrower than its config root ([§FS-scan.path.cover](FS-scan.md#pathcover-cover-runs-one-narrowed-scan)).
- **buffer** — The text an editor holds open for a file, saved or not, which a run reads as that file ([§FS-scan.text.buffer](FS-scan.md#textbuffer-a-files-text-is-what-a-save-would-write)).

## requirements: What every scan holds to

Four promises about what a run reads have points of their own, which every command shares: every region a run leaves unread is named and can be looked into ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)); every command answers a kind name from one reading of the configs ([§REQ-one-answer.identity.kinds](../requirements/REQ-one-answer.md#identitykinds-every-command-reads-one-kind-verdict)); a run given a path fails what the whole run fails about the files it reports ([§FS-check.requirements.narrow-never-lenient](FS-check.md#requirementsnarrow-never-lenient-a-narrower-run-never-passes-what-a-wider-run-fails-about-the-files-it-reports--realized)), and `list`, `show` and `id` resolve as it does ([§REQ-one-answer.differences.scope](../requirements/REQ-one-answer.md#differencesscope-scope)); and the machine's global git excludes are the one input from outside the checkout that decides which files are read ([§FS-config.requirements.8](FS-config.md#requirements8-a-projects-meaning-is-self-contained--realized)).

### requirements.spelling: How a tree is reached changes neither what is read nor what a finding names

A repository reads the same however a run arrives at it. A file reached through a link is named by the path the run met — the in-tree link, the explicit argument, the root as handed — never by its physical target, even where that target lies outside the config root ([§FS-scan.identity.link-path](FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path), [§FS-scan.identity.root-path](FS-scan.md#identityroot-path-the-scan-root-keeps-the-path-the-run-was-handed)). A physical file reached by two spellings is read once; its reading belongs to the physical file and its reported path to the spelling, so neither sort order nor the name a run was handed decides what it is read as or which names a finding carries ([§FS-scan.identity.read-once](FS-scan.md#identityread-once-one-physical-file-is-read-once), [§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it), [§FS-scan.identity.findings](FS-scan.md#identityfindings-a-finding-about-a-file-with-two-names-names-each-spelling-once)); an editor buffer is that file under any spelling ([§FS-scan.identity.buffers](FS-scan.md#identitybuffers-a-buffer-is-the-file-at-its-physical-location)). The project's canonical root stays the fence for directory links when the repository itself was reached through a link ([§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed)). So a checkout reached through a symlinked directory, as macOS reaches `/private/var` through `/var`, reads and reports what it does at its physical path, each finding spelled as its reader wrote it. Serves [§GOAL-friendliness-first.1](../goals.md#1-hard-requirements) and [§FS-non-goals.13](FS-non-goals.md#13-anything-that-would-let-two-grund-installs-disagree).

## path: What a path argument means

Every command that takes a `<path>` but `init`, whose `<path>` is the directory it writes in ([§FS-init.1](FS-init.md#1-inputs)), discovers its configuration from it. `check`, `list`, `show` and `id` resolve against the whole project the path discovers and let the path bound only what they report ([§DF-one-answer-rulings-run](../decisions/functional/DF-one-answer-rulings-run.md#df-one-answer-rulings-run-a-path-narrows-the-report-a-stub-reads-what-the-walk-reads-and-a-file-is-one-file-however-it-is-spelled-or-held), ruling D1); `cover` and `refs` give the path meanings of their own.

### path.discovery: A path is where discovery starts

An explicit `<path>` argument behaves as if the command were invoked from that path in what it discovers, so a `<path>` inside a member is member-scoped, not workspace-aggregate, even when a workspace exists above it ([§FS-scan.projects.discovery](FS-scan.md#projectsdiscovery-the-nearest-config-decides)). It does not behave so in what the run covers, which only an explicit path narrows ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)).

### path.none: A run with no path covers the project discovery finds

With no `<path>`, discovery starts at the current directory ([§FS-config.1](FS-config.md#1-file-location-and-discovery)). Where it finds no config, the run covers that directory on the canonical defaults. Where it finds one, the run covers that config root's default scope however far below the root it started: inside a member the member ([§FS-scan.projects.member](FS-scan.md#projectsmember-a-member-run-loads-the-member)), and at a workspace root, or below one outside every member, every project the workspace-root run loads ([§FS-scan.projects.workspace-root](FS-scan.md#projectsworkspace-root-a-run-at-the-workspace-root-loads-every-project)). It is the run given the config root's own directory as its `<path>`, so it is the run that writes section locks ([§FS-section-lock.write.rules](FS-section-lock.md#writerules-add-refresh-drop)) and the one [§FS-fmt.7.1](FS-fmt.md#71-scope-equivalence) calls the default scope.

Only an explicit `<path>` narrows a run, so from a directory `sub/` below the config root, `grund <command>` and `grund <command> .` are two different runs wherever the path bounds what is scanned or reported: `check`, `fmt`, `cover`, `list`, `refs` in each of its modes, `show --batch --all`, and `complete ids` ([§FS-completions.2.1](FS-completions.md#21-arguments-and-candidate-modes)). Where the path only chooses the project that answers, for `show` of one coordinate, `id`, `config` and `schema`, the two runs give one answer, and "`.` by default" is true of them alone. A page describing a path that bounds what is scanned or reported cites this point for the run given none rather than naming a directory the path defaults to.

### path.check: `check` reads more than it reports

A `check` given an explicit path reads what its project's ordinary run reads and reports only the files at or under the path. The **resolution scope** is the set of files the run reads so that citations resolve and citation edges count: the enclosing project's ordinary scope, `[scan] include` plus every walked kind home ([§FS-scan.scope.include](FS-scan.md#scopeinclude-include-is-scanned-from-the-config-root), [§FS-scan.scope.homes](FS-scan.md#scopehomes-every-configured-kind-home-is-scanned)), **union the path itself**, because a path may lie outside `include` and must still be read. The **report scope** is exactly the path. Every rule runs over the resolution scope, and a finding anchored outside the report scope is dropped before the report is written, unless it also names a site inside it ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)). Which projects the run loads is [§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)'s, and where it loads several the resolution scope is each one's. So for `check` a path narrows the report and not what the run resolves against; which verdicts that moves is [§FS-check.1.3.6.1](FS-check.md#1361-a-path-scope-narrows-the-report-not-the-resolution)'s. Decided in [§DF-path-scope-resolves-project-wide](../decisions/functional/DF-path-scope-resolves-project-wide.md#df-path-scope-resolves-project-wide-a-path-scoped-check-resolves-against-the-whole-project-and-reports-only-the-path).

### path.cover: `cover` runs one narrowed scan

Of the commands [§FS-workspace.8](FS-workspace.md#8-other-commands) covers, `cover` is the one whose `<path>` bounds a **scan** rather than choosing which config answers ([§FS-cover.1](FS-cover.md#1-inputs)): a scope narrower than the config root is one narrowed scan of the enclosing project, no workspace loaded and no `project` field. `cover` is outside the ruling that resolves the other commands against the whole project ([§DF-one-answer-rulings-run](../decisions/functional/DF-one-answer-rulings-run.md#df-one-answer-rulings-run-a-path-narrows-the-report-a-stub-reads-what-the-walk-reads-and-a-file-is-one-file-however-it-is-spelled-or-held), ruling D1), so it runs the narrowed scan. Decided in [§DF-cover-workspace-scope.2.1.1](../decisions/functional/DF-cover-workspace-scope.md#211-a-scope-narrower-than-the-config-root-stays-narrow).

### path.warning: Where the path changed an answer, the run said so

`list`, `show` and `id` resolve against the owning project ([§FS-scan.path.list](FS-scan.md#pathlist-list-reports-the-paths-entries-and-resolves-against-the-project), [§FS-scan.path.show](FS-scan.md#pathshow-show-resolves-the-id-against-the-project-the-path-discovers), [§FS-scan.path.id](FS-scan.md#pathid-id-numbers-from-the-project-the-path-discovers)), so no answer differs from that project's for a line to announce, and none is printed.

#### path.warning.shape: A text line after everything else on stderr

No such line is printed ([§FS-scan.path.warning](FS-scan.md#pathwarning-where-the-path-changed-an-answer-the-run-said-so)).

#### path.warning.cost: Only a narrowed path reads more

No such line is printed ([§FS-scan.path.warning](FS-scan.md#pathwarning-where-the-path-changed-an-answer-the-run-said-so)); a path narrower than its config root reads what [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) says.

#### path.warning.release: One named release, held by a test

No such line is printed ([§FS-scan.path.warning](FS-scan.md#pathwarning-where-the-path-changed-an-answer-the-run-said-so)), so no release is named.

### path.list: `list` reports the path's entries and resolves against the project

For `list`, `<path>` is the directory or file whose entries are reported, those declared at or under it; with none, every entry of the project the run covers ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)). Everything said about an entry is the owning project's answer, read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads it: its JSON `refs` count every citation of it in the project, `--unused` drops it when it is used anywhere in the project ([§FS-list.1.3](FS-list.md#13---unused)), an entry with another home outside the path carries the duplicate note ([§FS-list.2.6](FS-list.md#26-duplicate-declarations)), and the `--size` rows ([§FS-list.3.4](FS-list.md#34---size--per-coordinate-lead-and-full-body-measurements)) and `--summary` counts ([§FS-list.3.3](FS-list.md#33---summary)) give the same answers. A run that loads a workspace prints the catalog of [§FS-workspace.8.3](FS-workspace.md#83-grund-list), bounded by the path the same way ([§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)).

### path.show: `show` resolves the ID against the project the path discovers

For `show`, `<path>` chooses the project the ID resolves in; with none, the project the run covers ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)). The ID resolves against that project read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads it, so a path narrower than its config root moves no answer: an ID the project declares outside the path prints its body, exit `0`, one it declares both inside and outside the path is ambiguous ([§FS-show.2.2.1](FS-show.md#221-ambiguous-id)), and a short form ([§FS-show.1.2](FS-show.md#12-the-number-only-shorthand)) is matched over the same project. Under `--batch` every query resolves the same way. The path bounds nothing else, except that `--batch --all` takes its queries from the entries `list <path>` prints ([§FS-scan.path.list](FS-scan.md#pathlist-list-reports-the-paths-entries-and-resolves-against-the-project)), each resolved against the whole project.

### path.refs: `refs` scans the path's tree

For `refs`, in each of its modes ([§FS-refs.1.1](FS-refs.md#11-three-modes-one-path)), `<path>` is the directory or file whose tree is scanned, the project's with none ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)), and the sites it lists are that tree's. An ID operand resolves against the selected project's declarations, never another project's, read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads them, those retained for read compatibility included ([§FS-config.3.2.6](FS-config.md#326-resolving-an-off-grammar-citation)), and a compatible ID succeeds with exactly the path's sites, an empty selection included; inline sections and ambiguity use the same catalog ([§FS-refs.4](FS-refs.md#4-exit-codes)). Decided in [§DF-refs-compatible-id-project-scope](../decisions/functional/DF-refs-compatible-id-project-scope.md#df-refs-compatible-id-project-scope-a-refs-path-selects-sites-while-the-project-resolves-a-compatible-id). A `--from` source resolves against the project the path discovers, as `show`'s ID does ([§FS-scan.path.show](FS-scan.md#pathshow-show-resolves-the-id-against-the-project-the-path-discovers)). A run that loads a workspace lists the sites of the path's tree, not the workspace's: below the workspace root and outside every member, `--from` lists only the sites at or under the path ([§FS-refs.from](FS-refs.md#from---from-lists-what-one-point-cites)), and every other mode those and the ones a stub there lends ([§FS-declarations.stubs.target.5](FS-declarations.md#stubstarget5-what-a-target-outside-the-include-gives-and-what-stays-unjudged)).

### path.id: `id` numbers from the project the path discovers

For `id`, `<path>` is the directory whose project is numbered; with none, the project the run covers ([§FS-scan.path.none](FS-scan.md#pathnone-a-run-with-no-path-covers-the-project-discovery-finds)). That project is read as [§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports) reads it, so a path narrower than its config root proposes what a run at the config root proposes: the next number is one past the highest the project declares for the kind, wherever under it that declaration lies ([§FS-id.4](FS-id.md#4-next-number-derivation)), and under a number-less format ([§FS-id.4.1](FS-id.md#41-number-less-id-formats)) a proposal the project already declares anywhere is refused ([§FS-id.5](FS-id.md#5-collision-check)).

## projects: Which projects a run loads

Which projects a run loads decides whose kinds and declarations it reads; which project owns a directory is [§FS-workspace.6.2](FS-workspace.md#62-the-boundary-is-mutual)'s.

### projects.discovery: The nearest config decides

A run walks up from its `<path>` ([§FS-scan.path.discovery](FS-scan.md#pathdiscovery-a-path-is-where-discovery-starts)), or else the current directory, to the nearest `grund.toml` in either discovery form ([§FS-config.1](FS-config.md#1-file-location-and-discovery)). Where that is a member's own config, the run is member-local, and a qualified `<alias>/<ID>` cannot resolve, as `check` errors at the member scope ([§FS-workspace.5.1](FS-workspace.md#51-a-member-run)). A scope inside a member with no config of its own is member-local all the same, on [§FS-workspace.2](FS-workspace.md#2-workspace-configuration)'s canonical defaults with the member directory as the config root. Which member a scope lies in is judged on the path discovery climbs ([§FS-config.1.5](FS-config.md#15-the-ancestor-search-keeps-the-path-through-directory-links)), so `m/cases/b` is member `m`'s even where `m/cases` links out of the workspace or into another member; only a path in no member as written is judged where it resolves. Only outside every member does a nearest config at the workspace root run the command workspace-wide.

### projects.workspace-root: A run at the workspace root loads every project

`grund check` run at a workspace root checks the root project (unless `include_root = false`, [§FS-workspace.2](FS-workspace.md#2-workspace-configuration)) and all configured members, aggregates findings, and reports them in the shape of [§FS-check.2.1](FS-check.md#21-report-format), with paths relative to the workspace root when `[output] relative_paths = true`.

### projects.member: A member run loads the member

`grund check <member>` (or `grund check` invoked from inside a member tree) discovers the member's own config first and, for a member that declares no `[workspace]` block of its own, validates it as an independent project; one that does runs its own subtree ([§FS-workspace.6.1](FS-workspace.md#61-nested-workspaces)). What a qualified citation earns there is [§FS-workspace.5.1](FS-workspace.md#51-a-member-run)'s.

### projects.narrowed: A path below the config root loads what a run from it would see

`grund check <path>` with a `<path>` narrower than the config root loads the projects a run from `<path>` would load ([§FS-scan.projects.discovery](FS-scan.md#projectsdiscovery-the-nearest-config-decides), [§FS-workspace.8.8](FS-workspace.md#88-discovery-follows-grund-checks-walk-up)), resolves each of them completely, and reports only the path ([§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports)): inside a member the member, whose run refuses a qualified citation ([§FS-workspace.5.1](FS-workspace.md#51-a-member-run)); in a project with no workspace that project; and below a workspace root and outside every member every project the root run loads ([§FS-scan.projects.workspace-root](FS-scan.md#projectsworkspace-root-a-run-at-the-workspace-root-loads-every-project)), so a qualified citation the root run resolves resolves there too. Decided by [§DF-one-answer-rulings-run](../decisions/functional/DF-one-answer-rulings-run.md#df-one-answer-rulings-run-a-path-narrows-the-report-a-stub-reads-what-the-walk-reads-and-a-file-is-one-file-however-it-is-spelled-or-held), ruling D14, and [§DF-path-narrows-the-report-in-0-19](../decisions/functional/DF-path-narrows-the-report-in-0-19.md#df-path-narrows-the-report-in-0-19-in-0190-a-path-narrows-what-show-list-and-id-report-not-what-they-resolve-and-workspace-check--resolves-every-project-it-sees).

Below a workspace root such a run prints each finding the root run makes that is anchored at or under the path, or names a site there ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)), kept whole: the same bytes, its path rendered against the workspace root, an unknown alias with the outermost root's candidates ([§FS-check.3.8.2](FS-check.md#382-candidates-at-the-outermost-root)), and under `--format json` the object the root run writes, which carries no `project` field there either ([§FS-check.2.1](FS-check.md#21-report-format)). Run-level findings, the workspace run warnings among them, carry no path and print as the root run prints them ([§FS-check.1.3.6.1](FS-check.md#1361-a-path-scope-narrows-the-report-not-the-resolution)).

#### projects.narrowed.alias: A refused alias the workspace root resolved said so

No refusal is annotated: a run below a workspace root and outside every member resolves every alias the root run resolves ([§FS-scan.projects.narrowed](FS-scan.md#projectsnarrowed-a-path-below-the-config-root-loads-what-a-run-from-it-would-see)), and a member run refuses a qualified citation ([§FS-workspace.5.1](FS-workspace.md#51-a-member-run)), explaining an alias of the enclosing workspace's root as [§FS-workspace.5.1.1](FS-workspace.md#511-verified-enclosing-workspace-guidance) says.

### projects.kinds: Whose kinds a run reads

A run reads the kinds of the projects its configuration declares: its own config's `[[kinds]]` and, where that config declares a `[workspace]`, each member's ([§FS-config.3.4](FS-config.md#34-kinds--recognized-kinds), [§FS-workspace.2](FS-workspace.md#2-workspace-configuration)). It reads them from the configs alone, before any file is read, so a narrowed scan ([§FS-scan.path.cover](FS-scan.md#pathcover-cover-runs-one-narrowed-scan)), which loads no member's files, still reads the kinds its declared workspace configures and judges its `[citations]` targets against them ([§FS-config.3.9.5.2](FS-config.md#3952-a-pinned-target-is-judged-against-its-projects-kinds)); a rule object there is judged in the projects the run loads, so a namespaced one stays unverifiable ([§FS-rules.4.1](FS-rules.md#41-a-rule-this-scope-cannot-verify)). That one reading answers every command's question about a kind name ([§REQ-one-answer.identity.kinds](../requirements/REQ-one-answer.md#identitykinds-every-command-reads-one-kind-verdict)).

Each command asks within the **scope** it documents, a set of the projects the run read, and within one scope a name has one verdict, whichever command asks, except `code` where no row names the homeless kind ([§REQ-one-answer.differences.identity](../requirements/REQ-one-answer.md#differencesidentity-identity)):

| Who asks | Scope |
|---|---|
| `list --kind`, `list --selector`, `list --size --selector` | the selected projects: every loaded project, or those `--project` names ([§FS-list.1.2](FS-list.md#12---project)) |
| a rule subject, on `check`, `check --rule` and in the editor | the project whose configuration reads the rule ([§FS-rule-refusals.sentences.named-sections](FS-rule-refusals.md#sentencesnamed-sections-a-subject-that-needs-named-sections-is-answered-with-one-they-make-valid)) |
| a rule object, or a `[citations]` target | the local project for a bare `KIND`, the aliased project for `alias/KIND`, every project for `*/KIND` ([§FS-config.3.9.5](FS-config.md#395-validation)) |
| `grund id <KIND>` | the project the run loads ([§FS-id.1.1](FS-id.md#11-unknown-and-non-citable-kinds)) |

The verdict is one of four:

1. **citable** — a project in scope configures the name as a citable kind;
2. **configured but not citable** — a project in scope configures it with `citable = false` ([§FS-config.3.4.1](FS-config.md#341-citable--kinds-that-declare-no-ids)), and none in scope has it citable; the verdict carries that project's kind home, and its refusal is [§FS-errors.2.5.1](FS-errors.md#251-a-kind-that-declares-no-ids);
3. **unknown** — no project in scope configures it;
4. **unverifiable here** — the scope names a project alias and the run holds no workspace that could say what that project configures, as [§FS-rules.4.1](FS-rules.md#41-a-rule-this-scope-cannot-verify) defines it for a rule object.

Where two projects in one scope configure a name differently, citable wins, as [§FS-list.1.1](FS-list.md#11---kind) says for `--kind`. The `known kinds:` line a refusal ends in names the citable kinds of the same scope, once each, in configuration order.

A kind's named sections are read under the project that configures it: a named chapter subject of `KIND` ([§FS-rules.2](FS-rules.md#2-subject-selectors)) is accepted where that project sets `[id] named_sections = true`, whatever the root or another loaded project sets, so `list --selector API.terms` at a workspace root answers whatever `grund api/API-a.terms` answers ([§FS-declarations.section.map](FS-declarations.md#sectionmap-the-section-map-is-the-declarations-body-span)). Where two projects in scope configure `KIND`, the subject is accepted when either has named sections on, and it matches only the declarations of a project that has them on. Decided in [§DF-one-answer-rulings-grammar](../decisions/functional/DF-one-answer-rulings-grammar.md#df-one-answer-rulings-grammar-one-grammar-keeps-the-documented-refusal-bytes-and-order-and-one-kind-universe-keeps-each-commands-vocabulary), ruling D18, and [§DF-one-kind-verdict](../decisions/functional/DF-one-kind-verdict.md#df-one-kind-verdict-every-command-reads-one-kind-verdict-in-its-own-scope-and-refuses-a-rule-sentence-for-the-first-stage-it-fails).

Which end-to-end cases `--unused` leaves out ([§FS-list.1.3](FS-list.md#13---unused)), the kind titles a project lists, and where a non-citable kind's own files must cite are not kind-verdict questions, and stay their own points' ([§FS-config.3.4.1](FS-config.md#341-citable--kinds-that-declare-no-ids)).

## scope: Which files a run reads

A run reads the files its scan roots reach and its filters let through, `exclude`, the ignore files, the hidden-name rule and `extensions` among them. `exclude` is the set of directory names skipped at any depth — one path component each, so an entry containing `/` is refused rather than accepted as a path ([§FS-config.3.5.16](FS-config.md#3516-an-exclude-entry-containing--is-refused)). Where another project's directory stops a scan is [§FS-workspace.6.2](FS-workspace.md#62-the-boundary-is-mutual)'s, and a scan that reads no file is [§FS-check.2.2](FS-check.md#22-empty-scan)'s.

### scope.include: `include` is scanned from the config root

`include` is scanned **from the config root**, or, when no config was discovered, from the current working directory (never a subdirectory that merely happened to be passed as `grund`'s path argument); what an explicit path adds is each command's own ([§FS-scan.path](FS-scan.md#path-what-a-path-argument-means)). A plain parent-relative entry such as `../shared` intentionally names external content and is still scanned: the project-root fence of [§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed) binds a directory symlink only.

### scope.homes: Every configured kind home is scanned

**Every configured kind home is scanned, whether or not `include` names it** ([§FS-config.3.4](FS-config.md#34-kinds--recognized-kinds)), so `include` need name only the extra roots, such as `src` or a `README.md` ([§DF-non-citable-kinds.2.6](../decisions/functional/DF-non-citable-kinds.md#26-a-configured-home-is-in-the-scan-scope-by-construction)). A home that does not exist scans as nothing and earns no finding, so a fresh repository whose default homes are not scaffolded yet stays silent; a home whose lookup fails for another reason is not absent ([§FS-scan.scope.homes.lookup](FS-scan.md#scopehomeslookup-a-root-that-cannot-be-looked-up-is-a-scan-failure-not-an-absent-root)). A row marked `scan = false` lists its place without scanning it ([§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned)).

#### scope.homes.lookup: A root that cannot be looked up is a scan failure, not an absent root

A root does not exist only when its lookup says so: the path is not found, a component above it is a regular file, or the file system refuses the name itself as one it cannot hold, such as a `*` on Windows or a component over its length limit. A lookup that fails for any other reason, a denied permission among them, is a scan failure at the root ([§FS-check.2.4](FS-check.md#24-an-incomplete-run)), which for a kind home exits `2` at every severity its rows carry. A parent that cannot be listed while the root is still looked up and read is a failure at the parent alone, and where both fail they are two ([§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)). The rule holds for every root: a kind home, an `include` entry and a `<path>` given to a command. Decided in [§DF-home-lookup-failure-fails-at-the-home](../decisions/functional/DF-home-lookup-failure-fails-at-the-home.md#df-home-lookup-failure-fails-at-the-home-a-root-whose-lookup-fails-for-a-reason-other-than-absence-fails-at-the-root-and-exits-move-with-it).

Where a root's lookup fails, its boundaries are judged first, on where it goes as far as the disk answers, each link on the way read and what lies behind a directory that refused kept under its written names. A root that is itself a directory link out of the project is pruned in silence ([§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed)), a version 2 folder place out there is refused at load ([§FS-config-v2.schema.places.boundaries.3.1](FS-config-v2.md#schemaplacesboundaries31-judged-as-far-as-the-disk-answers)), and a root that resolves into another project stays that project's ([§FS-workspace.6](FS-workspace.md#6-nested-project-boundary)). A root link whose target cannot be looked up is followed as a file link where the walk would read its name as a file, wherever it resolves, and its failure is reported at the root. Every other root whose lookup fails, an inward link, a root that is not a link and a root written below a linked ancestor among them, is reported at the root.

A `<path>` given to a command is refused with this line, nothing on stdout and exit `2`, only where its lookup says nothing can stand there:

```text
error: path does not exist: <path>
```

A lookup refused for lack of permission, on the path itself or on any directory on the way to it, is the scan failure above instead, located at the path as given, never at the directory that refused or under a name the path resolves to ([§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)), with the fix [§FS-check.2.4.3](FS-check.md#243-what-failed-and-where-decide-the-code-and-the-fix) gives its place, which for a path that made the run read it is `passed`. That holds for a file or a directory, whether or not anything stands behind the refusal, and for every command that scans from a `<path>`: `check`, `list`, `cover`, `fmt`, `show`, `refs` and `id`, which refuses with the path and the reason alone ([§FS-id.4](FS-id.md#4-next-number-derivation)). A link given as the path is reported with the line its link earns ([§FS-scan.scope.links.owed](FS-scan.md#scopelinksowed-which-unresolvable-links-are-owed-a-report)).

The Rust library's data-returning entry points ([§FS-distribution.3.1](FS-distribution.md#31-rust-grund-core-crate)) take the path beside a field `path_provided`, `false` by default: unmarked, an existing path is only where discovery starts and the run covers what a run given no path covers; marked, it is a given `<path>`. Each entry point whose options carry a `path` — `check_with_opts`, `list`, `list_sizes`, `refs`, `format_references`, `cover`, `cover_text`, `complete_ids`, `propose_id` and the editor's `lsp_snapshot` ([§FS-distribution.2](FS-distribution.md#2-cli-parity)) — refuses one whose lookup says nothing can stand there with the error `path does not exist: <path>`, the CLI's line without its `error: ` prefix, whatever `path_provided` says, because a run that went on would answer for another tree, typically the working directory's project, without saying so. An unmarked path is refused after configuration discovery has answered, so a configuration that refuses to load is refused first ([§FS-config.1](FS-config.md#1-file-location-and-discovery)), and before anything is scanned. A marked path is refused as the CLI's `<path>` is, so a run warning its configuration earns comes before the refusal. `cover_lines` refuses an unmarked path as naming no file ([§FS-cover.6.4](FS-cover.md#64-errors)). The default path, `.`, always stands, and an unmarked path whose lookup is refused for lack of permission is not refused here.

### scope.roots: A scan root outruns every rule about descent

A home is a **scan root**, and no scan root is pruned by `exclude`, an ignore file, or the hidden-directory rule, so a home the repository also excludes is read while everything *below* it is filtered as usual: all three are rules about a descent, and `exclude` is written about descendants ([§DF-unwalked-kind-home.3](../decisions/functional/DF-unwalked-kind-home.md#3-alternatives-considered)). The two rules about a file's own name do reach a root: a file root that the hidden-file rule ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)) or the `extensions` list ([§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)) refuses is not read, and `check` names it ([§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read)).

### scope.not-a-fence: `include` is a scan scope, not a fence

A citation in a file that neither `include` nor a kind home brings into the scan is invisible rather than merely unchecked, so `grund check --full` scans the whole config root past this key; what else the flag lifts and which rules its scan keeps are [§FS-check.1.3](FS-check.md#13-the-full-tree-scope---full)'s and [§FS-check.1.3.1](FS-check.md#131-the-scan-covers-the-whole-config-root)'s.

### scope.hidden: A hidden file is not read, and the rule is not about descent

The scan skips a hidden directory by not descending into it; it skips a file whose own name begins with `.` by the name that file wears, before `extensions` is consulted at all. So a hidden file is not read even where its extension is listed, `grund check --full` does not reach it, and a citation inside it neither resolves nor dangles. Because the rule is about a name rather than a descent, it reaches a file root too: a `file` home or an `include` entry whose name is hidden is not read, and `check` names it at the row that made it a root ([§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read)). It is a declared blind spot ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)): a document that must be checked is one not named as a dotfile, and a run handed a hidden file whose extension is read says so rather than blaming the list ([§FS-check.2.2.2](FS-check.md#222-the-message-names-the-likely-cause)).

### scope.extensions: An extension makes a file readable, not declarable

Listing an extension makes a file *readable*, not declarable. A prose markup format other than Markdown — AsciiDoc, reStructuredText, LaTeX — has its citations checked as soon as its extension appears in `extensions`, because the citation grammar is format-agnostic; its native heading syntax still declares nothing, since only a line in declaration position declares ([§FS-declarations.line](FS-declarations.md#line-what-a-line-in-declaration-position-declares)).

#### scope.extensions.default: The `extensions` default follows the language table

With no `extensions` key, a run reads `md` followed by every extension grund's built-in language table names, in that table's order: each extension [§FS-inline-citation-style.1.1.2](FS-inline-citation-style.md#112-languages) assigns a doc-comment recognizer, and each language read through a comment prefix alone ([§FS-languages](FS-languages.md#fs-languages-how-a-source-files-lines-are-read)). A language the table gains is appended, so an earlier default is always a prefix of the current one. Extensions match case-sensitively, so `r` and `R` are two entries, and an explicit `extensions` replaces the default whole. Decided in [§DF-default-extensions-follow-language-table](../decisions/functional/DF-default-extensions-follow-language-table.md#df-default-extensions-follow-language-table-the-scan-extensions-default-reads-every-language-grund-classifies).

#### scope.extensions.root: A file root whose extension is unlisted is not read, and `check` says so

A scan root that is a single file — a `[[kinds]]` `file` home, a version-2 `files` entry, or an `[scan] include` entry naming a file — is read only if its extension is one `extensions` lists, or in a version-2 file one a language of `[schema.sources] languages` reads for declarations; a file a `data` language reads is read only by a value row's value pass ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)). A file with no extension at all, such as `NOTES`, is refused by the same rule, unless a version 1 list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)). The list is not widened for a root ([§DF-unread-scan-root.4](../decisions/functional/DF-unread-scan-root.md#4-alternatives-considered)): instead every `grund check` that has the root in its configured scope names it at the row that made the file a root ([§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read)), so a configuration that names a file to read and a list that keeps it out never passes as `success` ([§REQ-no-missed-citation.1](../requirements/REQ-no-missed-citation.md#1-no-silent-skips)). Which roots stay silent is that check's to say ([§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read)).

#### scope.extensions.empty: In version 1, an empty string in the list reads a file with no extension

A version 1 `[scan] extensions` that holds the empty string, as `extensions = ["md", ""]` does, reads each file whose extension is missing, empty or not UTF-8. Every reader of the list gets this one answer, so such a file is read as a file root, which then earns no warning of [§FS-scan.checks.unread-scan-root](FS-scan.md#checksunread-scan-root-a-configured-file-root-is-not-read), as a file in a directory the scan walks, as a buffer and as a stub's target. The hidden-file rule is asked first ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)). Version 1 keeps this reading for good ([§FS-config.5.2](FS-config.md#52-a-versions-meaning-moves-only-as-backwards-compatibility-allows)), and `config migrate` refuses the entry ([§FS-config.requirements.5](FS-config.md#requirements5-a-mistake-in-the-config-fails-loudly--realized-one-case-deferred), [§FS-config-migrate.3.1.9](FS-config-migrate.md#319-an-empty-string-in-scan-extensions)). The entry earns no warning of its own, because the version 1 caution ([§FS-config.5.3](FS-config.md#53-a-version-1-config-is-cautioned-and-never-retired)) already sends the file to the command that names it ([§DF-v1-empty-extension-reading](../decisions/functional/DF-v1-empty-extension-reading.md#df-v1-empty-extension-reading-version-1-keeps-reading-a-file-with-no-extension-through-an-empty-string-in-scan-extensions-and-the-specification-is-corrected-to-say-so)). Version 2 has no such entry, and refuses an empty suffix at load ([§FS-config-v2.schema.sources.extensions](FS-config-v2.md#schemasourcesextensions-schemasourcesextensions-maps-a-suffix-to-a-language)).

### scope.ignore-files: `respect_gitignore` — the ignore files

`respect_gitignore` makes the scanner honor every form of ignore file the `ignore` crate recognizes — `.gitignore` at any depth, `.git/info/exclude`, the global `core.excludesFile`, and `.ignore` files — and the directory-level `exclude` list applies **in addition** to them, never instead. An ignore file means what git means by it, in git's precedence: `.ignore` files, then the `.gitignore` files up to the repository top, then that repository's `info/exclude`, then the global file. The walk, its probe of a single path and a stub target's eligibility read the same rules and the same global file ([§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing)).

The global file is the existing readable file at the pathname Git resolves, where a `~` is a home abbreviation only at the start (`~/`, `~user/`) and a literal character anywhere else ([§DF-global-excludes-literal-tilde](../decisions/functional/DF-global-excludes-literal-tilde.md#df-global-excludes-literal-tilde-preserve-literal-tildes-in-the-global-excludes-pathname)). Each of its patterns anchors at the top of the repository its path belongs to: the nearest directory above the path that holds `.git` or a Jujutsu `.jj`, the innermost one where repositories nest, and a path below no top is matched by none of its patterns. Neither the directory grund runs from, nor a config root or scan root above the top, nor the spelling a platform gives the paths it walks moves the top ([§REQ-deterministic-output.2](../requirements/REQ-deterministic-output.md#2-input-is-the-tree-the-config-and-the-invocation), [§DF-global-excludes-anchor-at-the-repository-top](../decisions/functional/DF-global-excludes-anchor-at-the-repository-top.md#df-global-excludes-anchor-at-the-repository-top-a-global-excludes-pattern-anchors-at-the-repository-top-wherever-grund-runs-from)). That is git's top, except in a jj workspace with no `.git` nested inside a git repository, where git anchors at the outer top and grund at the workspace.

A line of an ignore file that does not parse takes its rule with it, so it is a scan failure at the ignore file ([§FS-check.2.4](FS-check.md#24-an-incomplete-run), [§FS-check.2.4.2](FS-check.md#242-one-failure-one-line)), wherever the walk meets the file and whether or not a kind home lies below it. Two kinds of file cost the walk that met them no rule, so their unparsed lines are no failure of that walk, however it met the file; one walk that reads under such a file is enough to report it ([§DF-unparsed-ignore-file-at-any-depth](../decisions/functional/DF-unparsed-ignore-file-at-any-depth.md#df-unparsed-ignore-file-at-any-depth-an-ignore-file-the-walk-cannot-parse-fails-the-run-at-any-depth-unless-the-run-does-not-apply-it)):

1. A `.ignore` or `.gitignore` that governs nothing the walk reads, because `exclude` keeps out whatever its directory holds, or whatever the walk root holds where that root lies below the file, by the test any file there faces on the way down ([§FS-config-v2.schema.sources.exclude.roots](FS-config-v2.md#schemasourcesexcluderoots-how-exclude-composes-with-the-other-filters)). Excluding the ignore file itself, as `.ignore` or `.*` does, clears nothing: it keeps the file from being read as a source and leaves its rules in force over what the directory still holds. `.git/info/exclude` governs its whole repository, so this never clears it.
2. A `.gitignore` no repository encloses, which a walk does not apply, except under a mounted root ([§FS-remote-projects.ignore](FS-remote-projects.md#ignore-ignore-isolation)). A `.ignore` applies with or without a repository, and a `.gitignore` the walker passes over for another reason, such as one above a nested repository, still fails the run.

### scope.links: A symlink in the tree is followed

A **file symlink** inside a scanned tree is followed wherever its target resolves. A **directory symlink** is followed only while its canonical target remains inside the independently checked project's canonical root; when the target is outside that root, the directory is pruned and no file below it is scanned. The same gate applies when a configured or explicit scan root is itself a directory symlink. Decided in [§DF-symlink-scan](../decisions/functional/DF-symlink-scan.md#df-symlink-scan-a-symlink-in-the-scanned-tree-is-followed-and-the-report-names-the-link).

The fence is the canonical root even when the repository itself was reached through a symlink, so its tree stays readable, and it binds links only: a parent-relative `include` entry may still name external content ([§FS-scan.scope.include](FS-scan.md#scopeinclude-include-is-scanned-from-the-config-root)). A loaded workspace adds the ownership boundary of [§FS-workspace.6](FS-workspace.md#6-nested-project-boundary), so a link into another loaded project is pruned even when that project lies inside the current project's root.

#### scope.links.names: The directory rules apply under the link name

The directory rules of [§FS-scan.scope](FS-scan.md#scope-which-files-a-run-reads) still apply to a followed directory under its **link** name, so `docs/node_modules -> ../../node_modules` is excluded exactly as a real directory of that name would be. Two boundaries are not name rules and hold however a link reaches them: another project's root, which a link may not carry a scan across in any direction ([§FS-workspace.6](FS-workspace.md#6-nested-project-boundary)), and an E2E case directory, whose fixture tree stays out of the host scan ([§FS-config.3.4.4.3](FS-config.md#3443-e2e-is-configured-not-a-default)).

#### scope.links.unresolvable: A link the scan cannot resolve is reported, and not scanned into

A link the scan cannot resolve is not a silent skip: a broken target, a loop, or a directory link whose target exists but cannot be opened is the scan failure of [§FS-check.2.4](FS-check.md#24-an-incomplete-run), located at the link ([§FS-check.2.4.2](FS-check.md#242-one-failure-one-line), [§REQ-no-missed-citation.1](../requirements/REQ-no-missed-citation.md#1-no-silent-skips)). The walk goes past the link and never *into* it: a loop is pruned where it is met, including the kind whose target reaches back over the scan root itself, so the run never reports findings out of a tree it has just called unreadable and `include` bounds what was read.

A link that a hidden name, `exclude` or an ignore file keeps out of the walk stays silent wherever it points ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded)), though a target another walk reads keeps the line that walk earns, while a link standing at a home the config lists without walking ([§FS-config.3.4.7.2](FS-config.md#3472-not-scanned-however-the-scan-arrives)) is reported. Decided in [§DF-unopenable-link-fails-at-the-link](../decisions/functional/DF-unopenable-link-fails-at-the-link.md#df-unopenable-link-fails-at-the-link-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-or-is-pruned-and-exits-move-with-it-in-both-directions).

A looping link handed to a run as its `<path>` exists, so the run reports the walk's failure at the link, never `path does not exist`, whatever the link's extension.

#### scope.links.owed: Which unresolvable links are owed a report

That report is owed only where the scan would otherwise have read through the link, judged by the rules any other entry faces there. A broken link, one whose target lookup says nothing can stand there ([§FS-scan.scope.homes.lookup](FS-scan.md#scopehomeslookup-a-root-that-cannot-be-looked-up-is-a-scan-failure-not-an-absent-root)), names a file, so `extensions` judges it as well, and a dangling link whose extension is not listed stays silent. A link whose resolution loops — one reaching back to a directory above it, one naming itself, each link of a cycle of links — is a loop and not a broken link, and is judged as a directory, whatever its name: by the ignore files as a directory, a hidden name and either version's `exclude`, never by `extensions` ([§DF-looping-link-is-a-loop](../decisions/functional/DF-looping-link-is-a-loop.md#df-looping-link-is-a-loop-a-link-whose-resolution-loops-is-a-loop-whatever-its-name-judged-by-the-ignore-files-as-a-directory-and-exits-move-with-it-in-both-directions)). A link whose target lookup is refused for lack of permission, on the target or on any directory on the way to it, is not broken whatever its name: it is a directory link whose target cannot be opened, reported at the link whether or not anything stands behind the refusal, and so is such a link given as the path itself ([§DF-refused-link-lookup-is-not-a-broken-link](../decisions/functional/DF-refused-link-lookup-is-not-a-broken-link.md#df-refused-link-lookup-is-not-a-broken-link-a-directory-link-whose-target-lookup-is-refused-on-the-way-is-unopenable-not-broken-and-exits-move-with-it)). A directory-only pattern such as `docs/ext/` covers a loop and an unopenable link alike, as it covers the followed link ([§FS-scan.scope.links.names](FS-scan.md#scopelinksnames-the-directory-rules-apply-under-the-link-name)), and never a dangling link, which names a file.

A directory link answers to the project-root fence of [§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed) and the ownership boundary of [§FS-workspace.6](FS-workspace.md#6-nested-project-boundary) on its canonical target, which is worked out from the directories on the way to it, as far as the disk answers, and never from the target's own contents, so it is known whether or not the target opens. An unopenable link whose target lies outside the project and in no tree the run reads is pruned in silence, whichever walk root meets it. One whose target is inside the project, or in a tree the run does read, a project of the run or an import's tree ([§FS-imports.mount](FS-imports.md#mount-an-import-is-a-mounted-root-read-live-and-read-only)), is owed its report at the link, though the walk does not read through it. A link named as the scan root itself answers to the root's gate ([§FS-scan.scope.links](FS-scan.md#scopelinks-a-symlink-in-the-tree-is-followed)). Decided in [§DF-unopenable-link-fails-at-the-link](../decisions/functional/DF-unopenable-link-fails-at-the-link.md#df-unopenable-link-fails-at-the-link-a-directory-link-whose-target-cannot-be-opened-fails-at-the-link-or-is-pruned-and-exits-move-with-it-in-both-directions).

#### scope.links.blind-spot: A broken link with no extension is a declared blind spot

A broken link with **no extension at all** is silent for the same reason, unless a version 1 list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)), and it is the one case where that answer can be wrong: `docs/shared -> ../nonexistent-dir` would have been a directory to descend into had it resolved. Nothing on disk distinguishes it from `bin/tool -> nowhere`, since only the missing target could have said which it was, so it is a declared, bounded blind spot ([§REQ-no-missed-citation.2](../requirements/REQ-no-missed-citation.md#2-every-blind-spot-is-declared-and-bounded), [§DF-symlink-scan.2.4](../decisions/functional/DF-symlink-scan.md#24-a-link-the-walk-cannot-resolve-is-reported-and-the-walk-continues)): a link you need scanned is one you need to resolve. A link whose resolution loops is not broken and is not in it ([§FS-scan.scope.links.owed](FS-scan.md#scopelinksowed-which-unresolvable-links-are-owed-a-report)).

## identity: Which path names a file a run read

A file a run reaches through a link is named by the path the run met, and a physical file is read once, one way.

### identity.link-path: A finding names the in-tree link path

Every finding from a link met **inside a scanned tree** is reported at the in-tree link path, never the target's ([§DF-symlink-scan.2.3](../decisions/functional/DF-symlink-scan.md#23-the-report-names-the-link-never-the-target)), and so is one from a link the run is handed as its path: `grund check docs/beta.md` reads the link's target and names `docs/beta.md`, spelled from the CLI base ([§FS-cli.3.4](FS-cli.md#34---path-base--where-report-paths-are-spelled-from)), in text and JSON alike, even where the target resolves outside the config root. A content finding is still the whole run's one line, which may name the link second ([§FS-scan.identity.findings.content](FS-scan.md#identityfindingscontent-a-content-finding-is-one-line-naming-every-name)).

### identity.root-path: The scan root keeps the path the run was handed

The same holds for the **scan root itself**: a repository whose own path is reached through a link, a symlinked `~/work` or macOS resolving `/var` to `/private/var`, is scanned and reported under the path the run was handed, never the physical one it resolves to.

### identity.read-once: One physical file is read once

One **physical** file is read once however many spellings reach it, and the run keeps every spelling. Spellings are listed the earlier root's first, and within one root lexicographically ([§FS-check.1.3](FS-check.md#13-the-full-tree-scope---full), [§FS-errors.4](FS-errors.md#4-determinism)). That order picks only the name listed first, never what the file is read as ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)), the homes it is judged in ([§FS-config-v2.schema.places.ownership](FS-config-v2.md#schemaplacesownership-a-listed-file-then-the-deepest-folder), [§FS-declarations.checks.misplaced-declaration](FS-declarations.md#checksmisplaced-declaration-misplaced-declaration-configured-kind-home)) or the names a finding carries ([§FS-scan.identity.findings](FS-scan.md#identityfindings-a-finding-about-a-file-with-two-names-names-each-spelling-once)). Two names are one file exactly where they resolve to one path, a file link and anything below a directory link alike. Hard links resolve to two paths and are two files, so a declaration in one is a duplicate of itself in the other ([§FS-declarations.checks.duplicate](FS-declarations.md#checksduplicate-duplicate-declaration)).

### identity.reading: How a file is read belongs to the file, not to the name that reached it

A file inside the config root is read as its own name reads, when that name claims a reading; any other file keeps the reading of the name that reached it, and is refused where two in-tree names read it differently ([§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)). Decided in [§DF-one-file-one-reading](../decisions/functional/DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name). With `txt` configured as Rust, `fs/a-link.txt -> m-real.md` reads as Markdown and `fs/m.md -> z.txt` as Rust, so `fmt` rewrites no string literal of the Rust file through its `.md` name ([§FS-fmt.2.3](FS-fmt.md#23-what-is-never-rewritten)).

A name claims a reading when an admitted language reads it under version 2 ([§FS-config-v2.schema.sources.extensions](FS-config-v2.md#schemasourcesextensions-schemasourcesextensions-maps-a-suffix-to-a-language)), or when the extension list holds its extension under version 1. So `LICENSE` claims nothing, unless a version 1 list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)). Only the name counts: a file whose own spelling is ignored, excluded, hidden or under no source still claims by its name, so `docs/fs/gen.md -> ../../build/gen.rs` reads as Rust with `build/` ignored. Whether a spelling enters the scan at all is asked of the spelling met, by the hidden-file rule and the extension list ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent), [§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)), so a refused spelling stays unread, and no finding about the file stands at it or names it among its sites.

The names with a say are those the plain run reaches ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)), when it reaches any. A name reached only by `--full`, or only by being handed to a run, such as a path under a directory the configuration excludes, decides nothing: not the reading, not a refusal or a move ([§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently), [§FS-scan.checks.reading-moved](FS-scan.md#checksreading-moved-a-link-is-read-as-its-targets-own-name-reads)), and not the name a finding stands at. Where the plain run reaches none of a file's names, the names the run met are judged among themselves, and the finding stands in the out-of-scope tier ([§FS-check.3.14](FS-check.md#314-out-of-scope-unresolvable-citation---full-only)).

Every run and every reader of the file asks this one rule: the text scan, the value reader, the checker, the formatter, `show` and the editor. So the value reader takes a file's JSON or YAML reading from this rule, and reads a text-named link to a value source once ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)). A narrow `fmt`, `cover` or `refs` run reads the file as the whole run does, so `fmt docs/license.rs --write` cannot rewrite a file another name reads as Markdown. A stub's written name is judged as written ([§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing)), and its target's text is read through this rule.

### identity.findings: A finding about a file with two names names each spelling once

A file reached by two names has one set of declarations and citations, and a finding about it repeats no line and names no spelling twice. How it names them depends on whether the finding depends on where the file sits.

#### identity.findings.place: A place finding is judged at each spelling

A rule that asks which row owns a file asks it of every spelling at its own path: misplaced declarations, citation directions of a file, grounding, indexes and stubs ([§FS-config-v2.schema.places.ownership](FS-config-v2.md#schemaplacesownership-a-listed-file-then-the-deepest-folder), [§FS-config.3.9.2](FS-config.md#392-the-homeless-kind)). Each finding stands at the spelling it holds at, whichever spelling sorts first. Each folder of a row that holds a spelling owes its index an entry, told at that spelling, even where the name listed first is in no home, and an entry in that index answers it under either name. A run naming a path narrows a place finding by the name it stands at, and a run that reaches the file by no in-tree name, through a link outside the root, keeps it at the file's own name. The editor shows a place finding at its own spelling only.

#### identity.findings.content: A content finding is one line naming every name

The file's declarations and citations stand at the name listed first: `decl.file` and `cite.file` hold it, and `list`, `refs` and `show` print one row there, while an ambiguous `show` names both ([§FS-declarations.checks.duplicate](FS-declarations.md#checksduplicate-duplicate-declaration)). A run of those three naming a path lists the name it was handed first ([§FS-scan.identity.link-path](FS-scan.md#identitylink-path-a-finding-names-the-in-tree-link-path)).

A finding about what the file holds is one line at the name listed first, the other names in a closing clause, and JSON carries them all in `sites`. With `notes/link.md -> ../docs/fs/a.md`:

```text
docs/fs/a.md:5: error: unknown reference FS-gone (also at notes/link.md:5)
```

The clause closes the line, except on a count row that names the citations it counted, where it stands directly after the remedy and before `; counted at` ([§FS-rules.7.3.1](FS-rules.md#731-a-count-above-zero-names-the-citations-it-counted)). A citation direction asked of a declaration follows the declaration's own kind, so a finding that it owes a citation, or holds one it must not, is one of these at any spelling, while the same code about a file is a place finding. Whatever else the finding names, a duplicate's other sites or the declaration a value mismatch points at, is named by the first name of its file from every scope, and a literal the author wrote stays as written. `check` naming any spelling prints the whole run's line ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)), which names only the spellings the plain run reaches ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)). The editor shows it on every name of the file it has open, once on each.

#### identity.findings.judged: A finding that resolves from the file's directory names the spelling it was judged at

A finding that resolves a relative path from the file's directory, such as a stub's link, can hold at one spelling and fail at the other: it is judged at the name listed first alone, and names that spelling with no closing clause, the limit [§FS-fmt.2.3.2.2](FS-fmt.md#2322-a-link-inside-the-config-root-is-written-through) names.

### identity.buffers: A buffer is the file at its physical location

An editor buffer is the file at the physical location its path resolves to, under whatever spelling the editor opened it and whatever spelling a stub or the walk reaches that file by. Decided in [§DF-a-buffer-is-the-file](../decisions/functional/DF-a-buffer-is-the-file.md#df-a-buffer-is-the-file-an-editor-buffer-is-the-file-it-names-under-every-spelling-and-with-no-file-saved-behind-it). Where `alias -> notes`, a buffer the editor opened as `notes/a.md` is the text of `alias/a.md`, so a stub that writes `../alias/a.md` reads the buffer as it would read the saved file ([§FS-scan.text.buffer](FS-scan.md#textbuffer-a-files-text-is-what-a-save-would-write)). Where the run holds a refusal for the file ([§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently)), the editor offers no on-type edit in it.

### identity.unresolved: A path that does not resolve keeps its components, and nothing is appended

A path the filesystem cannot resolve to its end, such as a buffer with no file behind it ([§FS-scan.text.buffer-only](FS-scan.md#textbuffer-only-a-buffer-with-no-file-behind-it-is-a-file)), a broken link or an entry under a directory that cannot be searched, is spelled as the canonical form of its longest existing prefix followed by the components that did not resolve, in their order, and by nothing else. A path whose every component exists but whose canonical form the filesystem will not give keeps its lexical form under the same rule. So the text ends in the path's last component and never in a separator, `<root>/real/unsaved.md` and not `<root>/real/unsaved.md/`, because a trailing separator says "directory" about a name that may be a file. This binds `canonical_snapshot_path`'s return value and the `path` of every finding in an `lsp_snapshot` report.

## text: Which text a file has

Every reader in a run reads one text per file, the one a save would write, for a file on disk and for one the editor has never saved.

### text.buffer: A file's text is what a save would write

A file's text is what saving it would write: the editor's open buffer where there is one ([§FS-scan.identity.buffers](FS-scan.md#identitybuffers-a-buffer-is-the-file-at-its-physical-location)), and the disk only where there is none, so a run from the command line, which holds no buffers, reads the disk. That holds for every reader a run has, the walk's scan of each file, a stub's target ([§FS-declarations.stubs.target.1](FS-declarations.md#stubstarget1-the-target-is-read-as-a-save-would-write-it)) and the body `show` slices out of it ([§FS-show.2.3](FS-show.md#23-source-declarations-in-code-and-doc-comments)) among them, so an unsaved edit moves every answer at once, exactly as saving it would ([§REQ-one-answer.text.targets](../requirements/REQ-one-answer.md#texttargets-a-stubs-target-answers-as-its-saved-text-would)).

### text.buffer-only: A buffer with no file behind it is a file

A buffer with no file on disk behind it, a new file the editor has not saved, is a file of the run. A stub to it is never `stub link target missing` and is judged on the buffer's text ([§FS-declarations.stubs.target.1](FS-declarations.md#stubstarget1-the-target-is-read-as-a-save-would-write-it)). The walk reads it or skips it exactly as it would the saved file ([§FS-scan.scope](FS-scan.md#scope-which-files-a-run-reads)), so a buffer for a file the walk skips is not read. As a stub's target outside `include` it is read as a saved file would be ([§FS-show.2.3](FS-show.md#23-source-declarations-in-code-and-doc-comments)), by the name and extension rules of [§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing) alone.

## checks: Checks

Each check here is located, rendered, selected and exits as [§FS-check.2.1](FS-check.md#21-report-format) says, at the severity and with the fix of its row of [§FS-errors.5.5](FS-errors.md#55-the-check-code-catalog).

### checks.reading-conflict: Two names of one file read it differently

Two in-tree names of a file whose own name claims no reading, or whose own name lies outside the config root, that read it differently leave nothing to decide by ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)). The run refuses the file, reading it under neither name, with one `reading-conflict` finding at the name listed first:

```text
docs/license.md:1: error: docs/license.md and docs/license.rs are one file that reads two ways, as markdown and as rust; keep one name, or give the file a name that claims a reading
```

The readings are named in the names' order, by language under version 2 and by extension under version 1, `markdown` for `md` and `source with no extension` for a name with none. JSON `sites` names both spellings, each once, and the finding is in scope at either ([§FS-check.1.3.6.2](FS-check.md#1362-a-finding-that-spans-several-sites-is-in-scope-at-any-of-them)). Only the names with a say are judged ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)). Neither selection axis hides it ([§FS-check.2.1.2](FS-check.md#212-selection-filters-the-complete-report)). `fmt` leaves the file alone ([§FS-fmt.2.3.2.3](FS-fmt.md#2323-a-file-two-names-read-differently-is-not-written)). Decided in [§DF-one-file-one-reading](../decisions/functional/DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name).

### checks.reading-moved: A link is read as its target's own name reads

A file whose reading moved under [§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it) earns one `reading-moved` warning at the name listed first, where that name is a link whose own reading differs from what the file is read as. Only the names with a say are listed ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)), and a reading is named as [§FS-scan.checks.reading-conflict](FS-scan.md#checksreading-conflict-two-names-of-one-file-read-it-differently) names it:

```text
docs/fs/gen.md:1: warning: read as rust, as its target's own name reads, not as markdown (since 0.22.0); rename the target or copy the file
```

Decided in [§DF-one-file-one-reading](../decisions/functional/DF-one-file-one-reading.md#df-one-file-one-reading-a-file-reached-by-two-names-is-read-as-its-own-name-reads-and-judged-and-reported-at-each-name). The warning stands for one minor release. grund 0.23.0 removes it: from there the code is spent, as the catalog says of a spent code, and the rule of [§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it) stands alone.

### checks.unread-scan-root: A configured file root is not read

`check` reports `unread-scan-root` at a scan root that is a single file, a `[[kinds]]` `file` home, a version-2 `files` entry or an `[scan] include` entry naming a file, whose name is hidden ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)) or whose extension the extension list leaves out ([§FS-scan.scope.extensions.root](FS-scan.md#scopeextensionsroot-a-file-root-whose-extension-is-unlisted-is-not-read-and-check-says-so)), so no file the configuration names is skipped in silence ([§REQ-no-missed-citation.1](../requirements/REQ-no-missed-citation.md#1-no-silent-skips)). A configured folder home, a `[[kinds]]` `folder` home or an entry of a version-2 `folders` key, is the same blind spot and earns it when the run read no file in it, by the walk or by the value pass ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)), though the walk refused at least one file in it by its extension or its language ([§DF-reading-at-fetch-and-unread-homes.2.5](../decisions/functional/DF-reading-at-fetch-and-unread-homes.md#25-a-folder-home-nothing-in-which-is-read-is-named)).

It is one warning per unread root, a root both rules refuse included ([§DF-unread-hidden-root.2.1](../decisions/functional/DF-unread-hidden-root.md#21-one-warning-names-both-rules)), located in the `grund.toml` that configured it at the line of the key that named the root: the `file` key of its `[[kinds]]` row, the `files` key of its version-2 row, the `[scan] include` key, or a folder home's `folder` or `folders` key. Two entries of one array share that line and sort by message ([§FS-errors.4](FS-errors.md#4-determinism)). Though it stands at a `grund.toml` line, it is a located finding on stdout, not a CLI-level message ([§FS-check.2.1.1](FS-check.md#211-cli-level-messages), [§DF-unread-scan-root.2.1](../decisions/functional/DF-unread-scan-root.md#21-check-alone-says-it)). As a finding about the default scope it replaces the empty-scan caution where the unread root, a folder home in which nothing was read included, was all the run would have read ([§FS-check.2.2.3](FS-check.md#223-exit-code-json-and-what-suppresses-it)).

Every `check` that loads the configuration asks it of every configured root, `--full` included ([§FS-check.1.3.2](FS-check.md#132-the-wider-scan-reads-a-superset-each-file-once)). A run given a path reports it only where the path covers the `grund.toml` that holds the row ([§FS-scan.path.check](FS-scan.md#pathcheck-check-reads-more-than-it-reports)); a path typed on the command line has no row behind it, so `grund check notes.txt` keeps the caution of [§FS-check.2.2.2](FS-check.md#222-the-message-names-the-likely-cause). In a workspace each project is asked on its own, and the warning is located in that project's own `grund.toml`. `list`, `refs`, `show`, `cover` and `fmt` read the same files and do not say it ([§DF-unread-scan-root.2.1](../decisions/functional/DF-unread-scan-root.md#21-check-alone-says-it)).

Nothing else earns it. A row marked `scan = false` is not a root ([§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned)), and a home or entry that does not exist earns nothing ([§FS-scan.scope.homes](FS-scan.md#scopehomes-every-configured-kind-home-is-scanned)). A hidden file inside a directory root earns nothing, and nor does a value row's home that is a value source, of either format, which the value pass reads whatever the list says ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)). A directory root is filtered file by file, so an `[scan] include` entry naming a directory whose files are all unlisted earns nothing here, and the empty-scan caution still speaks when the run read nothing at all ([§FS-check.2.2](FS-check.md#22-empty-scan)). In a folder home, a file whose name is hidden, or that an exclude pattern or an ignore file keeps out, never counts, read or refused ([§FS-scan.scope.hidden](FS-scan.md#scopehidden-a-hidden-file-is-not-read-and-the-rule-is-not-about-descent)), so a home that is empty or holds only such files, such as a fresh home holding only `.gitkeep`, earns nothing.

A read by either pass satisfies every folder home that holds a spelling of the file the walk or value-source discovery admitted, whichever spelling the reader chose ([§FS-scan.identity.read-once](FS-scan.md#identityread-once-one-physical-file-is-read-once)). Whether a spelling is admitted is asked of that spelling ([§FS-scan.identity.reading](FS-scan.md#identityreading-how-a-file-is-read-belongs-to-the-file-not-to-the-name-that-reached-it)), so a refused or filtered name gains nothing from a target read elsewhere, and a file discovered but read by neither pass satisfies no home.

The message is `<row> is not read — <reason>, so nothing in it is checked. <fix>.` The row names the file or folder as the configuration wrote it:

| Root | `<row>` |
|---|---|
| a `[[kinds]]` `file` home | ``[[kinds]] <KIND> home `<file>` `` |
| an `[scan] include` entry | ``[scan] include entry `<entry>` `` |
| a version-2 `files` entry | ``[schema.kinds.<KIND>] file `<file>` `` |
| a `[[kinds]]` `folder` home | ``[[kinds]] <KIND> home `<folder>` `` |
| a version-2 `folders` entry | ``[schema.kinds.<KIND>] folder `<folder>` `` |

The reason is the one wording of why a name is not read, the data row included: the broken-stub line of [§FS-declarations.stubs.target.3](FS-declarations.md#stubstarget3-a-target-the-scan-does-not-read-declares-nothing) and `fetch`'s refusal of a home the scan does not read ([§FS-fetch.4.2.1](FS-fetch.md#421-a-home-the-scan-does-not-read-is-refused)) say the same cell for the configuration and the name. A folder home's reason is said of the first file in it the walk refused, in path order. For a name that is not hidden, the reason names the extension as the name spells it, the part after the last `.`, or says there is none, and a name ending in `.` has none:

| Configuration | The file has an extension | The file has none |
|---|---|---|
| version 1 | `extension <ext> is not in [scan] extensions` | `it has no extension, and [scan] extensions reads a file only by its extension` |
| version 2 | ``no language in [schema.sources] languages reads `.<ext>` `` | `it has no extension, and [schema.sources] languages reads a file only by its extension` |

In a version-2 file, a name a listed language of class `data` reads, by its suffix or through a `[schema.sources.extensions]` entry ([§FS-config-v2.schema.sources.extensions](FS-config-v2.md#schemasourcesextensions-schemasourcesextensions-maps-a-suffix-to-a-language)), is read only by a value kind's value pass ([§FS-values.2.2](FS-values.md#22-declarations-from-value-sources)). Its reason is the data row, in place of the version-2 cell, naming the suffix as the name spells it and the language as the configuration names it, and a name no listed language claims keeps the version-2 cell ([§DF-reading-at-fetch-and-unread-homes.2.3](../decisions/functional/DF-reading-at-fetch-and-unread-homes.md#23-a-name-a-data-language-reads-has-its-own-reason)):

| Configuration | A listed `data` language reads the name |
|---|---|
| version 2 | ``the scan reads `.<ext>` as `<language>`, a data language only a value kind reads`` |

For a root whose name begins with `.`, the reason says so first, and names the extension as well where the list refuses it too, so one warning names every rule that keeps the file out:

| The hidden file | Reason |
|---|---|
| has an extension the list holds, or has none and the list holds the empty string ([§FS-scan.scope.extensions.empty](FS-scan.md#scopeextensionsempty-in-version-1-an-empty-string-in-the-list-reads-a-file-with-no-extension)) | `` its name begins with `.`, and grund reads no hidden file `` |
| has one it does not, version 1 | ``its name begins with `.`, and extension <ext> is not in [scan] extensions`` |
| has one it does not, version 2 | ``its name begins with `.`, and no language in [schema.sources] languages reads `.<ext>` `` |
| has one a listed `data` language reads, version 2 | ``its name begins with `.`, and the scan reads `.<ext>` as `<language>`, a data language only a value kind reads`` |
| has none, such as `.notes`, and the list does not hold the empty string | `` its name begins with `.`, and it has no extension `` |

The fix is the one edit that makes the row say what it means, given as cases of the row's *Fix* ([§FS-errors.5.5](FS-errors.md#55-the-check-code-catalog)) joined as alternatives, `a`, `a, or b`, `a, b, or c`. A hidden root's one rename satisfies every rule that keeps it out ([§DF-unread-hidden-root.2.1](../decisions/functional/DF-unread-hidden-root.md#21-one-warning-names-both-rules)), and a hidden file in a folder home never counts:

| Root | The list refuses its extension | It has no extension | Only its hidden name refuses it | Its hidden name and the list refuse it |
|---|---|---|---|---|
| a version-1 `[[kinds]]` `file` home | `add`, `give` | `rename` | `hidden` | `hidden-list` |
| an `[scan] include` entry | `add`, `drop` | `rename`, `drop` | `hidden`, `drop` | `hidden-list`, `drop` |
| a version-1 `[[kinds]]` `folder` home | `add` | `folder-rename` | — | — |
| a version-2 `files` entry | `language` | `language` | `hidden` | `hidden-language` |

A version-2 rule row takes `document` for `language`. A name the data row explains takes `value` on a citable row that sets no `form` or `fetch` and meets every value-form prerequisite, its fields and an authored `closed` key as they stand ([§FS-fields.forms](FS-fields.md#forms-form-lowers-to-the-version-1-contracts)), `document` elsewhere, and `hidden-document` where its name is hidden ([§DF-reading-at-fetch-and-unread-homes.2.4](../decisions/functional/DF-reading-at-fetch-and-unread-homes.md#24-what-is-offered-for-a-data-reading)). A rename is offered only to a suffix an admitted reader of the class the row needs reads: a data reading and a rule row need a document reader, while any other row may take a source reader too. Where none is admitted, the rename is `document-admit` instead, its `{rename}` `give the file an extension it reads`, or `rename the file to a name that is not hidden and an extension it reads` for a hidden name, and where a name that is not hidden would take `value`, `value-repair` carries it, lowercased, as its `{repair}`. No data-only admission repairs a prose scan.

A version-2 folder home's fix has its first refused file read, said of the files in it. Where the data row does not explain that file and an unlisted built-in language ([§FS-config-v2.schema.sources.epoch](FS-config-v2.md#schemasourcesepoch-the-v2-language-epoch)) of the class the row needs reads its extension, the fix is `folder-add`, said `folder-add-document` on a row that sets `form = "rule"`, which needs a document language. Otherwise it is the file root's case in its folder form: `folder-language`, `folder-document` or `folder-value` for `language`, `document` or `value`, and `document-admit` with `give the files in it an extension it reads`, carried by `value-repair` where it would be. A rule row's homes must be read as Markdown ([§FS-config-v2.schema.sources.rules](FS-config-v2.md#schemasourcesrules-every-home-of-a-rule-kind-is-judged-by-its-reading)), so a rule folder no admitted language can read as Markdown is refused at load ([§FS-config-v2.checks.config-rule-folder-not-markdown](FS-config-v2.md#checksconfig-rule-folder-not-markdown-a-rule-kinds-folder-can-hold-no-markdown)) and never earns this warning.

A file or folder home on a row with `citable = false`, which may name it only as a place in the Project map, ends its fix with `place` ([§FS-config.3.4.7](FS-config.md#347-scan--a-place-that-is-listed-not-scanned)). So, for four roots, the last in a run that admits a `document` definition reading `.adoc` and no language that reads `.md`:

```text
grund.toml:7: warning: [[kinds]] NOTES home `NOTES` is not read — it has no extension, and [scan] extensions reads a file only by its extension, so nothing in it is checked. Rename the file to an extension the list holds, or set `scan = false` on the row if it only lists a place.
grund.toml:10: warning: [[kinds]] TXT home `.notes.txt` is not read — its name begins with `.`, and extension txt is not in [scan] extensions, so nothing in it is checked. Rename the file to a name that is not hidden and an extension the list holds.
grund.toml:6: warning: [schema.kinds.FS] file `fs.json` is not read — the scan reads `.json` as `json`, a data language only a value kind reads, so nothing in it is checked. Set `form = "value"` on the row, or give the file an extension a listed document language reads.
grund.toml:17: warning: [schema.kinds.RULE] folder `rules` is not read — no language in [schema.sources] languages reads `.md`, so nothing in it is checked. Add `markdown` to [schema.sources] languages, or give the files in it an extension a listed document language reads.
```
